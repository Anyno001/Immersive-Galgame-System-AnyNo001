# combat 模块契约

## 职责

- 战斗扩展的领域逻辑：规则常量、数据契约校验、战斗引擎、托管策略、成长日志归并、副 LLM 生成校验、战报构造与战斗会话编排。
- 设计与计划：`.limcode/design/combat-expansion.md`、`.limcode/plans/combat-expansion.plan.md`；实施核实结论见 `docs/COMBAT_EXPANSION.md`。

## 依赖方向

- combat 只依赖 scene 的解析结果与经参数注入的 data/shujuku 适配器；不导入 visual、host、core。
- visual 与 core 依赖 combat；宿主发送、副 LLM、存储均由调用方传入。

## 文件

- `rules.js`：`COMBAT_RULES`（每回合能量 3、抽牌 5、卡组 20–30 张、敌人档位、职业原型）、基础卡 `BASIC_CARDS`、卡牌价值预算 `evaluateCardBudget`、经验曲线 `levelFromExp/expProgress`。`cardCopyLimit(rarity)`：basic / common / uncommon / rare / epic / personal 同名上限 3，mythic / signature 为 1，未知档返回 0；`validateDeck(deck, owned, catalog)` 必须由目录提供稀有度，缺卡返回 `unknown-card`、未知档返回 `invalid-rarity`，不放行。日志回放、自动入组、构筑按钮及奖励候选共用上限。稀有度窗口 `rarityWindows`（每档 `min / max / target` × 费用预算；`rarityWindow(cost, rarity)` 返回校验窗口与求解中心）：旧档位窗口保留；epic 为 0.9–1.5、目标 1.3，mythic 为 1.2–1.65、目标 1.45，signature 为 1.2–1.6；升级上限为窗口上限 × 1.3。未登记稀有度拒收，不回落 common。另有 `signatureLimit 2`、`signatureCopyLimit 1`、技能角色强度档 `allyTiers`（support / peer / ace / legend 的生命、技能倍率与绝招冷却，暂定值）与 `defaultAllyTier 'peer'`。
  - 敌人开战数值 `scaleEnemyStats(profile, level, difficulty, { gap })`：生命 = 档案生命 ×（1 + `tierScalePerLevel` 0.05 ×（等级 − 1））× 难度 hp × 档位 `hpScale` ×（1 + `levelGap.hp` 0.02 × 等级差）；伤害倍率 = 难度 damage × 档位 `damageScale` ×（1 + `levelGap.damage` 0.04 × 等级差），取两位小数、上限 5。等级差为敌人推导等级高出我方平均等级的部分，`enemyUnits` 传入，没有属性视图时为 0。档位校准倍率按 `scripts/combat-balance.mjs` 的托管模拟取值（普通 1.3 / 2.7、精英 1.15 / 1.75、首领 0.68 / 1）；档案生命区间与技能伤害上限仍按 `hp / damageCap` 校验，已入库档案与旧战斗记录重放不受影响。

- `schema.js`：效果原语、卡牌、技能、被动、档案（`class / deck-character / skill-character / enemy`）与成长日志条目的判别联合校验。`deck-character.heroSkill` 可选（人物技能，`{ id, name, effects, description? }`），效果按 `COMBAT_RULES.heroSkillCost` 费用的 `personal` 预算校验；旧档案没有该字段时由 `session.js` 按职业原型回落 `defaultHeroSkill`。`deck-character.signatureCards` 可选（0–2 张，只收 `signature` 稀有度，ID 不得与职业池 / 个人池 / 基础卡冲突，不得进入起始卡组 → `signature-in-starter`）；`skill-character.tier` 可选（`allyTiers` 的键）。两字段缺省时都不补字段。
- `random.js`：确定性哈希与伪随机数，用于战斗重放。
- `battle-state.js`：只读的战局查询与数值估算（存活单位、最弱目标、卡牌视图、伤害/格挡计算、条件判定、意图描述），供引擎与策略共用。
- `engine.js`：纯函数引擎。`createBattle(setup, seed)`、`applyAction(state, action) → { ok, state, events, error? }`、`legalActions(state)`、`replayBattle(setup, seed, actions)`、`seedFor(combatId)`。结局为 `victory / defeat / escape`；操控角色倒下即 `defeat`。人物技能动作 `{ type: 'hero-skill', targetId? }`：每回合一次、耗 `heroSkillCost`（2）能量，目标规则与出牌相同（只对需要敌方目标的效果展开敌方 targetId，`ally / all-allies` 自动结算）；发出 `hero-skill` 事件；setup 无 `heroSkill` 时不产生该动作，旧记录照常重放。规则 v4（`COMBAT_RULES.version = 4`，`COMPATIBLE_RULES_VERSIONS = [3, 4]`：v3 进行中战斗与记录照常重放；战局 `rulesVersion` 取 setup 的值，缺省为当前版本）新增弃牌、弃全手再抽、复制、生成临时牌（`TOKEN_CARDS`，每单位每回合上限 `tempCardsPerTurn`）、重复上一张、下一张多结算、本场成长、减费、限时触发 BUFF，出牌 / 被弃 / 消耗 / 击杀 / 洗牌 / 失去生命 / 获得格挡触发与对应条件，卡牌关键字 `innate / ethereal / unplayable / retain` 与 `onDiscard`，以及 `choose` 动作与 `state.pending` 待选阶段（界面未接入前生成路径不产出写 `choose` 的卡牌）；新事件 `discard / exhaust / card-created / repeat / replay / replay-next / grow / cost-mod / buff / buff-trigger / choose-start / choose`，战报、成就与命中演出只处理已知事件。规则 v3（当时 `COMBAT_RULES.version = 3`，v2 进行中战斗按 `rules-version-mismatch` 作废）新增效果原语 `damage-from-block`、`self-damage`、`double`（poison/block/strength）、`next-turn`（draw/energy）、`each-turn`（能力牌登记、每回合开始触发，不可嵌套）、`hand-cost`（本回合手牌费用修正、最低 0、X 费不变、回合结束清除），伤害可选 `strengthScale`，新状态 `intangible`（受伤降为 1，本单位下次回合开始衰减）、`no-draw`（本回合禁抽）、`endure`（首次致死保留 1 生命并获 `endureBlock` 格挡后移除）；`damage-from-block` 在技能伤害上限校验中按超限处理。觉醒动作 `{ type: 'awaken' }`：仅 setup 带合法 `awaken` 时可用，每场 1 次、不耗能量，效果取 `COMBAT_RULES.awakenEffects[type]`（`heal-pct`、`other-allies` 与 `next-turn` 的 status 增益只供觉醒内部使用，不进卡牌 schema），发出 `awaken` 事件；非法 `setup.awaken` 拒绝建局（`invalid-awaken`）。
  - v4 第二批机制（setup 不带新字段时结算不变）：新状态 `artifact`（人工制品：承受方被施加减益 `weak / vulnerable / poison / no-draw / frail` 时抵消并减 1 层，发 `artifact` 事件；净化不移除）、`frail`（脆弱：承受方获得的格挡在出手方敏捷加成后 ×0.75 向下取整，本单位回合结束减 1 层，可被净化）；被动触发 `foe-card-played`（对方出牌：出牌结算完后对侧存活单位的被动按行动顺序接收，主目标为出牌者，可限 `cardType`；限时 BUFF 不接收）；状态牌 `status-daze`（眩晕：不能打出、虚无）、`status-wound`（伤口：不能打出）。卡组单位的 `create` 照常生成进自己牌堆；技能单位（敌人、队友）的 `create` 只接受状态牌，塞进对方卡组单位的牌堆（技能指定目标 → 对方操控角色 → 对方第一名存活卡组单位），计入承受方本回合临时牌上限。估值：人工制品 6、脆弱 1.5，往自己牌堆生成状态牌每张 -3。
  - 场上 / 场外（P8b）：开战标签敌方合计上限 `COMBAT_RULES.maxEnemies`（50，与 `COMBAT_TAG_LIMITS.maxEnemies` 一致），场上同时最多 `maxEnemiesOnField`（5）。`setup.reserve` 可选：场外敌人 ID 队列，须为 setup 内不重复的敌人 ID、少于敌人总数，且场上敌人不超过 5，否则 `invalid-reserve` / `too-many-enemies`。场外敌人只进 `state.units`，不进 `state.order`（不行动、不可选为目标、不受群体效果、不公示意图）；场上敌人倒下时 `reinforce` 让场外队首接替它在 `order` 中的位置，发 `reinforce` 事件（`{ unitId, replaced }`），重新计时（下一轮才行动）、公示意图并触发自己的 `battle-start` 被动；`state.reserve` 用尽后删除。全部敌人倒下才判胜，撤退规则不变。`session.js` 的 `buildSetup(..., { combatId })` 在敌人超过 5 个时排位：首领先排、其余各按 `reserve:${combatId}` 种子排序，前 5 个上场，其余按序进场外（首领排不下时在场外队首），同一场重开结果不变；不超过 5 个时不写 `reserve`，setup 形状与旧版一致。EXP（`tiers`）、奖励（`start.enemies`）与战报（遍历 `state.units`）都按全部敌人计。场外剩余数的界面显示随 P9 预览确认。

- `policy.js`：确定性托管。`chooseAllyPlay`（预计受伤大于格挡先防御 → 可击杀时取最低费击杀 → 前两回合打能力牌 → 按伤害/费用攻击最弱敌人；v4 战斗（`state.rulesVersion >= 4`）没有伤害牌时按 `estimateEffectsValue` / 费用挑牌，此刻会落空的「重复上一张」「下一张多结算」不计价，没有值得打的牌就结束回合；v3 记录（含在 v4 引擎上重放）仍回退到手牌第一张，重放结果不变）；`pickCards`（自动选牌：弃牌先弃估值最低的，不能打出与带被弃时效果的优先；复制与减费取估值最高的；同值按手牌顺序）；`chooseSkillIntent`（按权重与冷却抽取，同一技能不连续使用三次；带 `ultimate:true` 的绝招冷却结束即优先，随机数照常消耗，重放确定）。
- `enemy-loadout.js`：敌人参战配置，开战时由 `session.js` 的 `enemyUnits` 调用，只写进 setup、不改档案、不发请求。`enemyAffixes(profile, difficulty)`：常驻效果数取 `COMBAT_RULES.difficulty[难度].affixes[档位]`（标准档普通 0、精英 1、首领 2），按 `affix:档案ID:难度` 种子给 `ENEMY_AFFIXES` 排序，首个取削弱我方的（`debuff`），其余按种子顺序；被动 ID 为 `af-键`、带 `source: 'affix'`（头像详情归入「常驻效果」，不参与结算）。`enemyFillSkills(profile, level, difficulty)`：模板敌人（`generated:false`）补到 `skillTarget(等级, 档位)`（`rules.js`：max(3, ⌈等级/3⌉)，精英 +1、首领 +2，上限 `SKILL_COUNT_MAX` = 10），再对所有敌人追加难度表 `extraSkills`；按 `fill:档案ID` 种子从 `SKILL_TEMPLATES` 的登记子集依次取（难度只追加、前面的不变），跳过同名，ID 为 `档案ID-f序号`，伤害按档位封顶。没有补充时 setup 沿用档案原数组。敌人档案 `skills` 放宽为 2–10，旧档仍合法。

- 鞭尸与超杀（`setup.overkill: true`，`session.js` 新开战斗写入；旧 setup 不带时规则与重放不变，非布尔值拒绝建局 `invalid-setup`）：己方出牌阶段打空最后一名敌人不立即判胜，操控角色可继续出牌；需要敌方目标的牌可选倒下的敌人（`isWhipping(state, unit)`），打在倒下敌人身上只发 `damage` 事件（`hpLoss:0`、`blocked:0`、`overkill:true`，带段号），不掉血、不触发荆棘与受击被动；仍有存活敌人时全体 / 随机攻击只打存活的，全灭后改打倒下的。敌人全灭时不能撤退（`escape-unavailable`），`end-turn` 直接判胜（只发 `battle-end`）。`report.js` 的 `collectTurns` 跳过 overkill 伤害，只有鞭尸命中的出手不写进战报。
- `feats.js`：`combatFeats(events, state)` 只读推导本场成就，不写存档、不进战报。`honor-kill`：胜利时最后倒下的敌人由操控角色的攻击击倒，且这一击扣除格挡后的伤害恰等于其剩余生命；`overkill`：全灭后操控角色的攻击打中倒下的敌人至少 `COMBAT_OVERKILL_HITS`（5）段（按动作序号 + 段号去重），带 `hits`。
- 全队覆灭（`setup.wipe: true`，`session.js` 新开战斗写入；旧 setup 不带时规则与重放不变，非布尔值拒绝建局 `invalid-setup`）：操控角色倒下不立即判负，我方全员倒下才判负（`checkOutcome`）。操控角色在出牌阶段（自伤、荆棘）或回合开始（中毒）倒下时，`continueWithoutHero` 清掉待选、先按自动阶段判一次胜负（overkill 战斗打空最后一名敌人的同时倒下直接判胜），再交给时间轴：队友与敌人一直自动行动到分出胜负，不再进入出牌阶段；双方都打不动时步数上限为 `MAX_TIMELINE_STEPS × WIPE_STEP_FACTOR`，到上限判负。`report.js` 只在 wipe 战斗判负且我方无人站着时写「终局：我方全员倒下，全队覆灭。」，僵持判负时队友仍站着，照常写落败。
- 持续伤势（v4，助手 10-29）：日志类型 `wound`（`{ hp, maxHp, down, reportId }`，不来自标签，锚定战报用户楼，`reportId` 须与楼里的战报一致，否则 `wound-report-invalid`）与 `heal`（`{ amount, mode: flat | percent, scale, reason }`，来自正文 `[igs-combat:heal|角色|恢复量|原因]`，不设每楼上限；`scale` 为扫描时难度表 `healScale` 的百分比快照，噩梦 50，之后改难度不影响；战报楼里的 heal 只记诊断 `combat-heal-tag-in-report`）。归并：`wound` 覆盖为最近一场的战后生命（满血且没倒下时清空，倒下记 0）；`heal` 只在有伤势时生效，按点数或记录上限的百分比乘 `scale` 恢复（至少 1 点，封顶，回满清空，回血后不再算倒下）。`characterView().wound` 为 `{ hp, maxHp, down }` 或 `null`，旧存档为 `null`（满血）。会话：出结果时把我方单位的战后生命随战报留档（`wounds`，重发沿用），战报楼落楼后写 `wound`（胜、败、撤退都写，条目 ID 确定、幂等）；`buildLobby` 把倒下的队友列进 `downed`、不进 `allies`（主角照常参战）；`buildSetup` 在难度生命上限之后按损失量算开战 `hp`（倒下的主角为 1，没有伤势时不写 `hp`，setup 形状不变）；`lobbyVitals` 写进会话 `lobby.vitals` 供战前显示，`vitalsOf` 供人物状态显示。`createCombatLedger({ difficulty })` 由 `core/combat-services.js` 注入当前难度，未注入按标准档。



- 行动顺序（规则版本 2）：行动值时间轴。每个单位行动间隔为 `1000000 / speed`，每步取剩余行动值最小者出手（相同时先计时者先动），全员扣除该段后出手者重新计时；操控角色轮到时 `phase = 'player'` 并发 `turn-start`（`side:'ally'`、`unitId`），`s.turn` 只在操控角色每次轮到时加一；结束回合后其余单位依次自动行动，每次出手前发 `act` 事件（`unitId, side`），快的单位可在操控角色下一回合前多次出手。格挡清零、中毒 / 再生、回能、抽牌、`turn-start` 被动在单位自己行动前结算（`startUnit`），`turn-end` 被动、弃牌、易伤 / 虚弱衰减在其行动后结算（`endUnit`）。开局操控角色先出牌。只读 `upcomingActors(state, count)` 推演接下来的出手者（不改状态、不耗随机数），供面板行动顺序槽。速度来源：`rules.js` 的 `combatSpeedFor({ archetype, tier, id })` 按职业原型 / 敌人档位基准 ± `speedJitter`（按 ID 散列，确定性），生成组装时写入档案 `base.speed`（schema 可选，范围 40–200）；旧档案缺速度时 `session.js` 按同一规则回落，不改写旧档案。`COMBAT_RULES.version` 由 1 升到 2，旧版本进行中战斗恢复时判 `combat-rules-version-mismatch`。

- `ledger.js`：成长账本。`createCombatLedger({ tables, chat, userName, sourceFilter, now })` → `read / effectiveState / append / scan / saveDeck / claimReward`；只读归并两张战斗表，按锚点（`messageId + swipeId + tagHash + occurrence`，不含 chatId）判定条目是否生效，读取失败返回 `ok:false`，不当作空账本；`claimReward` 只在等级已达到且未领取时写入；写入只经注入的 `tables`。`effectiveState()` 另返回 `growth`（已生效的 exp / learn / upgrade / class 条目，带接手角色、锚点与生效前后等级），供成长演出只读。同名时卡组档案优先：技能档案让位但保留（诊断 `combat-profile-superseded`），其 EXP 在归并时并入卡组档案，不改表；让位档案的其他条目只记诊断 `combat-superseded-entry-skipped`。
- `card-templates.js`：模板库。卡牌模板 `CARD_TEMPLATES` 固定效果形状（含 v2 复合 / 缝合模板，每张最多 3 个分量，可带条件追加与消耗），`solveCardTemplate(key, cost, rarity)` 在 `rarityWindow` 校验窗口内向该稀有度的求解中心整数搜索数值，并生成同形状、不减值、不超 `upgradeAllowance` 的升级版，结果经 `evaluateCardBudget` 复核，无解返回 `null`；`nearestTemplateCost` 取最近的有解费用（只在模板可用费用 `templateCosts(key)` 里找；X 费在要求 X 时最先、否则最后）；`fixedTemplateCost(key, cost)` 供职业卡固定位置使用：模板可用该费用时照用，可用 X 费的模板放在 1–3 费位置时改为 X 费，否则原样返回、由调用方拒收。v4 模板可带 `flags`（`innate / ethereal / unplayable`）、`onDiscard`、`costs`（限定费用，可含 `'X'`）与 `hero:false`；求解结果带出关键字与被弃时效果，估值与 `evaluateCardBudget` 同口径。`heroSkillFromTemplate` 排除带关键字、被弃时效果、限定费用且不含 `heroSkillCost`、或带本牌专属效果（复制本牌、成长、本牌减费、同名连出条件）的模板。写 `choose` 的模板在选牌界面接入前不开放。被动 `PASSIVE_TEMPLATES` 数值固定；技能 `SKILL_TEMPLATES` 按伤害封顶折算；`ultimateSkill(cap, { id, cooldown })` 是强度档绝招，不在目录里。`templateCatalogText()` 给提示词列出模板键与说明、0 费可用模板与按职业原型的推荐模板，不含数值。
- `generation-assembly.js`：紧凑回复 → 完整档案。`assembleClass / assembleDeck / assembleSkillCharacter / assembleEnemy / assembleGrowth` 只接受模板键、名称与少量数值。新职业池恰好 11 张，`classRaritiesFor(owner)` 按角色种子分配 common 7、uncommon 4，与费用使用不同种子域；重试不变，模型不选稀有度。职业卡、个人卡、专属卡的费用取请求里的 `input.costSlots` / 固定 `CARD_COST_SLOTS.signature`（由 `costSlotsFor(kind, 角色ID)` 确定性挑选；请求槽位非法时用固定槽位），回复费用不符只记 `combat-cost-slotted`。职业卡在指定费用与稀有度下无解返回 `template-unsolvable`（带 cost / rarity），交生成纠错，不移动费用槽（只用 `fixedTemplateCost`：X 费模板放在 1–3 费位置改为 X 费，其余限定费用模板费用不符即无解）；`buildCard` 把模板解出的关键字（`innate / ethereal / unplayable`）与 `onDiscard` 带进卡牌，旧模板的卡牌形状不变；其他卡保留最近有解费用规则，`skill-to-card` 仍取回复费用。ID（`档案ID-c1 / -m1/ -g1 / -s1 / -p1`）、效果、升级版、首领半血阶段与起始卡组由程序生成。`buildStarterDeck(classPool, personalPool, seed)` 保持 3/3/10/4，职业仅抽 common / uncommon、单卡 ≤3，个人卡单卡 ≤2；沿用旧职业池时也过滤 rare / epic / mythic。已存档的起始卡组和稀有度不重算、不自动写回；schema 卡池白名单仍接受旧 rare，并登记 epic / mythic。`profile-skill` 可选 `tier`。结构错误按紧凑回复字段路径返回 `errors`；数值越界夹回并记 `combat-value-clamped`。
- `generation.js`：副 LLM 生成。`generateEntities(entities, { request, llm, signal })` → `{ ok, accepted, rejected, diagnostics, blocked }`；回复先经组装，再走 `normalizeProfile / normalizeCard / normalizeSkill / validateStarterDeck`，不合格实体最多定向修正 2 轮，已通过实体不再提交；修正耗尽时敌人回落模板敌人、主角 `blocked`、队友不参战，补技能（`skill-fill`）没有回落；取消返回 `request-stale`。回复无法解析时细分 `combat-reply-empty / combat-reply-truncated / combat-reply-not-json`，不回显回复正文。只构造请求与校验，不落账。`skillFillEntity({ profile, count, version, existing?, createdAt? })` 给已有档案（技能角色或副 LLM 生成的敌人）补恰好 `count` 个技能：回复 `{ skills: [[名, 技能模板键], …] }`，`assembleSkillFill` 追加在档案技能末尾（ID 为 `档案ID-k序号`，接着现有技能数），名称与档案技能、`input.existing`（技能角色含习得的技能）或同批重复时拒收（`skill-name-exists`）；通过结果带 `version` 与沿用的 `createdAt`，`generationWrites` 据此写同 ID 的新版本档案。技能角色队友另传 `level`（属性视图等级，D10）：伤害折算上限按 `allyFillCap`（Lv1–5 为 `allySkillDamageCap` 18、Lv6–10 为 21、Lv11 起为 25）写在 `fixed.cap`（模型不可见），Lv6 起 `input.templates` 只给 `COMPOSITE_SKILL_KEYS` 的 14 个复合技能、选其他键拒收 `invalid-template`；Lv1–5 与未传等级时请求形状与旧路径一致，敌人不受影响。技能角色档案的技能伤害校验上限为 `ALLY_SKILL_CAP_MAX`（25）；新档案、剧情习得 / 精进的技能与绝招仍按 `allySkillDamageCap`。`withCharacterLore(entities, read)` 用调用方注入的读取器给 `profile-deck / profile-skill / profile-init / trait / skill-fill` 附 `input.lore`（角色设定参考），只在读到非空内容时加字段；未注入、读取失败或为空时实体原样返回。
- `generation-retry.js`：`generateWithRetry(entities, { retryDelays, onRetry, ...generateEntities 选项 })` 在 `generateEntities` 外做有界自动重试（默认 `COMBAT_GENERATION_RETRY_DELAYS` = 2s / 6s，最多重发 2 次）。只重发上游明确拒绝、可安全补发的请求（`requestFailure.reason === 'secondary-llm-http-failed'` 且 HTTP 408 / 425 / 429 / 500 / 502 / 503）；取消与迟到、配置不完整、副 LLM 不可用、回复格式修正耗尽、发送状态未知的传输失败与 504 都不自动重发。等待中取消返回 `request-stale`；发生重试时结果附 `retries`，未重试时结果与 `generateEntities` 一致。`generateEntities` 在请求本身失败时附 `requestFailure: { reason, status? }`（不含上游正文）。`session.prepare` 经它生成缺失档案；注入 `awaitProtagonist` 时先等在途的主角卡组预生成结束再读账本，等待后开战楼变化或取消返回 `request-stale`。
- `generation.js` 的 `withStoryContext(context, read, { names, signal, full, persona })`：用调用方注入的读取器给生成请求的 `context` 附 `story`（最近剧情节选）、`worldInfo`（按剧情触发的世界书条目）与 `userPersona`（仅 `persona` 为 true 时），只在读到非空内容时加字段；`full` / `persona` 只在为 true 时传给读取器；未注入、读取失败或为空时返回原 `context`，请求形状与旧版一致。`session.prepare`（按主角、队友、敌人名触发；本批含 `profile-deck` 时传 `full`，同批敌人、奖励与补技能共用这份完整 context）、`combat-services` 的卡组生成（`generateDeck` / `regenerateDeck` 传 `full`，队友卡组另传 `persona`）与 `retryGrowth` 三处接入。


- `report.js`：战报构造。`buildCombatReport(...)` → `{ ok, text, result, reportId, exp }`；只写技能名与相对伤势，胜利附 EXP 标签，失败与撤退不附。
- `session.js`：战斗会话。`createCombatSession(deps)` → `prepare / start / act / finish / retrySend / retryReward / skip / resume / reset / subscribe / state`；断点续战只存 `{ combatId, anchor, seed, setup, actions }`，核对锚点与规则版本后重放；先写待回传再发送，失败不自动重发；已回传的战斗只能回顾。可选 `chatRecord`（`read(anchor, combatId) / write(anchor, combatId, patch)`，bootstrap 注入 `host/combat-chat-record.js`）把准备与结果留档在开战楼聊天记录：首次准备到战前写 `prepared`；出结果当即生成战报并写 `result`（`reportId / result / text / outcome / turn / at`，有道具用量时附 `used / character`），不等发送。`prepare` 与 `resume` 读到 `result` 时只能重发同一份战报（`send-failed`），不重放、不重打，删战报楼或换设备后同样；读到 `prepared` 时只补缺失的主角档案，不再为队友、敌人请求生成；读取失败或格式不对时 fail-closed 阻断（`combat-record-read-failed / combat-record-corrupt`）。写前核对锚点（否则 `combat-record-stale`）；写失败不阻断开战与发送，会话快照带 `recordError`，结算与重发前补写结果。同一场并发 `prepare` 共用一次请求，结束后经 `subscribe(fn)` 通知订阅者。重发同一份战报时 `consume` 用战报自带的用量，道具不因删战报楼而退回。宿主能力全部注入（含可选 `readLore`：`prepare` 生成缺失档案前经 `withCharacterLore` 附角色设定）。补技能（计划 5.4）：首次准备时，技能少于 `skillTarget(等级, 档位)` 的技能角色队友（按属性视图等级）与副 LLM 生成的敌人（`generated` 不为 false；按相对档等级，没有时按我方平均等级）各一个 `skill-fill` 实体，与缺档案实体同批请求；本次新生成的档案仍不足时只含补技能再请求一轮；模板敌人由 `enemy-loadout.js` 按种子补、不发请求；已准备过的场次不请求。通过后写同 ID 的新版本档案（`profileMeta` 版本 + 1，沿用登记时间）并读回；拒收、请求不可用或写失败都不阻断开战，该角色带现有技能参战，会话快照带 `fillDiagnostics: [{ code, owner | owners, reason? }]`。`ledger.effectiveState()` 返回 `profileMeta`（档案 ID → `{ version, createdAt }`）。技能角色进 setup 时按 `allyTierOf(profile)` 放大生命与技能数值（倍率为 1 时沿用原对象），ace / legend 追加 `档案ID-u1` 绝招。开战楼的 `start.awaken` 只在点名角色是本场被操控者时写入 `setup.awaken = { type, line }`（主角可用「我」/主角名/别名）；点名他人或换人操控时不写入，`start()` 返回 `awakenDropped: 'combat-awaken-not-controlled'`；无觉醒时 setup 形状与旧版一致。已装备的装备被动随角色并入单位 `passives`；被操控者持有的道具（余量 > 0，最多 12 种）写入 `setup.items = [{ itemId, name, count, effects }]`，没有道具时不写字段。战报落楼后 `deliver` 按「带入数量 − 结束剩余」写 `consume` 条目（锚定战报用户楼、`tagHash = CONSUME_TAG_HASH`、ID 确定，重复落账幂等），结果放在返回值 `consume`。引擎道具动作 `{ type: 'item', itemId, targetId? }`：目标规则与出牌相同（`target:'ally'` 的回复 / 格挡 / 净化可指定一名存活的己方单位，不指定时按生命比例最低者；伤害与减益对敌方）；模板道具 `potion` / `barrier` / `purify` 为 `ally`，`session.js` 建局时经 `itemEffectsForBattle` 把旧道具 self 的回复 / 格挡 / 净化换成 ally（只影响新开的战斗，已存 setup 与重放不变），能量与抽牌只作用于使用者；道具模板另有单体伤害 `dagger`、单体减益 `poison-dart` / `weaken-powder` / `sunder` / `frail-dust`（选一名敌人）、群体减益 `toxic-cloud` / `smoke`、攻击增幅 `war-tonic`（选一名己方）/ `war-drum`（全体己方），数值见计划 3.8；不耗能量，操控角色每个己方回合限 1 次（`item-used`），用完 `item-empty`，未带入 `item-unavailable`；非法 `setup.items` 拒绝建局（`invalid-items`）。构筑面板换装经 `ledger.setGear(characterId, gearId, equip)` 写 equip / unequip（锚定最新楼层、`tagHash = GEAR_TAG_HASH`、不核对标签），同楼排在全部标签条目之后；只能装上背包里的、卸下已装备的（否则 `combat-gear-missing`）。面板 equip 只把已拥有的装备放进槽位，不按载荷改写拥有记录：来源标签楼换 swipe 或删楼后，面板条目记 `combat-gear-missing`，不复活装备。
- 专属卡成长：`generation.js` 的 `growthEntity` 遇到与档案专属卡同名（NFKC、去空白、小写）的 learn / upgrade 时直接给出条目（未持有 → learn 解锁，已持有 → upgrade），不请求副 LLM；副 LLM 的升级候选排除专属卡。`ledger.js` 只认档案登记过的专属卡（否则 `combat-signature-unknown`），专属卡精进只标升级形态、不替换卡面，奖励不得选专属卡（`combat-reward-signature`）。

## 约束

- schema 校验只拒收不修正：未知字段、越界数值、超预算、未知效果一律返回 `{ ok: false, errors: [{ path, reason, detail? }] }`。可选字段只在缺省时取默认值。
- 组装层只对模型给出的数值（费用、HP、每级 HP、列表长度、名称长度）夹回范围并记 `combat-value-clamped`；模板键、原型、必填被动等结构错误仍拒收并定向修正。组装产物必须再过 schema，组装不得绕过校验。
- 副 LLM 不写效果原语：只从模板目录选键，效果由模板生成；旧档案（完整效果结构）照常按 schema 读取。
- 档案与日志带 schema 版本 `v`；不支持的版本拒收，不就地升级。
- 同一职业以已登记的 `class` 档案为准；`deck-character` 通过 `classRef` 引用职业，只持有个人部分。
- 起始卡组固定为 20 张：基础攻击 3、基础防御 3、职业卡 10、个人卡 4，且同名卡不超过 3 张。
- 装备与道具（v2 阶段 3）：账本类型 `equip`（`{ gearId, name, slot, passive, description }`，带稀有度的装备另有 `rarity`（五档池稀有度）与 `bonus: { ability, amount 1–5 }`、可以没有 `passive`；不带 `rarity` 的旧条目必须带被动；同部位后装备顶替、旧装备留在背包）、`unequip`（`{ gearId }`，扫描时直接落账，未持有记 `combat-gear-missing`）、`item`（`{ itemId, name, count 1–3, effects, description }`，同名累加）、`consume`（`{ itemId, count, reportId }`，锚定战报用户楼、`tagHash = CONSUME_TAG_HASH`、不核对标签，超余量整条拒收 `combat-item-insufficient`）；`gearIdFor` / `itemIdFor` 由名称（NFKC、去空白、小写）确定性推导。角色视图带 `gear: { slots, bag }` 与 `items`（只列余量 > 0）；装着的装备 `bonus` 并入属性视图的调整项（与其他调整同受属性上限约束），检定、卡牌属性换算与开战快照都读这里，卸下即不计入。equip / item 标签进待生成队列，`growthEntity` 给出 `equip-to-passive` / `item-to-consumable` 实体（模型只回 `{ template }`：被动模板键 / 道具模板键 `ITEM_TEMPLATES`），名称、部位、数量与 ID 由程序给定，组装后过 `normalizeLedgerEntry` 直接成为 equip / item 条目；宝物被动经 `gearPassiveFromTemplate` 按 rare / common 求解中心之比向上取整加强。道具模板含新效果 `cleanse`（移除承受方虚弱、易伤、中毒、禁抽）。正文获得物带稀有度（D6–D9，标签末栏）时：`input.rarity` 只在标签写了稀有度时出现，候选模板 `input.templates` 由 `acquire-candidates.js` 的 `templateCandidates` 筛出 3–5 个（按名称与简述和模板说明的字面重合排序，不足按种子补足），模型只能从候选里选；装备回 `{ ability, template? }`，加成按 `GEAR_BONUS_BY_RARITY`（+1…+5），被动按 `gearHasPassive`（装备 ID 种子，普通 / 罕见 0、稀有 30%、史诗 60%、神话 100%）抽定，抽中时候选为按该稀有度加强后不超 `allySkillDamageCap` 的被动、强度取 `passiveAtRarity`，宝物不再另加强；道具数值按 `itemAtRarity` 以该稀有度与 common 求解中心之比放大（层数 ≤10、治疗 ≤60、能量 ≤3、抽牌 ≤5、其他 ≤99，说明数字同步）；卡组角色学会的卡牌取标签稀有度，候选为该稀有度下有解的卡牌模板并附 `input.templateVars`，模型可回 `values`，经 `cardFromValues` 按变量范围与费用 × 稀有度窗口校验（`values-length` / `values-out-of-range` / `values-out-of-window`），修正轮次用尽时去掉 `values` 改用程序求解并记 `combat-values-solved`。不带稀有度时请求、组装与载荷与旧路径一致；技能角色学技能不带稀有度。
- 成长日志除 `profile` 与 `revoke` 外必须带锚点 `{ messageId, swipeId, tagHash, occurrence }`；条目 ID 由 `ledgerEntryId` 确定性推导。

不与已装重复、被动伤害不超过队友技能上限；带 kind 的新条目装得下（`traitFits`：有空槽且主动不超 2 个）直接装上，否则成为 `pendingTrait`；没有 kind 的旧条目照旧只数抽到的特性，满 2 个才待定。固有人物技能与个人被动占槽：抽到的特性优先，固有特性按 active、passive 补剩余空位（主动不超上限），补不进的暂停、腾出位置或解锁新槽后自动回来。trait-pick 的 drop 为已装特性 ID（替换，新特性占它的位置）、保留着的固有特性 ID（记入 `innateDropped`，永久不再出现）或待定特性自己的 ID（放弃），被 drop 的永久消失、积分不退；待定的主动只能替换主动，替换不能让其他保留着的固有特性暂停、也不能让主动超过 2 个，否则拒收 `combat-trait-slot-cost-invalid` / `combat-points-insufficient`）；解锁后待定特性装得下就直接装上，随楼层回退。角色视图新增 `traits`、`pendingTrait`、`traitDraws`、`innateDropped`、`slotUnlocks`。会话：`deckUnit` 的被动追加装着的特性被动；`rewardFor` - 华而不实被动（P-e，助手反馈 3）：`card-templates.js` 的 `FLAIR_PASSIVE_TEMPLATES`（12 个 `flair-*`，基础效果都是 1 点或 1 层）与 `PASSIVE_TEMPLATES` 合并为 `GEAR_PASSIVE_TEMPLATES`，`passiveFromTemplate` / `passiveAtRarity` / `gearPassiveFromTemplate` 按合并表取值。组装层只让人物特性（`assembleTrait`）、装备被动（`assembleGear`）与胜利奖励的装备槽（`assembleReward` 的 gear 槽）按合并表校验模板键；职业、个人、技能角色与敌人被动（`passiveOf`）仍只认 `PASSIVE_TEMPLATES`，道具槽只认 `ITEM_TEMPLATES`，越界记 `invalid-template` 并定向修正。提示词模板目录另列华而不实被动表并写明可用范围。「在特性与装备奖励中提高权重」的机制与比例待助手确认，确认前不加权。



- 胜利翻牌（v3 第 12b 步）：`flip.js` 为纯函数，不读写存储。位置按 `combatId` 与套别的种子打乱（`flipOrder`），重开一致；透视（`offer.reveal`）先亮出 1–2 张，只亮不算翻（`revealedOf`）；4 槽（再翻）时翻两张后 `chooseCard` 二选一，否则 `flipCard` 翻一张即选定；`rerollPick` 花 `REROLL_COST` 换上备用套重新翻，每场一次，旧 offer 没有备用套或领取者不是主角时 `combat-reroll-unavailable`、余额不足 `combat-points-insufficient`、已换过 `combat-reroll-used`；`flipView` 只给已翻开、已亮出的牌带槽位内容，选定后全部翻开。会话在胜利结束（`ended` / `send-failed`）时经 `loadFlip()` 读本场 offer 建 `session.flip`：`loading`、`none`（没有 offer，照发不带战利品）、`error`（账本读不到或进度损坏 `combat-flip-corrupt`，不能发）、`ready`；`act` 出胜负、`prepare` 与 `resume` 落到已出结果时自动读取。`flip(position) / choose(position) / reroll()` 的进度 `{ set, flipped, choice }` 先存会话存档 `record.flip`，再写开战楼聊天记录该场的 `flip` 字段（不改 `result`）；没有会话存档时写进聊天记录才推进（否则 `combat-flip-save-failed`）。几份进度不一致时取更靠后的，换设备后同样不能重翻。`finish` 与 `retrySend` 在有 offer 时必须已选定（`combat-flip-required`），经 `attachLoot` 附战利品后写待回传再发送；战利品附进战报后翻牌锁定（`combat-flip-locked`）。会话只按当时余额放行重抽，实际扣分与拒收由账本按真实余额裁决。
- 翻牌界面（v3 第 12c 步）：战斗面板只读 `session.state().flip`，经 `session.flip(position)` / `choose(position)` / `reroll()` 操作；面板不另读积分，重新抽取的消耗与是否可用取 `flip.reroll`，选定战利品后才出。界面置灰只是提示，发送门禁仍由会话层 `combat-flip-required` 负责。


- 引擎不就地修改入参：`applyAction` 先校验，非法动作返回原 `state`、空事件和 `{ reason, detail? }`；合法动作在副本上结算。断点续战只保存 `setup`、`seed` 与动作序列，由 `replayBattle` 重建，不持久化引擎快照。
- 开局配置 fail-closed：规则版本不符、单位 ID 非法或保留名、卡组引用未知卡、操控角色不是友方卡组角色、种子非法均拒绝建局。

## 禁止

- 禁止在 combat 内直接访问 DOM、酒馆全局对象或 `AutoCardUpdaterAPI`。
- 禁止使用 `Math.random` 或当前时间影响战斗结算；随机性必须来自传入的种子。
