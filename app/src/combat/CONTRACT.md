# combat 模块契约

## 职责

- 职业显示：角色属性视图的 `className` 优先取当前已重放职业名，没有职业档案时回落属性初始化名称。转职不改写 init，不重置六维、定位或偏好；既有转职保留旧牌、仅把新职业卡加入目录的规则不变。

- 战斗扩展的领域逻辑：规则常量、数据契约校验、战斗引擎、托管策略、成长日志归并、副 LLM 生成校验、战报构造与战斗会话编排。
- 设计与计划：`.limcode/design/combat-expansion.md`、`.limcode/plans/combat-expansion.plan.md`；实施核实结论见 `docs/COMBAT_EXPANSION.md`。

## 依赖方向

- combat 只依赖 scene 的解析结果与经参数注入的 data/shujuku 适配器；不导入 visual、host、core。
- visual 与 core 依赖 combat；宿主发送、副 LLM、存储均由调用方传入。
- `challenge-*` 只依赖 combat 内部、scene 的标签解析常量与数值侧传入的参数，不导入 visual、host、core；数值结算放在 `scene/stats/stat-challenge.js`，由数值侧自己读战报，combat 不读数值存档。

## 文件

- `rules.js`：`COMBAT_RULES`（每回合能量 3、抽牌 5、卡组 20–30 张、敌人档位、职业原型）、基础卡 `BASIC_CARDS`、卡牌价值预算 `evaluateCardBudget`、经验曲线 `levelFromExp/expProgress`。`cardCopyLimit(rarity)`：basic / common / uncommon / rare / epic / personal 同名上限 3，mythic / signature 为 1，未知档返回 0；`validateDeck(deck, owned, catalog)` 必须由目录提供稀有度，缺卡返回 `unknown-card`、未知档返回 `invalid-rarity`，不放行。日志回放、自动入组、构筑按钮及奖励候选共用上限。稀有度窗口 `rarityWindows`（每档 `min / max / target` × 费用预算；`rarityWindow(cost, rarity)` 返回校验窗口与求解中心）：旧档位窗口保留；epic 为 0.9–1.5、目标 1.3，mythic 为 1.2–1.65、目标 1.45，signature 为 1.2–1.6；升级上限为窗口上限 × 1.3。未登记稀有度拒收，不回落 common。另有 `signatureLimit 2`、`signatureCopyLimit 1`、技能角色强度档 `allyTiers`（support / peer / ace / legend 的生命、技能倍率与绝招冷却，暂定值）与 `defaultAllyTier 'peer'`。
  - 敌人开战数值 `scaleEnemyStats(profile, level, difficulty, { gap })`：生命 = 档案生命 ×（1 + `tierScalePerLevel` 0.05 ×（等级 − 1））× 难度 hp × 档位 `hpScale` ×（1 + `levelGap.hp` 0.02 × 等级差）；伤害倍率 = 难度 damage × 档位 `damageScale` ×（1 + `levelGap.damage` 0.04 × 等级差），取两位小数、上限 5。等级差为敌人推导等级高出我方平均等级的部分，`enemyUnits` 传入，没有属性视图时为 0。档位校准倍率按 `scripts/combat-balance.mjs` 的托管模拟取值（普通 1.3 / 2.7、精英 1.15 / 1.75、首领 0.68 / 1）；档案生命区间与技能伤害上限仍按 `hp / damageCap` 校验，已入库档案与旧战斗记录重放不受影响。
  - 多敌折算与生成敌人校准（v0.39.1）：`enemyUnits` 在 `scaleEnemyStats` 与六维换算之后，再把单只敌人的生命与伤害倍率乘以 `crowdScaleFor(敌人总数) × generatedScale[档位]`。`crowdScaleFor(n)` = max(`crowd.floor` 0.4, 1 /（1 + `crowd.perExtra` 0.43 ×（在场人数 − 1））)，在场人数按 `maxEnemiesOnField` 截断，预备队不计，1 只时为 1；`generatedScale` 只登记首领 0.9，且只作用于生成敌人（`generated` 不为 `false`），模板敌人不乘。乘积为 1 时 `maxHp` / `damageScale` 原样写入，生命取整且不小于 1，伤害倍率取两位小数、上限 5。只写进新建 setup，不改 `COMBAT_RULES.version`，旧战斗按已存数值重放。

- `schema.js`：效果原语、卡牌、技能、被动、档案（`class / deck-character / skill-character / enemy`）与成长日志条目的判别联合校验。`deck-character.heroSkill` 可选（人物技能，`{ id, name, effects, description? }`），效果按 `COMBAT_RULES.heroSkillCost` 费用的 `personal` 预算校验；旧档案没有该字段时由 `session.js` 按职业原型回落 `defaultHeroSkill`。`deck-character.signatureCards` 可选（0–2 张，只收 `signature` 稀有度，ID 不得与职业池 / 个人池 / 基础卡冲突，不得进入起始卡组 → `signature-in-starter`）；`skill-character.tier` 可选（`allyTiers` 的键）。两字段缺省时都不补字段。
- `random.js`：确定性哈希与伪随机数，用于战斗重放。
- `battle-state.js`：只读的战局查询与数值估算（存活单位、最弱目标、卡牌视图、伤害/格挡计算、条件判定、意图描述），供引擎与策略共用。
- `engine.js`：纯函数引擎。`createBattle(setup, seed)`、`applyAction(state, action) → { ok, state, events, error? }`、`legalActions(state)`、`replayBattle(setup, seed, actions)`、`seedFor(combatId)`。结局为 `victory / defeat / escape`；操控角色倒下即 `defeat`。人物技能动作 `{ type: 'hero-skill', targetId? }`：每回合一次、耗 `heroSkillCost`（2）能量，目标规则与出牌相同（只对需要敌方目标的效果展开敌方 targetId，`ally / all-allies` 自动结算）；发出 `hero-skill` 事件；setup 无 `heroSkill` 时不产生该动作，旧记录照常重放。规则 v4（当前 `COMBAT_RULES.version = 5`，`COMPATIBLE_RULES_VERSIONS = [3, 4, 5]`：v3、v4 进行中战斗与记录照常重放，v5 新机制只在 `state.rulesVersion >= 5` 时启用；战局 `rulesVersion` 取 setup 的值，缺省为当前版本）新增弃牌、弃全手再抽、复制、生成临时牌（`TOKEN_CARDS`，每单位每回合上限 `tempCardsPerTurn`）、重复上一张、下一张多结算、本场成长、减费、限时触发 BUFF，出牌 / 被弃 / 消耗 / 击杀 / 洗牌 / 失去生命 / 获得格挡触发与对应条件，卡牌关键字 `innate / ethereal / unplayable / retain` 与 `onDiscard`，以及 `choose` 动作与 `state.pending` 待选阶段（界面未接入前生成路径不产出写 `choose` 的卡牌）；新事件 `discard / exhaust / card-created / repeat / replay / replay-next / grow / cost-mod / buff / buff-trigger / choose-start / choose`，战报、成就与命中演出只处理已知事件。规则 v3（当时 `COMBAT_RULES.version = 3`，v2 进行中战斗按 `rules-version-mismatch` 作废）新增效果原语 `damage-from-block`、`self-damage`、`double`（poison/block/strength）、`next-turn`（draw/energy）、`each-turn`（能力牌登记、每回合开始触发，不可嵌套）、`hand-cost`（本回合手牌费用修正、最低 0、X 费不变、回合结束清除），伤害可选 `strengthScale`，新状态 `intangible`（受伤降为 1，本单位下次回合开始衰减）、`no-draw`（本回合禁抽）、`endure`（首次致死保留 1 生命并获 `endureBlock` 格挡后移除）；`damage-from-block` 在技能伤害上限校验中按超限处理。觉醒动作 `{ type: 'awaken' }`：仅 setup 带合法 `awaken` 时可用，每场 1 次、不耗能量，效果取 `COMBAT_RULES.awakenEffects[type]`（`heal-pct`、`other-allies` 与 `next-turn` 的 status 增益只供觉醒内部使用，不进卡牌 schema），发出 `awaken` 事件；非法 `setup.awaken` 拒绝建局（`invalid-awaken`）。
  - v4 第二批机制（setup 不带新字段时结算不变）：新状态 `artifact`（人工制品：承受方被施加减益 `weak / vulnerable / poison / no-draw / frail` 时抵消并减 1 层，发 `artifact` 事件；净化不移除）、`frail`（脆弱：承受方获得的格挡在出手方敏捷加成后 ×0.75 向下取整，本单位回合结束减 1 层，可被净化）；被动触发 `foe-card-played`（对方出牌：出牌结算完后对侧存活单位的被动按行动顺序接收，主目标为出牌者，可限 `cardType`；限时 BUFF 不接收）；状态牌 `status-daze`（眩晕：不能打出、虚无）、`status-wound`（伤口：不能打出）。卡组单位的 `create` 照常生成进自己牌堆；技能单位（敌人、队友）的 `create` 只接受状态牌，塞进对方卡组单位的牌堆（技能指定目标 → 对方操控角色 → 对方第一名存活卡组单位），计入承受方本回合临时牌上限。估值：人工制品 6、脆弱 1.5，往自己牌堆生成状态牌每张 -3。
  - 场上 / 场外（P8b）：开战标签敌方合计上限 `COMBAT_RULES.maxEnemies`（50，与 `COMBAT_TAG_LIMITS.maxEnemies` 一致），场上同时最多 `maxEnemiesOnField`（5）。`setup.reserve` 可选：场外敌人 ID 队列，须为 setup 内不重复的敌人 ID、少于敌人总数，且场上敌人不超过 5，否则 `invalid-reserve` / `too-many-enemies`。场外敌人只进 `state.units`，不进 `state.order`（不行动、不可选为目标、不受群体效果、不公示意图）；场上敌人倒下时 `reinforce` 让场外队首接替它在 `order` 中的位置，发 `reinforce` 事件（`{ unitId, replaced }`），重新计时（下一轮才行动）、公示意图并触发自己的 `battle-start` 被动；`state.reserve` 用尽后删除。全部敌人倒下才判胜，撤退规则不变。`session.js` 的 `buildSetup(..., { combatId })` 在敌人超过 5 个时排位：按首领 → 精英 → 普通排位、同档内按 `reserve:${combatId}` 种子排序，前 5 个上场，其余按同一顺序进场外（首领、精英排不下时在场外队首，先于普通怪补位）；面板在补位怪出手前先完成旧敌人退场与新敌人入场，同一场重开结果不变；不超过 5 个时不写 `reserve`，setup 形状与旧版一致。EXP（`tiers`）、奖励（`start.enemies`）与战报（遍历 `state.units`）都按全部敌人计。场外剩余数的界面显示随 P9 预览确认。

- 规则 v5 基础设施（P0；v3/v4 setup 在新引擎上逐步事件流与结局不变，已用新旧引擎对拍核对）：
  - `mechanics/registry.js`：机制注册表，不引用其他战斗模块。`registerMechanic({ key, family, archetypes, unitKinds, ops, statuses, hooks, modifiers, lossKinds, describe, report })` 先整体校验再写入，非法即抛 `mechanic-invalid:键:原因`；内置 27 个算子与 12 种状态由 `schema.js` 启动时 `reserveBuiltins` 登记为保留名。查询 `opHandler / opAllowedFor / statusDef / statusLabel / hooksAt / damageModifiers / isLossKind`，未登记返回 null 或空数组。
  - 接线：`validateEffect` 只把非内置且已登记的算子交给其 `validate`（附字段校验工具与 `nested`）；`effectsDamage` 计入其 `damage`；`effectValue` 取其 `value`；`applyEffect` 只在 `state.rulesVersion >= 5` 且单位类型被允许时调用其 `apply`。
  - 时机钩子（只在 v5 调用，嵌套不超过 `MAX_DEPTH`，胜负已定即停）：`turn-start-before`（可置 `clearBlock = false`）、`turn-start-after`、`turn-end-before`、`turn-end-after`、`play-before`（可改 `runs`，上限 20；可置 `exhaust = true` 让该牌打出后消耗）、`play-after`、`draw`、`create`、`exhaust`、`shuffle`、`debuff-applied`、`damage-before`（可改 `amount`）、`damage-after`、`hp-loss-before`（可改 `hpLoss`）、`hp-loss-after`、`defeated`（补位之前）、`block-gained`（`{ target, amount, source, shared? }`，在 `block` 事件之后、「获得格挡」总线之前；可追加格挡并改写 `amount` 为本次合计）、`attack-target`（`{ attacker, target }`，单体攻击 `target: 'enemy'` 每次选定存活目标后，可换成同阵营另一名存活单位；全体、随机目标不经过）。登记的减益受人工制品抵挡；登记为 `decay` 的状态在 v5 回合结束减 1。
  - 获得格挡统一走引擎 `gainBlock(ctx, target, amount, source, extra)`（`block`、`double: block` 与机制共用，经 `engineKit.gainBlock` 交给机制）：数值为 0 也发 `block` 事件，大于 0 才走钩子与总线，v3/v4 事件流不变；`extra` 同时写进事件与钩子。
  - 伤害管线：`computeDamage(attacker, target, amount, strengthScale, rulesVersion)` 在 `rulesVersion >= 5` 时于攻击力之后、虚弱之前执行 `outgoing-add`、`outgoing-mult`，易伤之后执行 `incoming-mult`；引擎结算与 `estimateDamage` 传入战局版本，面板牌面预览暂不传。失去生命类伤害（内置 `poison`、`self`，机制可登记）在 v5 不触发伤害前后钩子，`damage` 事件附 `loss: true`，其余字段不变。
  - 资源容器 `unit.res`：只在 v5 由机制经 `engineKit.resOf(ctx, unit)` 按需创建（v3/v4 返回 null），`cloneUnit` 整体深拷贝；`buildUnit` 不写，setup 暂不接受该字段。
  - 卡牌字段：`replay`（1–3，v5 打出时整张额外执行 N 次，只付一次费、只计一次出牌，发 `replay` 事件带 `keyword: true`）；`sly`（布尔，字段先行，结算未接入）。卡牌预算暂不计 `replay`，出模板前须补。
  - 职业白名单：`card-templates.js` 的 `TEMPLATE_FAMILIES`（每个卡牌模板恰好一个机制族，`general` 为通用族；`sanctum` 为净化、人工制品、无实体、保命，只给祈司；`rampart` 为守护壁垒 D01–D08，只给守护）、`ARCHETYPE_FAMILIES`、`templateFamily / templateAllowedFor / templatesFor`，加载时自检全覆盖、各职业含通用族、推荐模板与默认人物技能均在允许范围内。装配期：职业池（职业声明后）、升阶卡、人物技能只收本职业允许的模板，个人卡池最多 1 张其他职业族，专属卡不限，越界统一报 `invalid-template`。`GENERATION_SYSTEM` 原有行不变，末尾追加一行静态的各职业模板范围；职业已知的 `profile-deck` 与 `class-tier` 请求带 `input.allowedTemplates`。特性池（`trait-pool.js`）不分职业，主动技能模板只按 `TRAIT_SKILL_TEMPLATE_KEYS` 筛选，不受职业白名单约束。
  - 守护壁垒（规则 v5 P3，`mechanics/rampart.js`，状态经 `apply-status` 施加）：`barricade` 固守（格挡本场不清，模板限史诗以上）、`retain-block` 固守回合（每保住一次减 1）、`block-surge` 格挡倍增（本回合前 N 次获得格挡追加等量，事件带 `surge: true`，回合结束清掉）、`plated` 甲层（回合结束获得等于层数的格挡，受到未格挡的攻击伤害减 1 层）、`recoil` 反震（被格挡的攻击伤害反射给攻击者，伤害种类 `recoil`）、`bramble` 临时荆棘（每次受击反伤层数，种类 `thorns`）、`juggernaut` 坚壁反击（每次获得格挡对随机存活敌人造成层数伤害，消耗一次随机数）、`cover` 掩护（敌方指向队友的单体攻击改由带掩护者承受，按出手顺序取第一名，发 `cover` 事件）、`share-block` 共盾（获得格挡后其余存活队友获得一半向下取整，分出的格挡带 `shared: true` 不再分发）。`recoil`、`bramble`、`cover` 在自身下回合开始时清掉。D02 已有格挡翻倍沿用内置 `double`，D09 延迟反击沿用 `delayed-counter`（`lure` 在 `fortify` 族）。

- 全队覆灭（`setup.wipe: true`，`session.js` 新开战斗写入；旧 setup 不带时规则与重放不变，非布尔值拒绝建局 `invalid-setup`）：操控角色倒下不立即判负，我方全员倒下才判负（`checkOutcome`）。操控角色在出牌阶段（自伤、荆棘）或回合开始（中毒）倒下时，`continueWithoutHero` 清掉待选、先按自动阶段判一次胜负（overkill 战斗打空最后一名敌人的同时倒下直接判胜），再交给时间轴：队友与敌人一直自动行动到分出胜负，不再进入出牌阶段；双方都打不动时步数上限为 `MAX_TIMELINE_STEPS × WIPE_STEP_FACTOR`，到上限判负。`report.js` 只在 wipe 战斗判负且我方无人站着时写「终局：我方全员倒下，全队覆灭。」，僵持判负时队友仍站着，照常写落败。
- 持续伤势（v4，助手 10-29）：日志类型 `wound`（`{ hp, maxHp, down, reportId }`，不来自标签，锚定战报用户楼，`reportId` 须与楼里的战报一致，否则 `wound-report-invalid`）与 `heal`（`{ amount, mode: flat | percent, scale, reason }`，来自正文 `[igs-combat:heal|角色|恢复量|原因]`，不设每楼上限；`scale` 为扫描时难度表 `healScale` 的百分比快照，噩梦 50，之后改难度不影响；战报楼里的 heal 只记诊断 `combat-heal-tag-in-report`）。归并：`wound` 覆盖为最近一场的战后生命（满血且没倒下时清空，倒下记 0）；`heal` 只在有伤势时生效，按点数或记录上限的百分比乘 `scale` 恢复（至少 1 点，封顶，回满清空，回血后不再算倒下）。`characterView().wound` 为 `{ hp, maxHp, down }` 或 `null`，旧存档为 `null`（满血）。会话：出结果时把我方单位的战后生命随战报留档（`wounds`，重发沿用），战报楼落楼后写 `wound`（胜、败、撤退都写，条目 ID 确定、幂等）；`buildLobby` 把倒下的队友列进 `downed`、不进 `allies`（主角照常参战）；`buildSetup` 在难度生命上限之后按损失量算开战 `hp`（倒下的主角为 1，没有伤势时不写 `hp`，setup 形状不变）；`lobbyVitals` 写进会话 `lobby.vitals` 供战前显示，`vitalsOf` 供人物状态显示。`createCombatLedger({ difficulty })` 由 `core/combat-services.js` 注入当前难度，未注入按标准档。
- 永久成长与击杀奖励（规则 v5 G24 / G25，`mechanics/battle-growth.js`）：卡牌顶层算子 `evolve`（`{ stat: damage | block, amount: 1–3 }`，打出后本牌成长；重演只算一次，临时牌不成长）与 `bounty`（`{ reward: damage | block | hp-max | upgrade, amount }`，`hp-max` 1–5、其余 1–3、`upgrade` 无数值；只是标记，由 `defeated` 钩子在「本牌击倒」时发奖：来源 `source.kind === 'card'`、`source.id` 与正在结算的 `ctx.inst` 同牌、出牌方为卡组单位且目标非 `minion === true`，中毒 / 灼痕 / 荆棘 / 反击等击倒不算；`upgrade` 只本场升级本牌、不写账本），嵌套在条件等效果里拒收（`card-only`）。本场累计在单位 `res.battleGrowth`（`{ cards: { 卡牌ID: { damage, block } }, hpMax }`，各封顶 20）；v3 / v4 战斗不进入。模板 `whetstone / carapace / trophy`（通用族，`hero:false`）。日志类型 `battle-growth`（`{ cards: [{ cardId, damage, block }], hpMax, reportId }`，不来自标签，锚定战报用户楼、`tagHash: 'battle-growth'`，`reportId` 须与楼里的战报一致，否则 `battle-growth-report-invalid`；只对卡组角色生效，否则 `combat-battle-growth-kind-mismatch`）。归并：按卡牌 ID 累计（同名副本共享），伤害、格挡与最大生命各自封顶 `BATTLE_GROWTH_MAX`（20）。`characterView().hpMax` 叠加累计最大生命，有成长时另返回 `battleGrowth`（`{ cards: { 卡牌ID: { damage, block } }, hpMax }`），没有成长时不写字段。会话：出结果时随战报留档 `battleGrowth`（`reportItemOf`、聊天记录与 `readChatRecord` 校验同步，重发与恢复沿用），战报楼落楼后写 `battle-growth`（胜、败、撤退都写，条目 ID 确定、幂等）；`deckUnit` 把累计伤害、格挡加到开战目录对应牌的 `damage` / `block` 效果（含升级版，单个效果封顶 99）。日常挑战不写。




- 行动顺序（规则版本 2）：行动值时间轴。每个单位行动间隔为 `1000000 / speed`，每步取剩余行动值最小者出手（相同时先计时者先动），全员扣除该段后出手者重新计时；操控角色轮到时 `phase = 'player'` 并发 `turn-start`（`side:'ally'`、`unitId`），`s.turn` 只在操控角色每次轮到时加一；结束回合后其余单位依次自动行动，每次出手前发 `act` 事件（`unitId, side`），快的单位可在操控角色下一回合前多次出手。格挡清零、中毒 / 再生、回能、抽牌、`turn-start` 被动在单位自己行动前结算（`startUnit`），`turn-end` 被动、弃牌、易伤 / 虚弱衰减在其行动后结算（`endUnit`）。开局操控角色先出牌。只读 `upcomingActors(state, count)` 推演接下来的出手者（不改状态、不耗随机数），供面板行动顺序槽。速度来源：`rules.js` 的 `combatSpeedFor({ archetype, tier, id })` 按职业原型 / 敌人档位基准 ± `speedJitter`（按 ID 散列，确定性），生成组装时写入档案 `base.speed`（schema 可选，范围 40–200）；旧档案缺速度时 `session.js` 按同一规则回落，不改写旧档案。`COMBAT_RULES.version` 由 1 升到 2，旧版本进行中战斗恢复时判 `combat-rules-version-mismatch`。
  - 技能单位两动（v0.39.1）：setup 中技能单位可选 `actions`（整数 1–2，只允许 `kind:'skill'`，否则 `invalid-stat`）；`autoAct` 每次出手在一次 `startUnit` / `endUnit` 之间连续调用 `useSkill` `actions` 次（缺省 1），行动间隔不变，单位倒下或分出胜负即停。`createUnit` 只在大于 1 时写入状态。`session.js` 的 `skillUnit` 给技能型助战写 `actions: 2`；敌人与卡组单位不写，旧 setup 没有该字段，重放结果不变，不改 `COMBAT_RULES.version`。

- 手动建档（P8c）：`abilities.js` 的 `MANUAL_BUILD = { base: 8, pool: 24, min: 3, max: 18 }`、`MANUAL_TOTAL = 72`；`normalizeManualScores(raw)` 要求恰好六维键、整数、单项 3–18、总分不超过 72，否则返回 null。`prefsFromScores(scores)` 取最高两项为主擅长、次擅长，其余最低一项为短板，同分按 `str, dex, con, int, wis, cha`。`parseCombatInit(raw, { allowScores })` 只在 `allowScores: true` 时收 `scores`，此时倾向由分值推导、传入的倾向不计；副 LLM 初始化与立绘 DNA 补档链不传该参数，带来的 `scores` 被忽略，返回形状与旧版一致。属性表 init 载荷可选 `scores`（`schema.js`），须合手动刻度（`invalid-scores`）且与 major / minor / weak 推导一致（`prefs-mismatch`）；旧 init 不带 `scores` 照旧读取。`SCHEMA_VERSION` 只用于档案 `v` 字段，未变。`ledger.writeInit(name, raw, { manual: true })` 必须带分值（缺则 `combat-init-invalid` / `scores` / `required`），首写为准不变；`attributeView` 对带 `scores` 的 init 以其为底分，档位修正、属性提升、调整与装备加成照常叠加。`wantsAutoInit({ mode, choice, protagonist, enemy })`：`relative` 只给主角，`manual` 只给敌人与 choice 为 `auto` 的角色，未选或 `auto` 全部给；`session.prepare` 经 `deps.buildMode`（`() → { mode, choices } | null`）按此过滤 `withCombatInitialization` 的名单，卡组与技能生成不受影响。

- `ledger.js`：成长账本。`createCombatLedger({ tables, chat, userName, sourceFilter, now })` → `read / effectiveState / append / scan / saveDeck / claimReward`；只读归并两张战斗表，按锚点（`messageId + swipeId + tagHash + occurrence`，不含 chatId）判定条目是否生效，读取失败返回 `ok:false`，不当作空账本；`claimReward` 只在等级已达到且未领取时写入；写入只经注入的 `tables`。`effectiveState()` 另返回 `growth`（已生效的 exp / learn / upgrade / class 条目，带接手角色、锚点与生效前后等级），供成长演出只读。同名时卡组档案优先：技能档案让位但保留（诊断 `combat-profile-superseded`），其 EXP 在归并时并入卡组档案，不改表；让位档案的其他条目只记诊断 `combat-superseded-entry-skipped`。
- `card-templates.js`：模板库。卡牌模板 `CARD_TEMPLATES` 固定效果形状（含 v2 复合 / 缝合模板，每张最多 3 个分量，可带条件追加与消耗），`solveCardTemplate(key, cost, rarity)` 在 `rarityWindow` 校验窗口内向该稀有度的求解中心整数搜索数值，并生成同形状、不减值、不超 `upgradeAllowance` 的升级版，结果经 `evaluateCardBudget` 复核，无解返回 `null`；`nearestTemplateCost` 取最近的有解费用（只在模板可用费用 `templateCosts(key)` 里找；X 费在要求 X 时最先、否则最后）；`fixedTemplateCost(key, cost)` 供职业卡固定位置使用：模板可用该费用时照用，可用 X 费的模板放在 1–3 费位置时改为 X 费，否则原样返回、由调用方拒收。v4 模板可带 `flags`（`innate / ethereal / unplayable`）、`onDiscard`、`costs`（限定费用，可含 `'X'`）与 `hero:false`；v5 模板的 `flags` 可含 `retain`，并可带 `minRarity`（稀有度下限：personal 视同 uncommon、signature 视同 epic，`solveCardTemplate` 与 `cardFromValues` 对低于下限的稀有度同样无解）；求解结果带出关键字与被弃时效果，估值与 `evaluateCardBudget` 同口径。`heroSkillFromTemplate` 排除带关键字、被弃时效果、稀有度下限、限定费用且不含 `heroSkillCost`、或带本牌专属效果（复制本牌、成长、本牌减费、同名连出条件）的模板。写 `choose` 的模板在选牌界面接入前不开放；`templateCatalogText()` 另起一行列出写 `choose` 的模板（按最小变量值构造后扫描效果树得出），注明只能作卡牌、托管由程序按策略选牌。被动 `PASSIVE_TEMPLATES` 数值固定；技能 `SKILL_TEMPLATES` 按伤害封顶折算；`ultimateSkill(cap, { id, cooldown })` 是强度档绝招，不在目录里。`templateCatalogText()` 给提示词列出模板键与说明、0 费可用模板与按职业原型的推荐模板，不含数值。
- `generation-assembly.js`：紧凑回复 → 完整档案。`assembleClass / assembleDeck / assembleSkillCharacter / assembleEnemy / assembleGrowth` 只接受模板键、名称与少量数值。新职业池恰好 11 张，`classRaritiesFor(owner)` 按角色种子分配 common 7、uncommon 4，与费用使用不同种子域；重试不变，模型不选稀有度。职业卡、个人卡、专属卡的费用取请求里的 `input.costSlots` / 固定 `CARD_COST_SLOTS.signature`（由 `costSlotsFor(kind, 角色ID)` 确定性挑选；请求槽位非法时用固定槽位），回复费用不符只记 `combat-cost-slotted`。职业卡在指定费用与稀有度下无解返回 `template-unsolvable`（带 cost / rarity），交生成纠错，不移动费用槽（只用 `fixedTemplateCost`：X 费模板放在 1–3 费位置改为 X 费，其余限定费用模板费用不符即无解）；`buildCard` 把模板解出的关键字（`innate / ethereal / unplayable`）与 `onDiscard` 带进卡牌，旧模板的卡牌形状不变；其他卡保留最近有解费用规则，`skill-to-card` 仍取回复费用。ID（`档案ID-c1 / -m1/ -g1 / -s1 / -p1`）、效果、升级版、首领半血阶段与起始卡组由程序生成。`buildStarterDeck(classPool, personalPool, seed)` 保持 3/3/10/4，职业仅抽 common / uncommon、单卡 ≤3，个人卡单卡 ≤2；沿用旧职业池时也过滤 rare / epic / mythic。已存档的起始卡组和稀有度不重算、不自动写回；schema 卡池白名单仍接受旧 rare，并登记 epic / mythic。`profile-skill` 可选 `tier`。结构错误按紧凑回复字段路径返回 `errors`；数值越界夹回并记 `combat-value-clamped`。
- `generation.js`：副 LLM 生成。`generateEntities(entities, { request, llm, signal })` → `{ ok, accepted, rejected, diagnostics, blocked }`；回复先经组装，再走 `normalizeProfile / normalizeCard / normalizeSkill / validateStarterDeck`，不合格实体最多定向修正 2 轮，已通过实体不再提交；修正耗尽时敌人回落模板敌人、主角 `blocked`、队友不参战，补技能（`skill-fill`）没有回落；取消返回 `request-stale`。回复无法解析时细分 `combat-reply-empty / combat-reply-truncated / combat-reply-not-json`，不回显回复正文。只构造请求与校验，不落账。`skillFillEntity({ profile, count, version, existing?, createdAt? })` 给已有档案（技能角色或副 LLM 生成的敌人）补恰好 `count` 个技能：回复 `{ skills: [[名, 技能模板键], …] }`，`assembleSkillFill` 追加在档案技能末尾（ID 为 `档案ID-k序号`，接着现有技能数），名称与档案技能、`input.existing`（技能角色含习得的技能）或同批重复时拒收（`skill-name-exists`）；通过结果带 `version` 与沿用的 `createdAt`，`generationWrites` 据此写同 ID 的新版本档案。技能角色队友另传 `level`（属性视图等级，D10）：伤害折算上限按 `allyFillCap`（Lv1–5 为 `allySkillDamageCap` 18、Lv6–10 为 21、Lv11 起为 25）写在 `fixed.cap`（模型不可见），Lv6 起 `input.templates` 只给 `COMPOSITE_SKILL_KEYS` 的 14 个复合技能、选其他键拒收 `invalid-template`；Lv1–5 与未传等级时请求形状与旧路径一致，敌人不受影响。技能角色档案的技能伤害校验上限为 `ALLY_SKILL_CAP_MAX`（25）；新档案、剧情习得 / 精进的技能与绝招仍按 `allySkillDamageCap`。`withCharacterLore(entities, read)` 用调用方注入的读取器给 `profile-deck / profile-skill / profile-init / trait / skill-fill` 附 `input.lore`（角色设定参考），只在读到非空内容时加字段；未注入、读取失败或为空时实体原样返回。
- `generation-retry.js`：`generateWithRetry(entities, { retryDelays, onRetry, ...generateEntities 选项 })` 在 `generateEntities` 外做有界自动重试（默认 `COMBAT_GENERATION_RETRY_DELAYS` = 2s / 6s，最多重发 2 次）。只重发上游明确拒绝、可安全补发的请求（`requestFailure.reason === 'secondary-llm-http-failed'` 且 HTTP 408 / 425 / 429 / 500 / 502 / 503）；取消与迟到、配置不完整、副 LLM 不可用、回复格式修正耗尽、发送状态未知的传输失败与 504 都不自动重发。等待中取消返回 `request-stale`；发生重试时结果附 `retries`，未重试时结果与 `generateEntities` 一致。`generateEntities` 在请求本身失败时附 `requestFailure: { reason, status? }`（不含上游正文）。`session.prepare` 经它生成缺失档案；注入 `awaitProtagonist` 时先等在途的主角卡组预生成结束再读账本，等待后开战楼变化或取消返回 `request-stale`。
- `generation.js` 的 `withStoryContext(context, read, { names, signal, full, persona })`：用调用方注入的读取器给生成请求的 `context` 附 `story`（最近剧情节选）、`worldInfo`（按剧情触发的世界书条目）与 `userPersona`（仅 `persona` 为 true 时），只在读到非空内容时加字段；`full` / `persona` 只在为 true 时传给读取器；未注入、读取失败或为空时返回原 `context`，请求形状与旧版一致。`session.prepare`（按主角、队友、敌人名触发；本批含 `profile-deck` 时传 `full`，同批敌人、奖励与补技能共用这份完整 context）、`combat-services` 的卡组生成（`generateDeck` / `regenerateDeck` 传 `full`，队友卡组另传 `persona`）与 `retryGrowth` 三处接入。


- `report.js`：战报构造。`buildCombatReport(...)` → `{ ok, text, result, reportId, exp }`；只写技能名与相对伤势，胜利附 EXP 标签，失败与撤退不附。
- `session.js`：战斗会话。`createCombatSession(deps)` → `prepare / start / act / finish / retrySend / retryReward / skip / resume / reset / subscribe / state`；断点续战只存 `{ combatId, anchor, seed, setup, actions }`，核对锚点与规则版本后重放；先写待回传再发送，失败不自动重发；已回传的战斗只能回顾。可选 `chatRecord`（`read(anchor, combatId) / write(anchor, combatId, patch)`，bootstrap 注入 `host/combat-chat-record.js`）把准备与结果留档在开战楼聊天记录：首次准备到战前写 `prepared`；出结果当即生成战报并写 `result`（`reportId / result / text / outcome / turn / at`，有道具用量时附 `used / character`），不等发送。`prepare` 与 `resume` 读到 `result` 时只能重发同一份战报（`send-failed`），不重放、不重打，删战报楼或换设备后同样；读到 `prepared` 时只补缺失的主角档案，不再为队友、敌人请求生成；读取失败或格式不对时 fail-closed 阻断（`combat-record-read-failed / combat-record-corrupt`）。写前核对锚点（否则 `combat-record-stale`）；写失败不阻断开战与发送，会话快照带 `recordError`，结算与重发前补写结果。同一场并发 `prepare` 共用一次请求，结束后经 `subscribe(fn)` 通知订阅者。重发同一份战报时 `consume` 用战报自带的用量，道具不因删战报楼而退回。宿主能力全部注入（含可选 `readLore`：`prepare` 生成缺失档案前经 `withCharacterLore` 附角色设定）。补技能（计划 5.4）：首次准备时，技能少于 `skillTarget(等级, 档位)` 的技能角色队友（按属性视图等级）与副 LLM 生成的敌人（`generated` 不为 false；按相对档等级，没有时按我方平均等级）各一个 `skill-fill` 实体，与缺档案实体同批请求；本次新生成的档案仍不足时只含补技能再请求一轮；模板敌人由 `enemy-loadout.js` 按种子补、不发请求；已准备过的场次不请求。通过后写同 ID 的新版本档案（`profileMeta` 版本 + 1，沿用登记时间）并读回；拒收、请求不可用或写失败都不阻断开战，该角色带现有技能参战，会话快照带 `fillDiagnostics: [{ code, owner | owners, reason? }]`。`ledger.effectiveState()` 返回 `profileMeta`（档案 ID → `{ version, createdAt }`）。技能角色进 setup 时按 `allyTierOf(profile)` 放大生命与技能数值（倍率为 1 时沿用原对象），ace / legend 追加 `档案ID-u1` 绝招。开战楼的 `start.awaken` 只在点名角色是本场被操控者时写入 `setup.awaken = { type, line }`（主角可用「我」/主角名/别名）；点名他人或换人操控时不写入，`start()` 返回 `awakenDropped: 'combat-awaken-not-controlled'`；无觉醒时 setup 形状与旧版一致。已装备的装备被动随角色并入单位 `passives`；被操控者持有的道具（余量 > 0，最多 12 种）写入 `setup.items = [{ itemId, name, count, effects }]`，没有道具时不写字段。战报落楼后 `deliver` 按「带入数量 − 结束剩余」写 `consume` 条目（锚定战报用户楼、`tagHash = CONSUME_TAG_HASH`、ID 确定，重复落账幂等），结果放在返回值 `consume`。引擎道具动作 `{ type: 'item', itemId, targetId? }`：目标规则与出牌相同（`target:'ally'` 的回复 / 格挡 / 净化可指定一名存活的己方单位，不指定时按生命比例最低者；伤害与减益对敌方）；模板道具 `potion` / `barrier` / `purify` 为 `ally`，`session.js` 建局时经 `itemEffectsForBattle` 把旧道具 self 的回复 / 格挡 / 净化换成 ally（只影响新开的战斗，已存 setup 与重放不变），能量与抽牌只作用于使用者；道具模板另有单体伤害 `dagger`、单体减益 `poison-dart` / `weaken-powder` / `sunder` / `frail-dust`（选一名敌人）、群体减益 `toxic-cloud` / `smoke`、攻击增幅 `war-tonic`（选一名己方）/ `war-drum`（全体己方），数值见计划 3.8；不耗能量，操控角色每个己方回合限 1 次（`item-used`），用完 `item-empty`，未带入 `item-unavailable`；非法 `setup.items` 拒绝建局（`invalid-items`）。构筑面板换装经 `ledger.setGear(characterId, gearId, equip)` 写 equip / unequip（锚定最新楼层、`tagHash = GEAR_TAG_HASH`、不核对标签），同楼排在全部标签条目之后；只能装上背包里的、卸下已装备的（否则 `combat-gear-missing`）。面板 equip 只把已拥有的装备放进槽位，不按载荷改写拥有记录：来源标签楼换 swipe 或删楼后，面板条目记 `combat-gear-missing`，不复活装备。
- 敌人图集题材（`encounter-theme`，助手 10-31）：`generation.js` 的 `encounterThemeEntity(start)` 产出每场一条可选实体（key `theme:encounter`，input `{ encounter, enemies: [名称] }`），副 LLM 回 `{ theme: 'western' | 'urban' | 'wuxia' }`（目录见 `enemy-art.js` 的 `ENEMY_ART_THEMES`）；非法或缺省只记 `combat-theme-invalid` 诊断、照常通过，不触发修正、不落账。`session.js` 只在首次准备（无 `prepared`）且开战楼留档没有合法 `theme` 时与同批实体一起请求，属 `NONBLOCKING_KINDS`；取得后写进开战楼留档 `theme`、会话快照 `theme` 与开战后的会话存档 `record.theme`，`prepare` 与 `resume` 读回合法值，非法值忽略。题材只决定面板基础格取哪套图集，不进 setup、不影响结算与重放。
- 按剧情给初始装备（`profile-gear`，助手 10-31）：`generation.js` 的 `profileGearEntity(name)` 产出可选实体（key `gear:<技能角色 ID>`，input `{ name, lore? }`），副 LLM 回 `{ gear: [[名称, 部位, 稀有度, 六维键, 被动模板键, 简述?], …] }`，0–4 件、每部位至多 1 件；剧情与设定没写到的装备不给，空列表合法。`generation-assembly.js` 的 `assembleInitialGear` 组装 equip 载荷：加成按稀有度（`GEAR_BONUS_BY_RARITY`），是否带被动按 `gearHasPassive` 由程序决定，被动受 `allySkillDamageCap` 约束；同部位或同名重复拒收并定向修正。只随卡组档案生成请求：`session.js` 首战准备生成主角卡组档案时同批请求（锚定开战楼），`combat-services.generateDeck` 面板手动生成或主角预生成卡组时同批请求（锚定最新楼层）；技能档案角色与敌人不发，属 `NONBLOCKING_KINDS`，失败只记 `gearDiagnostics`。档案读回后经 `ledger.grantGeneratedGear` → `ledger.grantInitialGear(characterId, items, { anchor? })` 写 equip：`tagHash = INIT_GEAR_TAG_HASH`（`init-gear`）、`occurrence` 为 `GEAR_SLOTS` 部位序号，ID 确定、重复写幂等；`anchorProblem` 对它只核对楼层与 swipe。主角启用物品表时与其他 equip 一样经 `appendStock` 入背包。
- 专属卡成长：`generation.js` 的 `growthEntity` 遇到与档案专属卡同名（NFKC、去空白、小写）的 learn / upgrade 时直接给出条目（未持有 → learn 解锁，已持有 → upgrade），不请求副 LLM；副 LLM 的升级候选排除专属卡。`ledger.js` 只认档案登记过的专属卡（否则 `combat-signature-unknown`），专属卡精进只标升级形态、不替换卡面，奖励不得选专属卡（`combat-reward-signature`）。

- 日常挑战（`docs/DAILY_CHALLENGE_DESIGN.md`，第一阶段）：把卡牌引擎当作「过程」使用，引擎、模板与重放原样复用，只在适配层换入口、说法与后果。
  - `challenge-labels.js`：说法映射表（难关、意志、进攻、防守、挑战，状态名慌乱 / 破绽 / 煎熬，难关出招别名），只读常量与查表，不含逻辑；内部字段名不变。
  - `challenge-cards.js`：领域到模板键映射 `DOMAIN_CARDS` 与 `buildChallengeDeck({ domain, skillValue })`，固定 20 张（基础攻击 3、基础防御 3、领域牌 10、生活牌 4）；技能值 0–29 / 30–59 / 60–79 / 80 以上对应 common / uncommon / rare / epic，epic 档只有一张独门牌。只用既有模板与稀有度窗口，结果必须通过 `validateDeck`；领域不在映射表时走通用牌组。第二阶段：`otherSkills`（`{ 技能名: 值 }` 或 `{ 技能名: { value } }`）里领域之外的相关技能（`RELATED_SKILLS`，每个领域三项）值不低于 `RELATED_MIN`（50）时，最多 `RELATED_MAX`（2）项用该技能领域的「应急」牌（tempo 位，按该技能值取稀有度）顶替，第一项换掉一张进展牌、第二项换掉一张稳住牌，卡组仍是 20 张；返回值多一个 `related`（实际顶替的技能名数组）。
  - `challenge-foes.js`：难关模板登记（面试官、评委、对方、截稿、长辈、考官），只登记模板键、日常名称、出招模板键与匹配词；`pickFoe(event, domain)` 先按事件名词、再按领域、最后取兜底难关。第二阶段：每个难关登记 `harvest`（离散词 `奖金` / `经验`），`challengeHarvest(foeKey, outcome, tier)` → `{ prize: 金钱档位词 | null, card: boolean }`，只有圆满才有收获；奖金只登记在评委（比赛类），金额按 `CHALLENGE_PRIZE_BY_TIER` 查金钱表，标签与提示词不增加任何字段。
  - `challenge-setup.js`：`buildChallengeSetup({ start, state, user })`，纯函数，不读写存储；`state` 是数值侧传入的主角快照 `{ bars: { stamina, stress }, skills }`。setup 带 `challenge: { event, domain, tier, stake, foe, rounds }`，`combatId` 前缀 `ch`（`challengeCombatIdFor`）。意志 `willFor` 按体力低、压力高各降一档（阈值与数值侧一致，由测试守住）；难关厚度 `foeThickness` 由 `scaleEnemyStats` 加按托管模拟取值的校准倍率。引擎不改：新建的日常挑战不写 `challenge.rounds`、不设回合上限，只按引擎胜负结算（D16）；`challengeResultOf(state, rounds)` 只在 `rounds` 为正整数时（亲密对决按 `foeThickness` 轻松 4 / 普通 5 / 艰难 6 写入，以及带 `rounds` 的旧挑战记录）判定，`state.turn` 超过上限仍无结局时按进展比例（不低于五成）判成败；`challengeOutcomeOf(result, willRatio, { byLimit })` 得出圆满 / 勉强 / 失败 / 放弃，达到回合上限的成功最多算勉强。建局不需要 `classRef` 或职业档案，单位直接带内联卡组与牌定义。第二、三阶段：`start.foe` / `start.foeName`（副 LLM 选的难关键与名称，键不在登记表时忽略）；`allies`（请求的协助者名）经 `validateChallengeAllies` 校验后加入 `setup.units`，返回值多一个 `allies: { accepted, rejected }`，`setup.challenge` 多 `counterpart` 与 `allies`；`state` 可带 `present`（在场人物名）与 `favors`（`{ 人物名: 好感 }`），并把 `state.skills` 作为相关技能传给 `buildChallengeDeck`。
  - `challenge-report.js`：`buildChallengeReport`，只写结局词与相对描述，不含数值，复用 `reportIdFor`；战报块为 `<igs-challenge-report id result outcome tier stake domain>`；`parseChallengeReport` 与 `challengeDirectiveOf` 供数值侧读回并合成 `challenge` 指令。`CHALLENGE_SKIP_TEXT` 为不使用卡牌结算时的提示，不触发结算。第二、三阶段：战报标记另带 `foe`、`counterpart`、`allies`（以「、」分隔）；`parseChallengeReport` 读回同名字段，`challengeDirectiveOf` 合成的指令多 `counterpart` 与 `prize`（金钱档位词或 null，由难关登记 + 结局 + 难度推出）；失败文案增加金钱与关系两类相对描述。
  - `challenge-allies.js`（第三阶段）：NPC 协助，纯函数。`eligibleChallengeAllies({ present, favors, exclude })` 列出在场且好感不低于 `CHALLENGE_ALLY_MIN_FAVOR`（26，「明确喜欢」阶段下限，即第一道关口之上；测试对齐 `FAVOR_GATES`）的人物；`validateChallengeAllies(requested, { present, favors, exclude })` → `{ accepted: [{ name, favor }], rejected: [{ name, reason }] }`，原因为 `invalid / duplicate / counterpart / not-present / favor-low / over-limit`，最多 `CHALLENGE_ALLY_MAX`（2）名，只拒收不修正；`buildChallengeAllies(accepted)` → `{ cards, units }`，每人一张专属牌（`allyExclusiveCard`，按人名从既有模板池 `ALLY_CARD_POOL` 稳定挑选，uncommon，id `ch-ally-<序号>`）并入主角卡组（20 + 人数张，仍在 `deckMax` 内、通过 `validateDeck`），友军为 `deck` 型单位（基础牌加两张专属牌，id `ally1` / `ally2`），由引擎自动回合按 `chooseAllyPlay` 出牌。
  - `challenge-foe-pick.js`（第二阶段）：`chooseChallengeFoe({ event, domain, request, llm, signal, context, retryDelays })` → `{ foe, name, source: 'llm' | 'local', reason? }`。经 `generation.js` 的 `challengeFoeEntity`（kind `challenge-foe`，input `{ event, domain, foes: [{ key, name, hints }] }`，回复 `{ foe, name }`）请求副 LLM，`generation-assembly.js` 的 `assembleChallengeFoe` 只收登记过的难关键与 1–20 字名称，非法即拒收并带错误重问（`generateEntities` 现有修正轮数），仍不合格或副 LLM 不可用、请求失败时退回本地 `pickFoe`（拒收记录的 `fallback` 为 `{ kind: 'local-foe', foe }`）。
  - `challenge-reward.js`（第三阶段）：`planChallengeReward({ combatId, outcome, tier, foe, domain })` → `{ ok, seed, slot: { rarity, cost }, card }` 或 `{ ok: false, reason }`。只有圆满且难关登记了「经验」才出牌；稀有度与费用取 `planRewardSlots` 的首个卡牌槽（稀有度封顶 rare、费用 1–2），模板键按种子从领域模板键里稳定挑选，求不出时顺延；只出数据，不写账本，落到卡库由接线层决定。
  - `challenge-history.js`（第三阶段）：`deriveChallengeHistory(messages)`，messages 为 `{ floor?, text }` 或字符串数组，只读推导，不新增账本类型、不存档；`parseChallengeReport` 读战报楼，同一战报编号只记一次，返回 `{ entries: [{ floor, event, reportId, result, outcome, tier, stake, domain, foe, counterpart, allies }], stats: { total, wins, losses, escapes, byOutcome, byDomain, bestStreak, currentStreak }, achievements: [{ id, name, floor }] }`；成就 id 见 `CHALLENGE_ACHIEVEMENTS`（初战告捷、圆满完成、迎难而上、连战连捷、并肩同行、百炼成钢），floor 为首次达成的楼层。
  - 数值结算（`scene/stats/stat-challenge.js`，第二阶段）：金钱代价按难度档查金钱表（少量 / 普通 / 昂贵），放弃减半，不超过合并余额（`walletBalance(bars, ctx.walletExtra)`）的 `DEFEAT_MONEY_LOSS`（两成），扣在 `bars.money`（可为负）；关系代价走 `applyDim(对方, '好感', -n)`（n 为一 / 二 / 三，单楼不超过 `FLOOR_GAIN_MAX`，放弃减半），对方不在 `state.characters` 或不在 `ctx.present` 时降级为压力并记 `challenge-stake-degraded`；`stat-favor.js` 的 `baseDelta` 接受好感的整数增量（只服务这条路径）。负向扣分不经过 `gateCap`，不会绕过关口，已解锁关口记录保留。胜利：圆满且指令带 `prize` 时发一次金钱收入；关系类圆满经 `applyKeyEvent('和解')` 突破关口，不直接加数字。

## 约束

- 日常局不写伤势、不写战斗账本，不产出战利品、翻牌与成长标签；`setup.challenge` 存在时 `session.prepare` 不调用档案生成。会话接线：`session.js` 的 `locateCombatStart(chat, id, filter, kinds)` 按对决类型认战斗或挑战标签（挑战 `combatId` 前缀 `ch`，会话带 `kind: 'challenge'`）；挑战备战只调副 LLM 选难关（失败退回本地），不读账本；`autoPlay` / `abandon` / `pickChallengeAllies` 为挑战专用入口；结束时不翻牌、不写伤势与物品消耗、不扫描战斗账本；圆满且难关登记了经验时战报发出后写一条挂在战报楼上的 `learn`（`ledger.js` 的 `CHALLENGE_REWARD_TAG_HASH`）。`combat-services.js` 的 `kinds()` 把对决类型传给会话，仅日常挑战时不预生成主角卡组、不接管物品表、不自动成长；`challengePromptQuota` 给提示词与入口做额度门禁，`challengeHistory` 只读聊天里的战报。
- schema 校验只拒收不修正：未知字段、越界数值、超预算、未知效果一律返回 `{ ok: false, errors: [{ path, reason, detail? }] }`。可选字段只在缺省时取默认值。
- 组装层只对模型给出的数值（费用、HP、每级 HP、列表长度、名称长度）夹回范围并记 `combat-value-clamped`；模板键、原型、必填被动等结构错误仍拒收并定向修正。组装产物必须再过 schema，组装不得绕过校验。
- 副 LLM 不写效果原语：只从模板目录选键，效果由模板生成；旧档案（完整效果结构）照常按 schema 读取。
- 档案与日志带 schema 版本 `v`；不支持的版本拒收，不就地升级。
- 同一职业以已登记的 `class` 档案为准；`deck-character` 通过 `classRef` 引用职业，只持有个人部分。
- 起始卡组固定为 20 张：基础攻击 3、基础防御 3、职业卡 10、个人卡 4，且同名卡不超过 3 张。

- 人物特性（P-d，助手反馈 3）：`traits.js` 为纯常量与纯函数：特性槽 `TRAIT_BASE_SLOTS = 2`、`TRAIT_SLOT_MAX = 5`、`TRAIT_SLOT_COSTS`（第 3 / 4 / 5 槽依次 500 / 1000 / 2000 积分）、主动上限 `TRAIT_ACTIVE_MAX = 2`，`traitSlots` / 1）；`planTrait(traitSeed(heroId, traitDraws))` 按主角 ID 与已生效抽取次数确定稀有度，楼层回退后再抽得到同一稀有度；`traitLinks(traits, gearSlots?)` 汇总翻牌联动（透视取最大、神话特性或神话饰品宝物亮 2 张，再翻 / 天运任一即生效；v5 起合并已装备饰品与宝物的可选 `link`，装备载荷 `equip.link ∈ reveal | reflip | fortune`，账本、背包定义与投影原样透传）；`traitPassives(view)` 只取装着的特性被动。日志表新类型 `trait`（`{ traitId, name ≤20, origin ≤30, rarity, passive, link?: reveal | reflip | fortune, cost }`）与 `trait-pick`（`{ traitId, drop }`），只主角卡组角色，锚定写入时最新楼层（`tagHash = TRAIT_TAG_HASH`，与其他面板操作共用 occurrence 序列），经 `ledger.drawTrait(characterId, trait)` / `ledger.pickTrait(characterId, traitId, drop)` 写前按「当前状态 + 本条」试归并，会被拒收时不写、不扣。归并：trait 须 `cost === TRAIT_DRAW_COST`（100，`points.js`）、没有待定特性、traitId 不与已装重复、被动伤害不超过队友技能上限；带 kind 的新条目装得下（`traitFits`：有空槽且主动不超 2 个）直接装上，否则成为 `pendingTrait`；没有 kind drop 的永久消失、积分不退；待定的主动只能替换主动，替换不能让其他保留着的固有特性暂停、也不能让主动超过 2 个，否则拒收 `combat-trait-pick-blocked`。日志表类型 `trait-slot`（`{ slot: 3–5, cost }`）经 `ledger.unlockTraitSlot(characterId, slot)` 写入：只主角，slot `traits`、`pendingTrait`、`traitDraws`、`innateDropped`、`slotUnlocks`。会话：`deckUnit` 的被动追加装着的特性被动；`rewardFor` 把准备时主角特性的 `traitLinks` 传给 `rewardEntity`（再翻 4 槽、天运上调一档、透视写入 offer.reveal），开战后换特性不影响本场。生成：v4 按与稀有度相同的种子抽定效果形状，`traitEntity` 带 `shape` 时 input 给 `kind` 与 `effect`，模型只回 `{ name, origin }`；内部禁止组合 `combos.js`（`FORBIDDEN_COMBOS` 7 条，`forbiddenCombos(shape, { withDeck })`）由 `buildCard`（命中记 - 华而不实被动（P-e，助手反馈 3）：`card-templates.js` 的 `FLAIR_PASSIVE_TEMPLATES`（12 个 `flair-*`，基础效果都是 1 点或 1 层；v5 抽取权重 `FLAIR_PASSIVE_WEIGHT = 2`：特性池 `planTraitShape` 按形状权重抽，胜利奖励的 gear 槽由 `rewardEntity` 按种子与权重预抽 5 个候选写入槽位 `templates`，`assembleReward` 只收候选内的模板，不带候选的旧槽仍用全表）与 `PASSIVE_TEMPLATES` 合并为 `GEAR_PASSIVE_TEMPLATES`，`passiveFromTemplate` / `passiveAtRarity` / `gearPassiveFromTemplate` 按合并表取值。组装层只让人物特性（`assembleTrait`）、装备被动（`assembleGear`）与胜利奖励的装备槽（`assembleReward` 的 gear 槽）按合并表校验模板键；职业、个人、技能角色与敌人被动（`passiveOf`）仍只认 `PASSIVE_TEMPLATES`，道具槽只认 `ITEM_TEMPLATES`，越界记 `invalid-template` 并定向修正。提示词模板目录另列华而不实被动表并写明可用范围。「在特性与装备奖励中提高权重」的机制与比例待助手确认，确认前不加权。



- 胜利翻牌（v3 第 12b 步）：`flip.js` 为纯函数，不读写存储。位置按 `combatId` 与套别的种子打乱（`flipOrder`），重开一致；透视（`offer.reveal`）先亮出 1–2 张，只亮不算翻（`revealedOf`）；4 槽（再翻）时翻两张后 `chooseCard` 二选一，否则 `flipCard` 翻一张即选定；`rerollPick` 花 `REROLL_COST` 换上备用套重新翻，每场一次，旧 offer 没有备用套或领取者不是主角时 `combat-reroll-unavailable`、合并余额不足 `combat-points-insufficient`、已换过 `combat-reroll-used`；`flipView` 只给已翻开、已亮出的牌带槽位内容，选定后全部翻开。会话在胜利结束（`ended` / `send-failed`）时经 `loadFlip()` 读本场 offer 建 `session.flip`：`loading`、`none`（没有 offer，照发不带战利品）、`error`（账本读不到或进度损坏 `combat-flip-corrupt`，不能发）、`ready`；`act` 出胜负、`prepare` 与 `resume` 落到已出结果时自动读取。`flip(position) / choose(position) / reroll()` 的进度 `{ set, flipped, choice }` 先存会话存档 `record.flip`，再写开战楼聊天记录该场的 `flip` 字段（不改 `result`）；没有会话存档时写进聊天记录才推进（否则 `combat-flip-save-failed`）。几份进度不一致时取更靠后的，换设备后同样不能重翻。`finish` 与 `retrySend` 在有 offer 时必须已选定（`combat-flip-required`），经 `attachLoot` 附战利品后写待回传再发送；战利品附进战报后翻牌锁定（`combat-flip-locked`）。会话按合并余额（见「金钱与积分合并」条）放行重抽，账本归并不再拒收。
- 金钱与积分合并（数值可见化计划 §二）：界面统一叫「金钱」，内部字段仍为 `points`。主角余额 = 战斗账本主角 `points`（净流水，可为负）+ 数值侧 `bars.money`（同步取值），按 1:1 相加，不迁移、不改写存储。`createCombatLedger({ wallet })` 接收同步取数函数（数值系统未启用或取不到为 0）：`effectiveState()` 返回的主角视图 `points` 已是合并余额（同一状态与同一金额返回同一对象，不改共享的记忆化状态），`effectiveState({ raw: true })` 只给战斗侧自己的流水（生命缓存与成长缓存用它，避免缓存会变的金额，也供数值系统读取战斗侧积分）。归并阶段删去全部 `state.points < cost` 拒收（loot 备用套、rebuild、respec、ascend、trait、trait-slot）；旧条目照旧有效。主角面板写口（`buildHeroPanelEntry`，传入 `wallet`）与服务层、会话层、面板的预检一律按合并余额判断。战斗扩展关闭时数值侧只剩 `bars.money`；战斗侧已有的积分不显示也不丢，重新打开后重新并入。数值侧「花费」的「买不起」按合并余额判断，扣款记在 `bars.money` 上（可为负）。随身系统（`scene/origin/*`）的「积分」是另一回事，不在此列。
- 翻牌界面（v3 第 12c 步）：战斗面板只读 `session.state().flip`，经 `session.flip(position)` / `choose(position)` / `reroll()` 操作；面板不另读积分，重新抽取的消耗与是否可用取 `flip.reroll`，选定战利品后才出。界面置灰只是提示，发送门禁仍由会话层 `combat-flip-required` 负责。


- 引擎不就地修改入参：`applyAction` 先校验，非法动作返回原 `state`、空事件和 `{ reason, detail? }`；合法动作在副本上结算。断点续战只保存 `setup`、`seed` 与动作序列，由 `replayBattle` 重建，不持久化引擎快照。
- 开局配置 fail-closed：规则版本不符、单位 ID 非法或保留名、卡组引用未知卡、操控角色不是友方卡组角色、种子非法均拒绝建局。

## 禁止

- 禁止在 combat 内直接访问 DOM、酒馆全局对象或 `AutoCardUpdaterAPI`。
- 禁止使用 `Math.random` 或当前时间影响战斗结算；随机性必须来自传入的种子。

## 卡组增强：卡组方向与角色素材

- `generation-materials.js` 负责 JSON 指针、候选路径、角色别称、素材裁剪与 14000 字符预算，纯函数，不访问宿主或写数据。方向上限 1600 字符；失效路径、表消失和超预算明确拒收。
- `context.generationHint` 指导名称、风格与模板，`context.characterMaterials` 携带 MVU/技能表素材及冲突优先来源；不改变输出协议、费用槽、卡牌数量、强度窗口或记账规则。资料文字不是系统指令，未解锁或归属不明的能力不自动视为已掌握。
- 初次卡组、重建、AI 转职与升阶走同一素材入口；确认时重读，`materialChatId` 与当前聊天不一致就停止。已有职业直接转职不请求模型和素材。
