# combat 模块契约

## 职责

- 职业显示：角色属性视图的 `className` 优先取当前已重放职业名，没有职业档案时回落属性初始化名称。转职不改写 init，不重置六维、定位或偏好；既有转职保留旧牌、仅把新职业卡加入目录的规则不变。

- 战斗扩展的领域逻辑：规则常量、数据契约校验、战斗引擎、托管策略、成长日志归并、副 LLM 生成校验、战报构造与战斗会话编排。
- 设计与计划：`.limcode/design/combat-expansion.md`、`.limcode/plans/combat-expansion.plan.md`；实施核实结论见 `docs/COMBAT_EXPANSION.md`。

## 依赖方向

- combat 只依赖 scene 的解析结果与经参数注入的 data/shujuku 适配器；不导入 visual、host、core。
- visual 与 core 依赖 combat；宿主发送、副 LLM、存储均由调用方传入。
- `challenge-*` 只依赖 combat 内部、scene 的标签解析常量与数值侧传入的参数，不导入 visual、host、core；数值结算放在 `scene/stats/stat-challenge.js`，由数值侧自己读战报，combat 不读数值存档。

## 文件

- `class-passives.js`（规则 v6 G6）：`CLASS_PASSIVES` 固定八职业三阶效果，`fixedClassPassive(archetype, tier, id)` 返回独立副本；未知原型或非 1–3 阶返回 `null`。新生成职业写 `classPassiveVersion: 1`，忽略模型的 `passive`；旧档案缺标记不补写，旧职业升阶仍用 `passiveAtTier`，已存 setup 按自身被动快照重放。
  - 战士开战攻击力 1／2／3；守护开战格挡 8／12／15；游侠主动弃每张牌对随机敌人造成 2／3／4 点攻击伤害，自然弃牌不触发。
  - 刺客一阶开战抽 2 张，二／三阶前 3 回合各抽 2／3 张；召唤每次自身回合开始召唤 1／2／3，二／三阶首次额外召唤 5／6（`battle-first`，不会按同一全局回合重复领取）。
  - 法师一阶凝结 1 雷珠，二／三阶凝结 3 雷珠并获得 1／2 层 `arc-core`（雷蕴），只在 v6 同时增加被动和引发雷伤；旧 `arc-boost`（雷涌）仍只增加引发伤害。状态经 orb 注册和 `apply-status` 校验。
  - 祈司开战圣辉 3／7／9，沿用单次上限 5 分段施加；乐师开战造 1／3／4 张 `token-miracle`，单次最多 3 张，遵守手牌与临时牌上限。「奇迹」0 费、保留、获得 1 能量后消耗；旧 `token-grace` 定义不变。

- `rules.js`：`COMBAT_RULES`（每回合能量 3、抽牌 5、卡组至少 `deckMin` 10 张且不设玩法上限（规则 v6，`deckSanityMax` 200 只是异常数据护栏）、敌人档位、职业原型）、基础卡 `BASIC_CARDS`、卡牌价值预算 `evaluateCardBudget`、经验曲线 `levelFromExp/expProgress`。`cardCopyLimit(rarity)`：basic / common / uncommon / rare / epic / personal 同名上限 3，mythic / signature 为 1，未知档返回 0；`validateDeck(deck, owned, catalog)` 必须由目录提供稀有度，缺卡返回 `unknown-card`、未知档返回 `invalid-rarity`，不放行。规则 v6 起同名上限只约束获得来源（奖励候选），卡组校验、日志回放与构筑按钮只看拥有数与稀有度有效性。稀有度窗口 `rarityWindows`（每档 `min / max / target` × 费用预算；`rarityWindow(cost, rarity)` 返回校验窗口与求解中心）：D-2 采用 42 张独立参考样本标定，基础档目标保持 1.0，common / uncommon / rare 的 min–max、target 分别为 0.75–2.07、1.8 / 0.65–2.7、1.98 / 0.6–3.25、2.16；epic / mythic / personal / signature 沿旧档目标比例外推，详见 `docs/COMBAT_CARD_CALIBRATION.md`。未标记自创牌的升级上限为窗口上限 × 1.4；模板升级方向由版本化显式策略决定，区分来源组件、项目策略及来源未核实处理，不再由 `templateUpgradeGain` 反解。`cardValue` 中全体系数 1.4、随机系数 0.85、`each-turn` 2.5 保持，`damage-from-block` 按预期格挡 8 × 4/3 估值，预期值不改变实际结算。未登记稀有度拒收，不回落 common。另有 `signatureLimit 2`、`signatureCopyLimit 1`、技能角色强度档 `allyTiers`（support / peer / ace / legend 的生命、技能倍率与绝招冷却，暂定值）与 `defaultAllyTier 'peer'`。
  - 预算与存档读取：`estimateEffectsValue`、`estimateCardValue` 和 `evaluateCardBudget` 默认使用当前模型；生成、新定义规范化及账本 `append` 不启用旧预算。仅账本 `normalizeSnapshot` 读回时向 `normalizeProfile`、`normalizeLedgerEntry` 显式传 `{ stored: true }`，由 `evaluateStoredCardBudget` 接受当前模型或冻结的 `CARD_BUDGET_V1` 之一完整合法的定义；不混用两版上下界、不缩放卡面、不写回存储，字段与效果结构校验保持严格。
  - 战斗自动选择：引擎的发现、预知、额外保留及 `policy.js` 选牌使用 `estimateBattleEffectsValue`，沿用 D-2 前效果估值（格挡转换固定为 8 价值）；预算标定只影响新定义，不让旧 setup 中动作的隐式选牌漂移。
  - 敌人开战数值 `scaleEnemyStats(profile, level, difficulty, { gap })`：生命 = 档案生命 ×（1 + `tierScalePerLevel` 0.05 ×（等级 − 1））× 难度 hp × 档位 `hpScale` ×（1 + `levelGap.hp` 0.02 × 等级差）；伤害倍率 = 难度 damage × 档位 `damageScale` ×（1 + `levelGap.damage` 0.04 × 等级差），取两位小数、上限 5。难度倍率大于 1 的部分按档位 `difficultyGain` 折算。等级差由 `enemyUnits` 按敌人等级减我方平均等级传入，负值按 0；没有属性视图时为 0。基础生命／伤害倍率为普通 1.2／2.38、精英 1.01／1.49、首领 0.51／0.75。档案生命区间与技能伤害上限仍按 `hp / damageCap` 校验。
  - 剧情建局阶梯：`crowdScaleFor(敌人总数, 有效胜场)` 依次为单敌、双敌、三敌、四敌以上取值；只计到第一名后备，更多后备不继续折扣。

    | 有效胜场 | 单敌 | 双敌 | 三敌 | 四敌以上 |
    |---|---:|---:|---:|---:|
    | 0–4 | 0.80 | 0.40 | 0.28 | 0.22 |
    | 5–9 | 0.85 | 0.55 | 0.46 | 0.42 |
    | 10–14 | 0.90 | 0.70 | 0.64 | 0.61 |
    | 15–19 | 0.95 | 0.85 | 0.82 | 0.81 |
    | 20 起 | 1 | 1 | 1 | 1 |

  - 有效胜场复用主角 `purge.battle`，弱敌胜利不推进。`prepare` 只重放至开战楼并冻结胜场，准备期间重读不漂移；回退后新建战斗重新取档。剧情精英另乘 `encounterScaleFor('elite', 胜场, 主角当前职业)`：初期强度战士 1.25、守护 1.06、游侠 1.11、刺客 1.27、法师 1.33、祈司 1.10、召唤师 1.16、乐师 1.15，每五胜按四等分恢复到 1.4；返回值除以同档单敌 `crowd`，使群敌沿相对人数折算，未知职业从 1.4 起。普通及其他档位该函数返回 1。此层只在剧情 `buildSetup` 使用，共用 `scaleEnemyStats` 与日常挑战不接入。
  - `enemyUnits` 在基础与六维换算后，将生命、伤害倍率乘以 `crowd × encounterScaleFor × generatedScale[档位]`。`generatedScale` 仍只登记生成首领 0.9，模板敌人不乘；生命取整并限制 1–9999，伤害倍率取两位小数、上限 5。`buildSetup` 保存已烘焙单位与 `crowd`，引擎只校验后者为 (0,1] 并透传；恢复及旧 setup 重放均不再计算阶梯。
  - 新 v6 剧情 setup 写 `hpLossRules: 1`：完整未格挡攻击金额先进入 `hp-loss-before`，随从分摊后再按主人当前生命封顶。字段只接受显式 `rulesVersion: 6` 的数值 1，否则拒收 `invalid-hp-loss-rules`；不带该字段的旧 setup 保留原先提前封顶的重放语义。

- `schema.js`：效果原语、卡牌、技能、被动、档案（`class / deck-character / skill-character / enemy`）与成长日志条目的判别联合校验。`deck-character.heroSkill` 可选（人物技能，`{ id, name, effects, description? }`），效果按 `COMBAT_RULES.heroSkillCost` 费用的 `personal` 预算校验；旧档案没有该字段时由 `session.js` 按职业原型回落 `defaultHeroSkill`。`deck-character.signatureCards` 可选（0–2 张，只收 `signature` 稀有度，ID 不得与职业池 / 个人池 / 基础卡冲突，不得进入起始卡组 → `signature-in-starter`）；`skill-character.tier` 可选（`allyTiers` 的键）。两字段缺省时都不补字段。
- `random.js`：确定性哈希与伪随机数，用于战斗重放。
- `battle-state.js`：只读的战局查询与数值估算（存活单位、最弱目标、卡牌视图、伤害/格挡计算、条件判定、意图描述），供引擎与策略共用。`targetSpec` 统一静态固定卡省略 `target` 时的默认值，出牌目标判定、合法动作、托管、面板与结算共用；`engine.js` 保留同名导出。随从攻击、计数攻击、溅射等进攻效果默认指向敌人，状态按自身／减益类别取目标；显式目标优先，`conditional / requires / random-branch` 的即时嵌套效果参与选敌判定。
- 卡牌六维倍率（`attribute-policy.js` / `card-origin.js` / `card-attributes.js`）：只作用于卡组单位的卡牌效果；技能单位、敌人技能仍走 `card-scaling.js` 的 `scaleSkills`，人物技能、特性、装备与职业被动不换算。
  - 策略快照 `{ version, role, scores, proficiency }` 由 `createAttributePolicy(character)` 按开战时的六维、熟练加值与当前职业 `classProfile.archetype` 冻结，新建局写 `version: 2`；`validAttributePolicy(value, version?)` 接受 1、2，要求原型为八职业之一、六维为 1–30 整数、熟练加值为 2–9 整数，给定 `version` 时须与之相同，非法即抛 `invalid-attribute-policy`，不退回倍率 1。
  - 倍率 v1（旧局）：`diff = floor((属性 − 10) / 2) + proficiency − 2`；普通档 `round2(clamp(1 + 0.08 × diff, 0.90, 1.30))`，保守档（`tier: 'support'`）`round2(clamp(1 + 0.04 × diff, 0.95, 1.15))`。
  - 倍率 v2（规则 v7 新建局）：`diff = floor((属性 − 10) / 2)`，熟练加值仍保存但不参与，等级不再带来倍率成长；普通档 `round2(clamp(1 + 0.30 × diff, 0.70, 3.00))`（主属性 20 为 2.5），保守档 `round2(clamp(1 + 0.15 × diff, 0.85, 2.00))`。两版共用 `scalePositive`：只换算原本为正的数值，`max(1, round(原值 × 倍率))`；零、负值与代价不变。
  - 归属：`cardArchetypeOf(card, origins)` 依次取固定牌分组、机制临时牌表、卡牌 `archetype` 字段、开战装配还原的 `cardOrigins`（旧职业池与升阶记录），都没有时为 `general`；非法值抛 `invalid-card-archetype`。`cardAbility`：伤害取牌归属职业的主属性（物理四职业力量、法师智力、祈司感知、召唤师／乐师魅力），`general` 取使用者当前职业主属性；普通格挡法系四职业取其主属性、其余取敏捷；治疗取感知。转职、复制、升级不改变归属。
  - 换算点：`cardView` 先合并升级、成长、加成与刻印，再由 `attributeCardView` 遍历 `effects`、`then / a / b` 与 `onDiscard`，静态金额（`timing: 'static'`）在视图换算一次并写 `attributeScaling[]`（`path / ability / multiplier / base / value`）；延迟金额（`timing: 'deferred'`：计数合计、法珠效能、`apply-status` 中的蚀珠蓄积）只在 `_attribute` 冻结倍率，由所属算子在最终基值处经 `attributeAmount` 换算一次。算子在机制注册时以 `attribute` 声明换算职责，未声明的算子不调整；已带 `attributeScaling` 的视图不重复换算。实际结算、`estimateDamage / estimateBlock`、托管与手牌共用同一视图。
  - setup：`buildSetup` 新建局写 `attributeRules: 2`，`deckUnit` 不预缩放目录、带 `attributePolicy`；`validAttributeRules` 只接受 1（`rulesVersion >= 6`）与 2（`rulesVersion >= 7`），否则 `invalid-attribute-rules`；带此字段时卡组单位缺策略、策略非法或策略版本与 `attributeRules` 不同即拒收 `invalid-attribute-policy`。已存 v6／v7 的 `attributeRules: 1` 局按 v1 公式重放；不带 `attributeRules` 的旧 setup 不读策略，沿用已存目录数值重放。
  - 敏捷筛牌：敏捷 ≥ `ATTRIBUTE_SIFT_AT`（16）的单位，每个自身回合一次，主动打出的牌首轮执行 `draw` 时多抽 1 张，后续 `mode: 'choose'` 的弃牌按实际多抽张数追加；没有实际多抽就不追加。限次记在 `turnStats.attributeSift`，进度随 `state.play` 跨待选阶段保留，自动连带出牌与重演第二次起不触发。
  - 等级免费额度：每个 2 级起、非属性点等级给一次免费抽卡与一次免费升级，互相独立。`card-draw` 可带 `free: { level }`（此时 `cost` 须为 0），`card-upgrade` 可带 `level` 代替胜场机会；重放核对等级（`combat-card-draw-free-level-invalid / -level-unreached / -used`，升级同名前缀 `combat-card-upgrade-free-`），旧 `reward` 已领的等级不再发放。角色视图给 `freeDraws / freeUpgrades`（可用等级列表）；服务层 `drawCard({ signal, free })`、`upgradeCard({ level, copyId })`，额度不可用时返回 `combat-card-draw-free-unavailable` / `combat-card-upgrade-free-unavailable`，生成失败或取消不消耗。
  - 职业牌池：新生成职业不再请求或组装 `classPool`（为空）；旧档案的 `classPool` 照常读取，供目录装配与归属还原。
- `engine.js`：纯函数引擎。`createBattle(setup, seed)`、`applyAction(state, action) → { ok, state, events, error? }`、`legalActions(state)`、`replayBattle(setup, seed, actions)`、`seedFor(combatId)`。结局为 `victory / defeat / escape`；操控角色倒下即 `defeat`。人物技能动作 `{ type: 'hero-skill', targetId? }`：每回合一次、耗 `heroSkillCost`（2）能量，目标规则与出牌相同（只对需要敌方目标的效果展开敌方 targetId，`ally / all-allies` 自动结算）；发出 `hero-skill` 事件；setup 无 `heroSkill` 时不产生该动作，旧记录照常重放。规则 v4（当前 `COMBAT_RULES.version = 5`，`COMPATIBLE_RULES_VERSIONS = [3, 4, 5]`：v3、v4 进行中战斗与记录照常重放，v5 新机制只在 `state.rulesVersion >= 5` 时启用；战局 `rulesVersion` 取 setup 的值，缺省为当前版本）新增弃牌、弃全手再抽、复制、生成临时牌（`TOKEN_CARDS`，每单位每回合上限 `tempCardsPerTurn`）、重复上一张、下一张多结算、本场成长、减费、限时触发 BUFF，出牌 / 被弃 / 消耗 / 击杀 / 洗牌 / 失去生命 / 获得格挡触发与对应条件，卡牌关键字 `innate / ethereal / unplayable / retain` 与 `onDiscard`，以及 `choose` 动作与 `state.pending` 待选阶段（界面未接入前生成路径不产出写 `choose` 的卡牌）；新事件 `discard / exhaust / card-created / repeat / replay / replay-next / grow / cost-mod / buff / buff-trigger / choose-start / choose`，战报、成就与命中演出只处理已知事件。规则 v3（当时 `COMBAT_RULES.version = 3`，v2 进行中战斗按 `rules-version-mismatch` 作废）新增效果原语 `damage-from-block`、`self-damage`、`double`（poison/block/strength）、`next-turn`（draw/energy）、`each-turn`（能力牌登记、每回合开始触发，不可嵌套）、`hand-cost`（本回合手牌费用修正、最低 0、X 费不变、回合结束清除），伤害可选 `strengthScale`，新状态 `intangible`（受伤降为 1，本单位下次回合开始衰减）、`no-draw`（本回合禁抽）、`endure`（首次致死保留 1 生命并获 `endureBlock` 格挡后移除）；`damage-from-block` 在技能伤害上限校验中按超限处理。觉醒动作 `{ type: 'awaken' }`：仅 setup 带合法 `awaken` 时可用，每场 1 次、不耗能量，效果取 `COMBAT_RULES.awakenEffects[type]`（`heal-pct`、`other-allies` 与 `next-turn` 的 status 增益只供觉醒内部使用，不进卡牌 schema），发出 `awaken` 事件；非法 `setup.awaken` 拒绝建局（`invalid-awaken`）。
  - v4 第二批机制（setup 不带新字段时结算不变）：新状态 `artifact`（人工制品：承受方被施加减益 `weak / vulnerable / poison / no-draw / frail` 时抵消并减 1 层，发 `artifact` 事件；净化不移除）、`frail`（脆弱：承受方获得的格挡在出手方敏捷加成后 ×0.75 向下取整，本单位回合结束减 1 层，可被净化）；被动触发 `foe-card-played`（对方出牌：出牌结算完后对侧存活单位的被动按行动顺序接收，主目标为出牌者，可限 `cardType`；限时 BUFF 不接收）；状态牌 `status-daze`（眩晕：不能打出、虚无）、`status-wound`（伤口：不能打出）。卡组单位的 `create` 照常生成进自己牌堆；技能单位（敌人、队友）的 `create` 只接受状态牌，塞进对方卡组单位的牌堆（技能指定目标 → 对方操控角色 → 对方第一名存活卡组单位），计入承受方本回合临时牌上限。估值：人工制品 6、脆弱 1.5，往自己牌堆生成状态牌每张 -3。

### 特色模板与真实消耗

- 新剧情、挑战和亲密局保存 `exhaustRules: 1`，只接受显式规则 v7；非法值或旧版本携带该字段报 `invalid-exhaust-rules`。无标记旧 setup 恢复不补字段，保留历史余烬与消耗计数行为。规则版本仍为 7，`cardUpgradeRules` 仍为 1。
- `exhaustCard` 区分能力牌正常离场（`reason: 'power-play'`）与真实消耗（效果消耗或本牌消耗）。新局事件带 `reason / realExhaust`，实例保存最近入堆的 `realExhaust`；能力牌正常离场不触发余烬，真实消耗能力牌照常触发。`exhausted-gte` 和消耗堆计数在新局只计 `realExhaust === true` 的实例，旧局保持原过滤。
- `mechanics/card-signatures.js` 登记特色算子、估值与运行钩子。`on-event` 将永久效果写入 `unit.buffs`，允许 `exhaust / create / card-played / radiance-shift`；`create` 按本单位实际生成张数触发，含状态与诅咒，敌方塞牌不派发该总线。`radiance-shift` 只在圣辉实际增减时派发一次，不按点数；0–10 截断后无变化不触发，消耗圣辉原有的 `radiance-spent` 仍独立派发。
- `exhaust-strike` 先固定其余手牌集合，按实际消耗数对指定敌人逐次攻击，不把消耗触发新抽到的牌计入原集合；`orb-barrage` 按当前持有法珠数攻击指定敌人，无珠不攻击。两者的运行估算读取实际手牌／法珠数量；动态数量估值是项目假设，不代表整体平衡。

- `delay-attack` 是下回合整回合攻击翻倍；`extra-turn` 结束当前回合并允许连续额外回合，不受旧 `curtain-call` 每场一次约束。`reboot` 将其余手牌、弃牌与消耗堆洗回抽牌堆再抽牌，本牌按自身消耗结算。Hologram 升级通过 `remove` 策略移除效果数组中的本牌消耗，另增加格挡。

- `dirge` 共用本次 X 投入，逐次召唤并生成对应数量的魂到抽牌堆；`rattle` 按本回合此前随从攻击次数增加段数，群攻只计一次出手，至多 20 段。`spirit-loss` 登记为失去生命类；`bind-doom` 保留最初目标并在回合末清除。`doom-all` 先给全体存活敌人施加灾厄，再即时处决灾厄不低于当前生命者，神器按减益规则阻断施加；此即时判定不受普通回合末灾厄的精英／首领半血上限约束。来源快照的 End of Days 为 29→37，本模板基础值参数化、升级 +8，不声称固定原作数值。

- `generation.js`：副 LLM 生成。`generateEntities(entities, { request, llm, signal })` → `{ ok, accepted, rejected, diagnostics, blocked }`；回复先经组装，再走 `normalizeProfile / normalizeCard / normalizeSkill / validateStarterDeck`，不合格实体最多定向修正 2 轮，已通过实体不再提交；修正耗尽时敌人回落模板敌人、主角 `blocked`、队友不参战，补技能（`skill-fill`）没有回落；取消返回 `request-stale`。回复无法解析时细分 `combat-reply-empty / combat-reply-truncated / combat-reply-not-json`，不回显回复正文。只构造请求与校验，不落账。`skillFillEntity({ profile, count, version, existing?, createdAt? })` 给已有档案（技能角色或副 LLM 生成的敌人）补恰好 `count` 个技能：回复 `{ skills: [[名, 技能模板键], …] }`，`assembleSkillFill` 追加在档案技能末尾（ID 为 `档案ID-k序号`，接着现有技能数），名称与档案技能、`input.existing`（技能角色含习得的技能）或同批重复时拒收（`skill-name-exists`）；通过结果带 `version` 与沿用的 `createdAt`，`generationWrites` 据此写同 ID 的新版本档案。技能角色队友另传 `level`（属性视图等级，D10）：伤害折算上限按 `allyFillCap`（Lv1–5 为 `allySkillDamageCap` 18、Lv6–10 为 21、Lv11 起为 25）写在 `fixed.cap`（模型不可见），Lv6 起 `input.templates` 只给 `COMPOSITE_SKILL_KEYS` 的 14 个复合技能、选其他键拒收 `invalid-template`；Lv1–5 与未传等级时请求形状与旧路径一致，敌人不受影响。技能角色档案的技能伤害校验上限为 `ALLY_SKILL_CAP_MAX`（25）；新档案、剧情习得 / 精进的技能与绝招仍按 `allySkillDamageCap`。`withCharacterLore(entities, read)` 用调用方注入的读取器给 `profile-deck / profile-skill / profile-init / trait / skill-fill` 附 `input.lore`（角色设定参考），只在读到非空内容时加字段；未注入、读取失败或为空时实体原样返回。
- `generation-retry.js`：`generateWithRetry(entities, { retryDelays, onRetry, ...generateEntities 选项 })` 在 `generateEntities` 外做有界自动重试（默认 `COMBAT_GENERATION_RETRY_DELAYS` = 2s / 6s，最多重发 2 次）。只重发上游明确拒绝、可安全补发的请求（`requestFailure.reason === 'secondary-llm-http-failed'` 且 HTTP 408 / 425 / 429 / 500 / 502 / 503）；取消与迟到、配置不完整、副 LLM 不可用、回复格式修正耗尽、发送状态未知的传输失败与 504 都不自动重发。等待中取消返回 `request-stale`；发生重试时结果附 `retries`，未重试时结果与 `generateEntities` 一致。`generateEntities` 在请求本身失败时附 `requestFailure: { reason, status? }`（不含上游正文）。`session.prepare` 经它生成缺失档案；注入 `awaitProtagonist` 时先等在途的主角卡组预生成结束再读账本，等待后开战楼变化或取消返回 `request-stale`。

  - `challenge-labels.js`：说法映射表（难关、意志、进攻、防守、挑战，状态名慌乱 / 破绽 / 煎熬，难关出招别名），只读常量与查表，不含逻辑；内部字段名不变。
  - `challenge-cards.js`：领域到模板键映射 `DOMAIN_CARDS` 与 `buildChallengeDeck({ domain, skillValue })`，固定 20 张（基础攻击 3、基础防御 3、领域牌 10、生活牌 4）；技能值 0–29 / 30–59 / 60–79 / 80 以上对应 common / uncommon / rare / epic，epic 档只有一张独门牌。只用既有模板与稀有度窗口，结果必须通过 `validateDeck`；领域不在映射表时走通用牌组。第二阶段：`otherSkills`（`{ 技能名: 值 }` 或 `{ 技能名: { value } }`）里领域之外的相关技能（`RELATED_SKILLS`，每个领域三项）值不低于 `RELATED_MIN`（50）时，最多 `RELATED_MAX`（2）项用该技能领域的「应急」牌（tempo 位，按该技能值取稀有度）顶替，第一项换掉一张进展牌、第二项换掉一张稳住牌，卡组仍是 20 张；返回值多一个 `related`（实际顶替的技能名数组）。
  - `challenge-foes.js`：难关模板登记（面试官、评委、对方、截稿、长辈、考官），只登记模板键、日常名称、出招模板键与匹配词；`pickFoe(event, domain)` 先按事件名词、再按领域、最后取兜底难关。第二阶段：每个难关登记 `harvest`（离散词 `奖金` / `经验`），`challengeHarvest(foeKey, outcome, tier)` → `{ prize: 金钱档位词 | null, card: boolean }`，只有圆满才有收获；奖金只登记在评委（比赛类），金额按 `CHALLENGE_PRIZE_BY_TIER` 查金钱表，标签与提示词不增加任何字段。
  - `challenge-setup.js`：`buildChallengeSetup({ start, state, user })`，纯函数，不读写存储；`state` 是数值侧传入的主角快照 `{ bars: { stamina, stress }, skills }`。setup 带 `challenge: { event, domain, tier, stake, foe }`，`combatId` 前缀 `ch`（`challengeCombatIdFor`）。意志 `willFor` 按体力低、压力高各降一档（阈值与数值侧一致，由测试守住）；难关厚度 `foeThickness` 由 `scaleEnemyStats` 加按托管模拟取值的校准倍率。引擎不改：新建的日常挑战与亲密对决（`intimate-setup.js`）都不写 `challenge.rounds`、不设回合上限，只按引擎胜负结算（D16）；亲密对决面板只保留随对方血条加快的心跳描边与耳语牌压暗，没有结尾吱呀与晃动窗口。`challengeResultOf(state, rounds)` 只在 `rounds` 为正整数时（带 `rounds` 的旧挑战与旧亲密对决记录，`foeThickness` 轻松 4 / 普通 5 / 艰难 6）判定，`state.turn` 超过上限仍无结局时按进展比例（不低于五成）判成败；`challengeOutcomeOf(result, willRatio, { byLimit })` 得出圆满 / 勉强 / 失败 / 放弃，达到回合上限的成功最多算勉强。建局不需要 `classRef` 或职业档案，单位直接带内联卡组与牌定义。第二、三阶段：`start.foe` / `start.foeName`（副 LLM 选的难关键与名称，键不在登记表时忽略）；`allies`（请求的协助者名）经 `validateChallengeAllies` 校验后加入 `setup.units`，返回值多一个 `allies: { accepted, rejected }`，`setup.challenge` 多 `counterpart` 与 `allies`；`state` 可带 `present`（在场人物名）与 `favors`（`{ 人物名: 好感 }`），并把 `state.skills` 作为相关技能传给 `buildChallengeDeck`。
  - `challenge-report.js`：`buildChallengeReport`，只写结局词与相对描述，不含数值，复用 `reportIdFor`；战报块为 `<igs-challenge-report id result outcome tier stake domain>`；`parseChallengeReport` 与 `challengeDirectiveOf` 供数值侧读回并合成 `challenge` 指令。`CHALLENGE_SKIP_TEXT` 为不使用卡牌结算时的提示，不触发结算。第二、三阶段：战报标记另带 `foe`、`counterpart`、`allies`（以「、」分隔）；`parseChallengeReport` 读回同名字段，`challengeDirectiveOf` 合成的指令多 `counterpart` 与 `prize`（金钱档位词或 null，由难关登记 + 结局 + 难度推出）；失败文案增加金钱与关系两类相对描述。
  - `challenge-allies.js`（第三阶段）：NPC 协助，纯函数。`eligibleChallengeAllies({ present, favors, exclude })` 列出在场且好感不低于 `CHALLENGE_ALLY_MIN_FAVOR`（26，「明确喜欢」阶段下限，即第一道关口之上；测试对齐 `FAVOR_GATES`）的人物；`validateChallengeAllies(requested, { present, favors, exclude })` → `{ accepted: [{ name, favor }], rejected: [{ name, reason }] }`，原因为 `invalid / duplicate / counterpart / not-present / favor-low / over-limit`，最多 `CHALLENGE_ALLY_MAX`（2）名，只拒收不修正；`buildChallengeAllies(accepted)` → `{ cards, units }`，每人一张专属牌（`allyExclusiveCard`，按人名从既有模板池 `ALLY_CARD_POOL` 稳定挑选，uncommon，id `ch-ally-<序号>`）并入主角卡组（20 + 人数张，不低于 `deckMin`、通过 `validateDeck`），友军为 `deck` 型单位（基础牌加两张专属牌，id `ally1` / `ally2`），由引擎自动回合按 `chooseAllyPlay` 出牌。
  - `challenge-foe-pick.js`（第二阶段）：`chooseChallengeFoe({ event, domain, request, llm, signal, context, retryDelays })` → `{ foe, name, source: 'llm' | 'local', reason? }`。经 `generation.js` 的 `challengeFoeEntity`（kind `challenge-foe`，input `{ event, domain, foes: [{ key, name, hints }] }`，回复 `{ foe, name }`）请求副 LLM，`generation-assembly.js` 的 `assembleChallengeFoe` 只收登记过的难关键与 1–20 字名称，非法即拒收并带错误重问（`generateEntities` 现有修正轮数），仍不合格或副 LLM 不可用、请求失败时退回本地 `pickFoe`（拒收记录的 `fallback` 为 `{ kind: 'local-foe', foe }`）。
  - `challenge-reward.js`（第三阶段）：`planChallengeReward({ combatId, outcome, tier, foe, domain })` → `{ ok, seed, slot: { rarity, cost }, card }` 或 `{ ok: false, reason }`。只有圆满且难关登记了「经验」才出牌；稀有度与费用取 `planRewardSlots` 的首个卡牌槽（稀有度封顶 rare、费用 1–2），模板键按种子从领域模板键里稳定挑选，求不出时顺延；只出数据，不写账本，落到卡库由接线层决定。
  - `challenge-history.js`（第三阶段）：`deriveChallengeHistory(messages)`，messages 为 `{ floor?, text }` 或字符串数组，只读推导，不新增账本类型、不存档；`parseChallengeReport` 读战报楼，同一战报编号只记一次，返回 `{ entries: [{ floor, event, reportId, result, outcome, tier, stake, domain, foe, counterpart, allies }], stats: { total, wins, losses, escapes, byOutcome, byDomain, bestStreak, currentStreak }, achievements: [{ id, name, floor }] }`；成就 id 见 `CHALLENGE_ACHIEVEMENTS`（初战告捷、圆满完成、迎难而上、连战连捷、并肩同行、百炼成钢），floor 为首次达成的楼层。
  - 数值结算（`scene/stats/stat-challenge.js`，第二阶段）：金钱代价按聊天货币配置的难度档查四档价格（少量 / 普通 / 昂贵），放弃减半，不超过剧情货币实余额的 `DEFEAT_MONEY_LOSS`（两成），经 `ctx.currency` 结算物品表增量，不扣积分。纯结算调用未传货币上下文时保留旧合并余额与 `bars.money` 路径，生产货币未就绪时跳过并诊断；关系代价走 `applyDim(对方, '好感', -n)`（n 为一 / 二 / 三，单楼不超过 `FLOOR_GAIN_MAX`，放弃减半），对方不在 `state.characters` 或不在 `ctx.present` 时降级为压力并记 `challenge-stake-degraded`；`stat-favor.js` 的 `baseDelta` 接受好感的整数增量（只服务这条路径）。负向扣分不经过 `gateCap`，不会绕过关口，已解锁关口记录保留。胜利：圆满且指令带 `prize` 时发一次剧情货币收入；关系类圆满经 `applyKeyEvent('和解')` 突破关口，不直接加数字。

## 约束

- 日常局不写伤势、不写战斗账本，不产出战利品、翻牌与成长标签；`setup.challenge` 存在时 `session.prepare` 不调用档案生成。会话接线：`session.js` 的 `locateCombatStart(chat, id, filter, kinds)` 按对决类型认战斗或挑战标签（挑战 `combatId` 前缀 `ch`，会话带 `kind: 'challenge'`）；挑战备战只调副 LLM 选难关（失败退回本地），不读账本；`autoPlay` / `abandon` / `pickChallengeAllies` 为挑战专用入口；结束时不翻牌、不写伤势与物品消耗、不扫描战斗账本；圆满且难关登记了经验时战报发出后写一条挂在战报楼上的 `learn`（`ledger.js` 的 `CHALLENGE_REWARD_TAG_HASH`）。`combat-services.js` 的 `kinds()` 把对决类型传给会话，仅日常挑战时不预生成主角卡组、不接管物品表、不自动成长；`challengePromptQuota` 给提示词与入口做额度门禁，`challengeHistory` 只读聊天里的战报。
- schema 校验只拒收不修正：未知字段、越界数值、超预算、未知效果一律返回 `{ ok: false, errors: [{ path, reason, detail? }] }`。可选字段只在缺省时取默认值。
- 组装层只对模型给出的数值（费用、HP、每级 HP、列表长度、名称长度）夹回范围并记 `combat-value-clamped`；模板键、原型、必填被动等结构错误仍拒收并定向修正。组装产物必须再过 schema，组装不得绕过校验。
- 副 LLM 不写效果原语：只从模板目录选键，效果由模板生成；旧档案（完整效果结构）照常按 schema 读取。
- 档案与日志带 schema 版本 `v`；不支持的版本拒收，不就地升级。
- 同一职业以已登记的 `class` 档案为准；`deck-character` 通过 `classRef` 引用职业，只持有个人部分。
- 起始卡组固定为 20 张，且同名卡不超过 3 张。v3–v5 档案：基础攻击 3、基础防御 3、职业卡 10、个人卡 4（`starterDeckShape`）。规则 v6 档案（起始卡组含本职业固定卡 ID，由 `validateStarterDeck` 识别）：本职业固定卡普通 / 罕见 7 种、份数 3/3/3/3/2/2/2，其中攻击、技能各至少 3 种，个人牌 1 种 ×2，不含基础牌与其他来源（`starter-shape` / `starter-rarity`）。目录经 `buildCardCatalog` 与 `rebuild` 只补起始卡组里出现的固定卡 ID；已存档的旧起始卡组不重算。
- 装备与道具（v2 阶段 3）：账本类型 `equip`（`{ gearId, name, slot, passive, description }`，带稀有度的装备另有 `rarity`（五档池稀有度）与 `bonus: { ability, amount 1–5 }`、可以没有 `passive`；不带 `rarity` 的旧条目必须带被动；同部位后装备顶替、旧装备留在背包）、`unequip`（`{ gearId }`，扫描时直接落账，未持有记 `combat-gear-missing`）、`item`（`{ itemId, name, count 1–3, effects, description }`，同名累加）、`consume`（`{ itemId, count, reportId }`，锚定战报用户楼、`tagHash = CONSUME_TAG_HASH`、不核对标签，超余量整条拒收 `combat-item-insufficient`）；`gearIdFor` / `itemIdFor` 由名称（NFKC、去空白、小写）确定性推导。角色视图带 `gear: { slots, bag }` 与 `items`（只列余量 > 0）；装着的装备 `bonus` 并入属性视图的调整项（与其他调整同受属性上限约束），检定、卡牌属性换算与开战快照都读这里，卸下即不计入。equip / item 标签进待生成队列，`growthEntity` 给出 `equip-to-passive` / `item-to-consumable` 实体（模型只回 `{ template }`：被动模板键 / 道具模板键 `ITEM_TEMPLATES`），名称、部位、数量与 ID 由程序给定，组装后过 `normalizeLedgerEntry` 直接成为 equip / item 条目；宝物被动经 `gearPassiveFromTemplate` 按 rare / common 求解中心之比向上取整加强。道具模板含新效果 `cleanse`（移除承受方虚弱、易伤、中毒、禁抽）。正文获得物带稀有度（D6–D9，标签末栏）时：`input.rarity` 只在标签写了稀有度时出现，候选模板 `input.templates` 由 `acquire-candidates.js` 的 `templateCandidates` 筛出 3–5 个（按名称与简述和模板说明的字面重合排序，不足按种子补足），模型只能从候选里选；装备回 `{ ability, template? }`，加成按 `GEAR_BONUS_BY_RARITY`（+1…+5），被动按 `gearHasPassive`（装备 ID 种子，普通 / 罕见 0、稀有 30%、史诗 60%、神话 100%）抽定，抽中时候选为按该稀有度加强后不超 `allySkillDamageCap` 的被动、强度取 `passiveAtRarity`，宝物不再另加强；道具数值按 `itemAtRarity` 以该稀有度与 common 求解中心之比放大（层数 ≤10、治疗 ≤60、能量 ≤3、抽牌 ≤5、其他 ≤99，说明数字同步）；卡组角色学会的卡牌取标签稀有度，候选为该稀有度下有解的卡牌模板并附 `input.templateVars`，模型可回 `values`，经 `cardFromValues` 按变量范围与费用 × 稀有度窗口校验（`values-length` / `values-out-of-range` / `values-out-of-window`），修正轮次用尽时去掉 `values` 改用程序求解并记 `combat-values-solved`。不带稀有度时请求、组装与载荷与旧路径一致；技能角色学技能不带稀有度。
- 成长日志除 `profile` 与 `revoke` 外必须带锚点 `{ messageId, swipeId, tagHash, occurrence }`；条目 ID 由 `ledgerEntryId` 确定性推导。
- 胜利奖励 offer（v3 §5.1，第 11 步）：`rewards.js` 的 `planRewardSlots({ combatId, tier, enemyTiers, character, links })` 按遭遇档位定 EXP（与战报同口径）、3 槽（再翻 4 槽）及每槽类别、稀有度、费用 / 部位 / 数量。类别只有杂物（keepsake，只有名称与来历，也带稀有度供翻牌爆光）、卡牌、装备（武器 / 防具 / 饰品，及稀有以上的宝物部位）与一次性道具，不出属性点、卡牌升级与人物特性；基础类别仍按杂兵 85% 杂物、精英 / 首领首槽保底非杂物且其余 80% 杂物规划；随后用独立种子仅把部分杂物提升为卡牌，使卡组角色普通 3 槽盲翻一张的卡牌率达到杂兵 30%、精英 40%、首领 50%，主套与备用套同口径。原保底槽、装备和道具份额不变，首领保底槽史诗以上、杂物稀有度另用更高的权重；同一 combatId 与角色重算一致，技能角色不出卡牌。`generation.js` 的 `rewardEntity` 给出 `battle-reward` 实体：模型只见类别、稀有度与命名线索，回 `{ slots: [[名称, 模板键, 来历 ≤30 字], …], reserve: […] }`；`reserve` 是翻牌花积分重抽时换上的备用套，与主套同规则与槽位数、种子派生（`${seed}|reserve`），同一实体一次生成，两套同成同败；`generation-assembly.js` 的 `assembleReward` 组装后成为日志表 `offer` 条目（载荷 `{ combatId, tier, exp, reveal, slots, reserve? }`，槽位按类别白名单校验，`reserve` 与 `slots` 等长；旧条目没有 `reserve`，不可重抽）。offer 锚定开战楼的开战标签锚点、不核对标签，开战楼换 swipe 或删楼即作废；`effectiveState().offers` 按 combatId 归并，同场先生效的为准，后到的记 `combat-offer-duplicate`。`session.prepare` 首次准备且日志表没有本场 offer 时与缺档案实体同批请求；已有 offer 或已准备过的场次不自动请求。奖励失败不阻断开战，会话带 `reward: { status: 'ready' | 'pending' | 'failed', exp, slots, reason? }`，`retryReward()` 只重新请求奖励，写入并读回后更新大厅。offer 只存日志表，不写开战楼聊天记录（助手决定 2b）。

- 规则 v6 奖励与卡组（G3）：`session.js` 的 `planReward` 在本场 setup `rulesVersion >= 6` 时给 `rewardEntity` / `planRewardSlots` 传 `candidates: true`，卡组角色的卡牌槽是程序预定的一张牌（`REWARD_CARD_CHOICES` = 1）：稀有及以下的槽以 `REWARD_RANDOM_CARD_SHARE` 1/3 的概率出本职业随机卡（槽位带 `fixedIds: []` 与 `randomAt: 0`），否则出一张本职业固定卡（槽位带 `fixedIds`（1 张），不带 `randomAt`）；史诗及以上（固定池封顶稀有）出随机卡。固定候选取本职业固定池（按槽位稀有度、史诗及以上按稀有，跳过已达同名上限的牌，不够逐档降低，槽位稀有度随这张牌），固定卡以 `REWARD_GENERAL_SHARE` 0.25 的概率换成无色固定卡（无色池从罕见起算；积分抽卡不出无色）；固定池凑不齐时改出随机卡。「多一个可选项」（遗物或特质 `bonus.choices`）时为固定卡与随机卡各一张，按 `randomAt` 排成二选一。预定固定卡槽给模型只看 `fixedCard` 牌名，模型名称与模板键填 null、只写来历；含随机卡的槽照旧只收本职业允许的模板。`assembleReward` 产出 `choices`（新 offer 1–2 张；旧 offer 3–4 张三选一照旧校验与重放）。结算页单张预定牌给「接受 / 放弃」，多张时点选其一或跳过；翻牌 `pick.card` 为候选序号或 `'skip'`（`pickCardChoice`，发送前可改选），不再触发任何抽卡，`flipView` 对候选槽给 `needCard / card`，未定时 `resolveLoot` 拒发 `combat-flip-card-required`、界面不出发送按钮。`attachLoot` 对候选槽写第 5 字段 `[igs-combat:loot|角色|战报ID|槽位|main 或 reserve|序号或 skip]`，账本 `loot` 载荷带 `pick`（候选槽缺 `pick` 记 `combat-loot-pick-missing`）；固定卡入目录后直接 `addCard`，出单后才达同名上限记 `combat-loot-copy-limit`，`skip` 不入账。不带 `choices` 的旧 offer / loot 与 4 字段旧标签重放不变。自由组卡取消：`ledger.saveDeck` 只在 `deckNeedsAdjust` 时写 `deck` 记录，否则 `combat-deck-locked`，面板同样只在需调整时出加入 / 移出 / 保存；已有 `deck` 记录照旧重放。删卡：本场正好满 5 场普通胜利时，结算页给主角一次删牌机会（`flipView` 带 `purge: { battle, cost, available, reason?, cards, pick? }` 与 `needPurge`；`session.pickPurge(副本ID | 'skip')` 选牌或不删，发送前可改选，未选前不出发送战报），选牌后 `report.js` 的 `attachPurge` 在战报块之后写 `[igs-combat:purge|角色|战报ID|副本ID]`，不删不写标签；账本扫描按 `purgeChance(view, reportId)`（战报未计入胜场时按下一场算，已计入时按当时场次，不是最近一场即 `combat-purge-expired`）核对后生成日志类型 `purge`（`{ copyId, cost, battle, reportId }`，只认胜利战报楼里本场战报，否则 `purge-report-invalid`），同楼重复扫描不重复写入，只主角；普通战斗胜场由重放统计——只认战报用户楼里 `reason` 为 `战斗:<本楼战报ID>` 的胜利经验，同一战报计一次（剧情经验、日常挑战、亲密对决不计）；`purgeOpportunity(state)` 在胜场为 `PURGE_EVERY` 5 的倍数、该档未用过、卡组多于 `deckMin` 时可删，再赢一场即过期作废，费用 `purgeCost(已删次数)` = 75 + 50 × 已删次数；角色视图有胜场或删过牌时带 `purge: { battle, cost, available, next, reason? }`，否则不写字段。

- 劣等杂物的 `junk` 由程序装配并随 offer、loot、收藏和物品装配定义保存；单件售价为同身份普通售价的 1/4、最低 1。主角物品表同名且品质不同时另建带「（劣等）」或「（普通）」后缀的库存名，同品质继续叠数量，已丢失定义同样参与品质判断；未注入物品表的收藏仍按 loot ID 区分。背包详情在品质旁显示单件回收价值（如「劣等 · 2 积分」）；原位「回收」按钮通过 `createIgsModal.quantity` 打开独立确认弹窗，数量默认 1，实时显示「总计 X 积分」。只有弹窗中「确认」才执行回收；取消、Esc、关闭面板、重读或切换物品均取消待确认操作，重复确认只提交一条批量记录。
- 数量回收由 `sellHeroItem(kind, id, count = 1)` 经 `sellKeepsake(id, count)` / `sellGear(id, count)` 写入 `sell.payload.count`。数量须为正安全整数且不超过实际可回收库存，非法值返回 `combat-sell-count-invalid`，超量返回 `combat-sell-count-insufficient`；前端输入限制不能替代账本构造及库存写口校验。总积分为 `sellPrice(rarity, id, { junk }) * count`，新物品表记录保留 `rarity`、`count` 与劣等标记供重放，gearId / lootId 携带 junk 拒收 `sell-junk-target-invalid`。旧记录缺 `count` 按 1 重放且不补写历史字段；未注入物品表的旧 gearId / lootId 仍只支持单件。部分回收只扣数量并保留定义；实际持有数量归零时删除物品表行和装配定义。装备上限只含背包余量，不含穿戴件；回收全部备用件后若仍穿戴一件，物品行及定义保留。
- 回收写入沿用先记账、再扣物品数量、最后清理定义的顺序；回收的库存计划拒绝或试算失败以失败回执返回，不作为成功跳过。定义清理失败不得回报回收成功：仅对本次目标按写前快照尝试恢复原数量、定义与穿戴状态，再撤销本次积分记录。恢复仅接受原数量或本次扣减后的预期数量，遇到其他状态停止补偿。`stock[].restored` / `revoked` 分别记录补偿与撤销结果；库存恢复失败返回 `combat-sell-rollback-failed`，账本撤销失败返回 `combat-stock-revoke-failed`。这是跨表补偿而非原子事务，失败需先核对库存与积分，不能自动重试或当作成功。

- 胜利翻牌（v3 第 12b 步）：`flip.js` 为纯函数，不读写存储。位置按 `combatId` 与套别的种子打乱（`flipOrder`），重开一致；透视（`offer.reveal`）先亮出 1–2 张，只亮不算翻（`revealedOf`）；4 槽（再翻）时翻两张后 `chooseCard` 二选一，否则 `flipCard` 翻一张即选定；`rerollPick` 花 `REROLL_COST` 换上备用套重新翻，每场一次，旧 offer 没有备用套或领取者不是主角时 `combat-reroll-unavailable`、合并余额不足 `combat-points-insufficient`、已换过 `combat-reroll-used`；`flipView` 只给已翻开、已亮出的牌带槽位内容，选定后全部翻开。会话在胜利结束（`ended` / `send-failed`）时经 `loadFlip()` 读本场 offer 建 `session.flip`：`loading`、`none`（没有 offer，照发不带战利品）、`error`（账本读不到或进度损坏 `combat-flip-corrupt`，不能发）、`ready`；`act` 出胜负、`prepare` 与 `resume` 落到已出结果时自动读取。`flip(position) / choose(position) / reroll()` 的进度 `{ set, flipped, choice }` 先存会话存档 `record.flip`，再写开战楼聊天记录该场的 `flip` 字段（不改 `result`）；没有会话存档时写进聊天记录才推进（否则 `combat-flip-save-failed`）。几份进度不一致时取更靠后的，换设备后同样不能重翻。`finish` 与 `retrySend` 在有 offer 时必须已选定（`combat-flip-required`），经 `attachLoot` 附战利品后写待回传再发送；战利品附进战报后翻牌锁定（`combat-flip-locked`）。会话按合并余额（见「积分余额与剧情货币」条）放行重抽，账本归并不再拒收。
- 积分余额与剧情货币（规则 v6 G8）：共享积分 = 战斗账本主角 `points`（净流水，可为负）+ 旧 `bars.money` + 数据库已确认的 Origin 净流水，三份额各计一次；原存储与旧值保持不变。`effectiveState()` 主角视图 `points` 为共享余额，`effectiveState({ raw: true })` 的角色 `points` 仍为战斗净流水，独立字段 `originPoints` 为当前 Origin 路径净流水。`readSharedPoints()` 给出三份额、净流水之和 `flow` 与总额 `balance`，数值页只将 `flow` 加到旧钱包一次；积分显示与 Origin 消费不受战斗界面开关影响。Origin 购买／抽奖和战斗面板消费共用 `withPointsLock`，在锁内读取已确认记录后预检。剧情货币是物品表固定行的数量，配置存于 `chat:currency`；money 标签、速算战利品、战败、打工和挑战奖金／扣款只改变该行。纯结算未传 `ctx.currency` 时保留旧兼容语义，生产货币未就绪时跳过并诊断。随身系统积分单向兑换剧情货币、小游戏收益与额度留后续 G8 子批。
- Origin 共用积分：正文与数据块只接受积分增减，旧 `balance` 操作与正文余额事实不参与覆盖。操作差分以 `type: 'origin'` 记录追加到「IGS战斗·日志」；先在副本上试算，数据库读回确认后才发布物品、奖励、通知与状态。回放是纯计算，楼层／手动操作保存当次外部积分份额供重放，实时总余额只合并一次；折叠、memo、checkpoint、swipe、删楼与重开不回写外部钱包。原 `origin_v2` 仅在数据库无 Origin 记录时导入，旧 metadata 保留；断链、冲突和非法记录拒绝消费，不退回旧数据继续记账。失败请求不留共享 FIFO 自动补交，重试复用原意图；分段恢复只接受原意图且已存片段逐项匹配，未确认的残缺记录不能用于消费。同步提示词事件当轮注入已确认状态，操作绑定异步保存；设置页提供「重试保存」。已发给宿主的写入不能撤回，不宣称跨表事务或跨页面分布式锁。
- Origin 异步恢复：消息事件租约校验原路径前缀，允许同聊天尾部追加；失败期间暂存后续事件，确认后重新排队，同一意图的事件、通知与提交后动作只发布一次。swipe／删楼使待保存路径失效时，重试先刷新读回：未入库的旧意图不提交，已写入或匹配的缺段按实况确认，再重算并保存当前路径，不发布旧分支通知。聊天身份、数据库适配器或启用代次变化时旧请求失效。
- 战斗胜利积分（规则 v6 G5g，D-16）：账本类型 `battle-points`，载荷 `{ amount, tier, combatId, reportId }`，`tier` 取 `BATTLE_POINT_TIERS`（normal / elite / boss），`amount` 须落在 `points.js` 的 `BATTLE_POINTS_RANGE` 对应区间（普通 10–15、精英 16–22、首领 23–30），且必须等于 `battlePoints(tier, combatId)` 重算值（否则 `battle-points-mismatch`）；越界、缺 `combatId` 或金额不符均拒收。会话 `settleReport` 在普通战斗胜利（挑战与亲密对决不发，敌人撤离的胜利照发）时写一条：角色为本场 `setup.controlledId`，锚定胜利战报楼（`BATTLE_POINTS_TAG_HASH`，`occurrence: 0`），档位取本场最高敌人档位（`battleTierOf(record.tiers)`），金额由 `battlePoints(tier, combatId)` 按战斗 ID 哈希定额。重放只认胜利战报楼里同 `reportId` 的记录（否则 `battle-points-report-invalid`），楼层删除或 swipe 切换即撤销；非主角为 `combat-points-not-protagonist`。积分写进主角战斗 `points` 净流水，并入共享余额供战斗与随身系统消费，不改写 `bars.money`。
- 胜利加成（规则 v6 G5f-4c）：普通战斗的 `battle-points.amount` 保持上述基础定额；可选 `bonus: { points, hpMax, relics }` 由写入时真正持有的 `win-points` 遗物特性快照计算。固定积分相加，百分比只按基础 amount 向下取整，`hpMax` 单独累计到 `relicHpMax`、不占战斗成长上限。schema 重算数值并拒绝重复或不适用的引用，重放再核对当时是否持有（`combat-points-bonus-not-held`）；待选特性不生效，来源楼回退时累计随之撤销。弱敌战是基础金额范围的唯一例外：载荷须带 `weak: true`，amount 严格等于 `weakBattlePoints(tier, combatId)`；weak 必须与本楼战报一致，且不得带 bonus（`battle-points-weak-mismatch` / `battle-points-weak-bonus`）。
- 获得时遗物（规则 v6 G5f-4d）：`ledger.drawTrait` 保存 `relic` 引用，对获得时被动特性写入 `pickup: true`；schema 只允许值为 true 且模型为 `pickup` 的被动特性，缺字段历史记录保留原重放语义。`trait`、`trait-pick`、`trait-slot` 的真正装上转换共用 `settlePickup`，待选或丢弃不触发。同角色按遗物 ID 去重，换下再装上不重复；随机候选按卡组副本顺序，以装上记录 ID、遗物 ID 与 upgrade／inscribe／copy 用途隔离种子，不重复抽取，候选不足取现有对象。获得时生命另加到 `relicHpMax`，沿用失血量结转，回满清除伤势。升级排除专属、已升级（含旧升级张数分配）与无升级形态；刻印排除已有刻印及 `inscribable` 不适用对象：虬木锤为锋利、木札为灵巧、拳刺为动量。人偶镜从未达同名获得上限的非专属副本中复制，继承升级与刻印，不继承战斗成长；内部 `localGrowth` 只用于账本副本视图，新建 setup 时同名共享成长转入原副本 bonus，镜像独立累计成长，内部标记不写入战斗存档。装上记录失效时全部效果随重放撤销。
- 御印选定协议（G5f-4d）：获得时有可刻对象才挂 `relicInscribe: [{ relic: { relicId, model }, inscription: 'sovereign', cardType: ['attack', 'skill'], copies: [copyId] }]`，无对象则本次作废。日志类型 `relic-inscribe` 的 payload 为 `{ relicId, model, copyId, cardId, inscription }`，所有字段必填；写口 `ledger.inscribeRelic(characterId, payload)`、服务 `inscribeRelic({ relicId, model, copyId })`、宿主接口 `inscribeCombatRelic(opts)`。服务从权威视图补 cardId 和刻印，账本串行试重放复核待刻项、卡组副本、牌型与刻印适用性，拒绝重复消费；无需模型、不扣费、无跳过操作。记录挂最新操作楼的 trait 面板锚点；删除选定楼或切换 swipe 恢复待刻，装上楼失效则待刻和刻印一并撤销。界面（G5f-5，已经助手确认）在人物状态页「待刻印」区选定副本、先看刻印前后再确认，见 `app/src/visual/igs-ui/CONTRACT.md`。
- 加卡遗物（规则 v6 G5f-4e）：`addCard` 为实际新增卡组副本的统一结算点，先应用副本继承标记，再按已装上特性的 `card-added` 模型结算升级、积分与回血。新 `learn`、`reward`、`loot`、`card-pick`、`exp`（专属解锁）及人偶镜 `trait` 记录可带 `added: true`，schema 只接受 true，并拒绝非加卡奖励、skip、非复制特性等非法组合；缺字段历史记录不追溯。剧情成长、挑战经验牌与专属生成写口同步携带标记。三类蛋仅升级匹配牌型、非专属且有升级形态的副本；招财鱼符每张加 15 积分；五环剑谱按该角色持有期间实际加卡累计，每 5 张回 20 生命、不超过当前伤势上限，满血清伤势；未持有期间不累计，换下不清除已累计余数。初始卡组、整理、重建、待选、跳过及拒收不触发。计数与收益均从有效账本顺序重算，不新增持久化计数来源，重复读取不重复发放，锚点失效时自然回退。
- 奖励遗物（规则 v6 G5f-4f）：备战从已装特性提取 `flipRelics` 写入 offer，重放按持有快照校验；新 offer 的 `afterPanel` 为出单时同楼同 swipe、同角色的面板操作数量，排序在前 N 条面板操作之后、后续操作之前，缺字段旧 offer 沿用原顺序。只在请求 `effectiveState({ includePanelBoundary: true })` 时返回边界元数据。转经筒限普通档、晨星限精英档并给稀有卡槽；新增卡槽与再翻合计最多 4 槽，沿用四槽翻两张选一张的协议。奖励候选基础 3 张、最多 4 张，仅增加固定候选，随机候选仍为 1 张；`CARD_DRAW_CHOICES` 独立固定为 3，不影响积分抽卡。固定候选不足时沿用单随机卡回退，并保留遗物标记。旧毯每次增加候选，长效糖果按持有期间的新普通胜利计数，弱敌、重复战报、历史未知不推进，换下保留余数，随有效账本回退重算。

- 引擎不就地修改入参：`applyAction` 先校验，非法动作返回原 `state`、空事件和 `{ reason, detail? }`；合法动作在副本上结算。断点续战只保存 `setup`、`seed` 与动作序列，由 `replayBattle` 重建，不持久化引擎快照。

## 禁止

- 禁止在 combat 内直接访问 DOM、酒馆全局对象或 `AutoCardUpdaterAPI`。
- 禁止使用 `Math.random` 或当前时间影响战斗结算；随机性必须来自传入的种子。

## 卡组增强：卡组方向与角色素材

- `generation-materials.js` 负责 JSON 指针、候选路径、角色别称、素材结构整理与 14000 字符预算，纯函数，不访问宿主或写数据。字符串资料完整保留，结构深度与条目数限制仍生效；方向上限 1600 字符，失效路径、表消失和超预算明确拒收。

- 初次卡组、重建、AI 转职与升阶走同一素材入口；确认时重读，`materialChatId` 与当前聊天不一致就停止。已有职业直接转职不请求模型和素材。

- `ledger.drawTrait(characterId, trait, { expectedDraws })` 在串行写入前核对规划时的抽取次数，否则拒收 `combat-trait-stale`。预检参数不进入历史载荷，不在重放时重新拒收已获得的特性；早期楼层换分支时后续有效条目仍保留。服务层同聊天同一生命周期只允许一次抽取生成在途，重复调用返回 `combat-trait-busy`。此保护覆盖本机调用与写入前检查，不承诺数据库提供跨设备事务。
