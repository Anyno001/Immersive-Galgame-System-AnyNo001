# 数值系统计划（好感 / 技能 / 生活条 / 检定）

状态：2026-10-22 讨论定稿 v7（对齐基准恋爱 gal 模板：好感 -100～100、6 基础属性 10–90、IGS 适配版模板）。P1–P5 已在内测版本地落地并接入运行时（`app/src/scene/stats/`、`app/src/core/stats-runtime.js`、`app/src/data/shujuku/stats-push.js`，未提交）；真机项未验证，明细与偏离见 §11 落地记录。适用于内测版。

## 0. 目标与原则

让游玩方式更接近养成类 galgame：角色有好感和关系阶段，主角有生活技能、体力、金钱和压力，关键行动通过掷骰决定成败。

核心原则：**AI 只报告发生了什么，加减多少由脚本决定。**

- 所有骰子由 IGS 脚本掷出，随机源为 `crypto.getRandomValues`。AI 看不到也无法影响掷骰过程。
- AI 输出的只有离散标签（用哪个技能、难度档、好感反应方向、体力事件档），任何数字都不由 AI 给出。
- 数值真值存在 IGS 内部，单向推送给 shujuku 和 AcuDice；表格里的改动不会读回，下一次推送时被覆盖。
- **独立启用，不依赖表格**：设置器侧边栏新增“数值系统”分类，顶部是总开关，默认关闭。关闭时 IGS 不注入、不解析、不结算，与现状完全一致。推送到表格只是该分类里的一个子开关，默认关闭；不装表格插件也能完整使用。

## 3. 数据模型

```
statsState = {
  version: 1,
  enabled: true,
  ruleset: 'd100',
  clock: { day: 3, lastHour: 23 },            // 第几天，最后一次识别到的钟点
  protagonist: {
    skills:  { 烹饪: { value: 20, marked: false }, 学习: {...}, ... },
    bars:    { stamina: 72, money: 340, stress: 25 },   // stamina/stress 0–100，money 不设上限
  },
  characters: {
    '<角色主名>': {
      dims:   { 好感: 34, 信任: 20, 了解: 15, 欲望: 5 },   // -100～100；欲望只在 NSFW 开启时启用；维度名可按卡改
      stage:  'friend',
      daily:  { day: 3, gained: { 好感: 5 } },    // 每日上限计数
      recent: ['送礼:花', '夸奖'],                 // 重复递减用
      lastSeenDay: 3,
      unlocked: ['date-1'],                        // 已通过的关键事件
    },
  },
  log: [ { floor, source: 'roll'|'tag'|'manual'|'table'|'daily', target, key, from, to, note } ],
}
```

- **按楼快照**：每次结算前，把结算前状态存进该楼层，键为 `chatId|messageId|swipeId`（与 `media/illustration-store.js` 的 `floorKeyOf` 同格式）。**必须按 swipe 区分**：
  - 重 roll（新建 swipe）：从本楼结算前快照出发，重新掷骰、重新结算，结果存进新 swipe。
  - 左右切换到已有的 swipe：读取那个 swipe 已存的结果，**不重掷**。只有生成新 swipe 时才重掷。
  - 删楼：回到上一楼的快照。
  - 切换分支：读取当前楼层、当前 swipe 的快照。
- **存放位置**：存档必须跟着聊天文件走（换设备、导出聊天后不能丢），因此不能只存在 IndexedDB。优先写进聊天本身（楼层的 `extra` 或聊天元数据）；实施前先核实 TavernHelper / SillyTavern 的写入接口与保存时机，IndexedDB 只作缓存。
- **配置与状态分开**：技能清单、维度名、阶段文案、规则表属于“卡配置”，随预设导出；数值本身属于“存档”，随聊天走。
- 遵守设置器卡顿修复时定下的规矩：配置共享只读、写时浅拷，不原地修改。

## 4. 检定流程

### 4.1 先掷后写（玩家主动行动）

1. 玩家输入或选择一个行动，例如“我给她做一顿寿司”。
2. **判断技能**：先用本地关键词表匹配（做饭、料理 → 烹饪）。匹配不上时，调用辅助模型（已有 secondary LLM 通道），让它从当前技能清单里选一个，同时选难度档（普通 / 困难 / 极难 / 无需检定）。辅助模型只能从给定选项里选，返回的内容不在选项中就作废，退回“无需检定”。
3. 脚本掷 d100，计入体力劣势、压力修正和情境奖惩骰，得出成功等级。
4. 结果**通过提示词注入**交给本次生成（depth 0），AI 按结果来写；不写进玩家楼正文。重 roll 时重新掷骰、重新注入，满足“重 roll 也重掷”。最终生效的结果记在 AI 楼的数值快照里。
   - 现有 `formatCheckMessage` 是把结果写进玩家输入，那样重 roll 时无法重掷。数值系统开启时改走注入；未开启时保留现有行为。
5. 播放检定骰演出；成功的话给对应技能打上成长勾。

玩家也可以在设置中关闭“自动判断”，改为每次手动选择技能，或者直接跳过检定。

**检定建议表的选项**：玩家点击检定建议表的选项时，直接用该行的 `骰子命令`（AI 选的属性和难度，属于允许 AI 判断的范围），跳过本地匹配；命令中的属性值由 IGS 属性源提供，命令里写的属性 IGS 没有时退回最接近的基础属性并记诊断。`必成` / `必败` / `无` 照现有 `dice-check` 处理。

### 4.1A 技能匹配词系统

本地匹配是主力，辅助模型只是兜底，所以词系统要做得精细：

- **词条结构**：每个技能有一组词条，每条由“动作词 + 可选对象词”组成，例如 烹饪 = {做/煮/炒/烤/煎/炖/下厨/掌勺} × {饭/菜/汤/面/甜点/寿司/便当…}，另有独立成立的词（下厨、料理、烘焙）。动作词与对象词都要命中才算组合命中，避免“做作业”被判成烹饪。
- **排除规则**，以下情况不触发检定：
  - 否定与假设：不、没、别、不想、如果、要是、假如、打算……
  - 引号内的台词（“我会做饭哦”是说话，不是行动）；
  - 回忆、梦境；
  - 只是旁观他人（“看她做饭”）。
- **冲突裁决**：一句话命中多个技能时，取命中最长、离句首主语最近的那个；仍然并列时交给辅助模型裁决。
- **难度词**：精致、高难度、第一次、赶时间 → 困难；传说级、不可能、极限 → 极难；随便、简单 → 普通。
- **世界观词表**：通用词表 + 世界观扩展词表（魔法：施法/念咒/熬魔药；修仙：运功/炼丹/御剑……），与技能清单的扩展同步启用。
- **用户词表**：面板中可以给任一技能增删词条；卡自定义的技能必须至少有一个词条，否则只能走辅助模型。
- **学习缓存**：辅助模型判断过的“动作词 → 技能”会记进本卡的学习表，下次直接本地命中，不再调用模型。学习表可在面板中查看和删除。
- **测试语料**：建一份不少于 200 句的正例与反例语料（含否定、引号、旁观、多技能冲突），作为单测的验收集。

**检定频率**：只有存在风险、对手或挑战时才掷骰，闲聊、日常移动默认“无需检定”。每楼最多一次先掷后写。

**情境奖惩骰**：攻略对象在场协助、持有合适道具、熟悉的环境给奖励骰；受伤、高压力、恶劣环境给惩罚骰。复用现有奖惩骰（最多 2 颗）。

**NPC 与敌人数值**：对抗检定需要对方数值，AI 只给档位，由脚本换算：
- **优先读表格**：对手是已建档角色时，读该角色在重要角色表 `基础属性 / 特有属性` 里的对应数值。IGS 第一次读到就记进存档并**冻结**，之后 AI 填表再改也不采纳（玩家可在面板里手改）。
- 表格里没有该角色或该属性时，才按档位换算。NPC 能力档：普通人 45 / 擅长 60 / 专家 75 / 大师 88（落在 10–90 内）；
- 敌人档：杂兵 / 精英 / 头目，对应的能力值和伤害档见 §6A。
- 已登记的攻略对象可以在面板里设置固定的擅长项，例如“她的厨艺固定为 70”。

### 4.2 事后结算（AI 正文中的事件）

AI 在正文中输出数值标签，脚本解析后结算。标签不显示在阅读器中。

```
[igs-stat:favor|角色名|开心]        好感方向：开心 / 感动 / 心动 / 平淡 / 失望 / 反感 / 吃醋 / 受伤
[igs-stat:trust|角色名|上升]        其它维度：上升 / 下降
[igs-stat:stamina|重]               体力事件：轻 / 中 / 重 / 熬夜 / 受伤 / 进食 / 小憩
[igs-stat:money|花费|普通]           金钱：收入或花费，档位为 少量 / 普通 / 昂贵 / 巨额
[igs-stat:stress|上升]              压力：上升 / 下降
[igs-stat:sleep]                    入睡（触发日结算）
[igs-stat:event|角色名|约会]          关键事件（用于突破阶段）
[igs-stat:battle|精英|2]             遭遇战斗：敌人档位与数量（见 §6A）
[igs-stat:hurt|轻伤]                 伤势：轻伤 / 重伤（非战斗受伤）
[igs-stat:gift|角色名|甜点]           送礼：礼物类别，与角色喜好表匹配
[igs-stat:work|打工]                 打工/工作：触发一次技能检定，按结果给收入档
[igs-stat:skip|7天]                  时间跳跃
```

- 金钱档位按世界观换算成具体数额：现代用元，古风用文，魔法用金币。换算表放在卡配置里。
- 一楼之内，同一角色的同一维度只结算一次（取最强的那个方向），防止 AI 连打标签刷分。
- 标签在阅读器、语音朗读、漫画泡、弹幕取词中一律剔除。
- **漏打兜底**：AI 没打体力标签时，按正文关键词做最小兜底（吃饭 → 进食，睡下 → 入睡）。只兜底体力和入睡，好感不兜底。
- **回忆与梦境**：处于回忆、梦境、闪回段落中的“第二天”等字样不触发跨天，标签照常结算。

## 5. 好感系统

### 5.1 维度与阶段

- 默认四个维度，范围都是 -100～100：**好感**（喜恶与亲疏）、**信任**（是否相信对方、愿意暴露弱点）、**了解**（对对方的认知深度，负数表示认知偏差）、**欲望**（亲密吸引，只在 NSFW 开启时启用，基准模板中没有此列，不推送）。维度名可以按卡修改。
- 阶段由“好感”决定，默认九档，与基准模板的行为描述一致：仇恨 -100～-76 / 强烈反感 -75～-51 / 厌烦排斥 -50～-26 / 淡淡不喜 -25～-1 / 无感 0 / 初步好感 1～25 / 明确喜欢 26～50 / 强烈在意 51～75 / 深爱 76～100。信任、了解也各有九档描述（取自基准模板），用于维度组合描述。
- 每个阶段一到两句约束文案，注入提示词，写的是“这个阶段她会做什么、不会做什么”。默认文案从基准模板的分档描述压缩而来，可在设置中修改。
- 维度组合能产生补充描述：比如好感高、信任低时写成“喜欢但仍有防备”。组合规则做成一张小表，不穷举。

### 5.2 防止好感膨胀（四层）

1. **表格不是写入口**：AI 填表改了好感也不会被读回，下一次推送时被 IGS 真值覆盖（见 §8）。数值只能在 IGS 面板里修改。
2. **只给方向，脚本查表**：每个方向标签对应一个固定的基础增量（开心 +2、感动 +3、心动 +3、平淡 0、失望 −2、反感 −4、受伤 −6、吃醋 −3）。单楼单维度最多 +3，每天每维度最多 +8；扣分不设上限。
3. **越高越难涨**：遇到正向标签时掷 d100，点数大于当前值（负值按 0 算）才按增量加分，否则只加 1。负向标签直接扣分。信任按基准模板的说法“建立缓慢、崩塌迅速”：正向增量减半，负向增量加倍。
4. **跨阶段要靠关键事件**：正向区间有三道关口，25→26、50→51、75→76。日常积累在关口处封顶（比如“初步好感”最多到 25）。负向区间往回涨不设关口。只有通过一次关键事件（约会、告白、共患难，由 `event` 标签或先掷后写触发）的检定，才能升入下一阶段。

辅助手段：
- **重复递减**：`recent` 里出现过同类行为（同一礼物、同一夸法），收益逐次减半。
- **叙事约束**：注入“当前阶段不会做的事”，防止 AI 在叙事上越级。

**突破提示**：好感到达阶段上限后，提示词提醒 AI 在合适时机给出一次关键事件的机会（邀约、独处、危机），状态栏上该角色显示“可以更进一步”的小标记。玩家也可以主动发起（先掷后写，用魅力或交涉检定）。

### 5.1A 角色个性

每个**重要角色**有一张个性卡，可在面板中编辑：
- **喜好 / 雷点**：礼物类别和行为类别，例如喜欢甜点、讨厌烟味。送礼命中喜好时增量翻倍，踩中雷点按“反感”结算。
- **性格系数**：慢热 ×0.5 / 普通 ×1 / 外向 ×1.5，作用于正向增量。
- **初始关系**：青梅竹马、同事、陌生人等，决定初始阶段和初始维度值。

**按需生成，不在登场时生成**：新登记的角色先用默认值（普通性格、无喜好雷点、好感信任了解均为 0）。只有当玩家打开该角色的卡，或第一次对 TA 送礼时，才按角色名读取世界书条目和角色卡（复用立绘写词读取世界书人设的路径），由辅助模型在后台生成草稿，标为“AI 草稿”，可随时修改。世界书里查不到时保持默认值，不追问玩家。

### 5.1B 谁会被记录（防 NPC 泛滥）

注意：IGS 不会把新角色自动写进角色名单。自动生成的立绘先进“待确认”区，需要用户手动归入（`scene/asset-match.js` `bindGeneratedSprite`）。所以“已登记”不能作为唯一来源，否则不手动归入的用户一个重要角色都没有。

- **路人**：未登记角色的好感标签直接忽略，不存数值、不进提示词、不提示。
- **重要角色**：默认**自动登记**，无需确认。角色在正文中出现（作为说话人或标签对象）时，满足任一条件即登记：
  1. 已在 IGS 角色名单中（用户区或生成区，含别名，用 `resolveCharacterKey` 解析）；
  2. 是当前角色卡的名字，或群聊成员；
  2A. 表格重要角色表里 `角色类型` 为“恋爱对象”的角色（基准模板有此列）。这类角色直接作为攻略对象；“家人”“配角”等类型登记为重要角色但默认不显示欲望维度；
  3. 世界书（角色卡绑定的和全局启用的）中有以该名字或别名为关键词的条目。路人通常没有世界书条目，这是区分路人与正式角色的主要依据；
  4. 兜底：累计 3 楼收到好感标签，且跨越至少 2 天。
- 判定只在角色**第一次**以未登记身份出现时做一次，结果缓存在存档中，不在每次渲染时重复查询世界书。
- **纠错**：状态栏上可以“移出攻略”（移出后进入忽略名单，不再自动登记）或“加入攻略”。
- **设置**：登记方式分“自动”（默认）和“仅手动”两档。
- 提示词只放在场的重要角色（见 Q4）。

### 5.3 下降与吃醋

- **冷却**：超过 N 天（默认 3 天）没有互动，正值好感每天 −1，降到当前阶段下限为止，不会因为冷落而掉阶段；负值不随时间变化。
- **吃醋**：`吃醋` 标签除了扣分，还会把信息传给修罗场演出。只有当过对象的角色才算，与现有修罗场规则一致。

### 5.4 亲密门槛

- NSFW 剧情需要好感达到某个阶段（默认“强烈在意”，即 51 以上）、信任达到某个值（默认 26 以上），同时欲望达到某个值。未达到时，提示词要求角色拒绝或回避。
- 设置中可以关闭门槛。

## 6. 技能与成长

- **基础属性**（固定 6 项，所有角色都有）：健康、力量、敏捷、理智、观察、魅力。含义沿用基准模板的说明（理智指日常关系里的冷静与抗压，不是 SAN）。
- **特有属性**（即生活技能）：默认提供烹饪、家务、学习、运动、艺术、话术、照顾、应变等，用户可增删；恋爱对象可有专属特有属性（基准模板举例：雨天照顾、冷场补救、夜宵投喂）。
- **范围**：10–90。普通人 40–65，短板 10–35，优势 66–80，顶尖 81–90。成长上限 90。
- **推送格式**：与基准模板和 AcuDice 一致，`健康:60；力量:45；敏捷:55；理智:50；观察:62；魅力:58`（全角分号），特有属性 `属性名:数值；`。
- **世界观扩展**：魔法（咒语、魔药、飞行）、修仙（修为、炼丹、御剑）、恐怖（侦查、理智）等，跟随现有世界观识别结果自动追加。
- **卡自定义**：可在面板中增删技能、改名、调整初始值。
- **建卡**：开局按点数池分配。基础属性 6 项默认各 40，另有 60 点自由分配（单项上限 80，下限 10）；特有属性另给 3 项 × 50 起步，可调。也可以用卡里预设的初始值，或从表格一次性导入。
- **成长**：检定成功时给技能打勾。日结算时，对每个打了勾的技能掷 d100，点数大于当前值则 +1d10（不超过 90），然后清除勾。技能值越高越难涨。
- **等级型属性**：修仙境界、游戏等级这类不是 10–90 百分制的属性。它们用“阶 + 进度”记录，进度满了需要一次突破检定才能升阶，失败则受伤或倒退一部分进度。由世界观扩展开启。
- **战斗技能**：格斗、射击、闪避、法术（按世界观换名），与生活技能共用同一套检定和成长规则。

## 6A. 战斗（整场速算）

日常向游戏里，战斗是日常的一部分，不能拖慢节奏。

- **触发**：AI 打出 `battle` 标签（敌人档位与数量），或者玩家主动发起。
- **结算**：一场战斗按敌人档位掷 1–3 次对抗（杂兵 1 次，精英 2 次，头目 3 次）。对抗项从主角的战斗技能里选最高的一项，闪避单独掷一次。
- **结果**：大胜 / 胜 / 险胜 / 败，四档。脚本根据结果计算生命、体力损耗和战利品档（金钱档），结果注入提示词，AI 按结果写出整场战斗。
- **敌人档**：

| 档 | 能力值 | 败北伤害 | 战利品 |
|---|---|---|---|
| 杂兵 | 35 | 轻伤 | 少量 |
| 精英 | 55 | 中伤 | 普通 |
| 头目 | 75 | 重伤 | 昂贵 |

  数量每多一个，给主角一颗惩罚骰（最多 2 颗）。
- **队友**：攻略对象参战时，给主角一颗奖励骰。并肩作战取胜，可以算作“共患难”关键事件，用于突破好感阶段（受每日上限约束）。队友不单独建卡。
- **战败**：不会死亡。生命归零时昏迷、被救或被俘，丢失一部分金钱；提示词要求 AI 写出对应情节。
- **演出**：结算结果交给现有的战斗演出（遭遇卡、逐招出手、结算卡、战斗名牌）。逐招动作由 AI 正文决定，胜负和伤势由脚本决定。

## 7. 生活条与时间

| 生活条 | 规则 |
|---|---|
| 生命 0–100 | 与体力分开，管受伤。轻伤 −15、中伤 −30、重伤 −50。低于 50 记为“轻伤”状态，低于 20 记为“重伤”状态（检定惩罚骰 1 颗，并且无法参加重体力行动）。每天自然恢复 +15，就医或用药按档位加快。归零时昏迷，不会死亡 |
| 体力 0–100 | 管疲劳。体力事件按档扣减（轻 −5、中 −15、重 −30、熬夜 −20；进食 +10、小憩 +20）。低于 30 时检定劣势（掷两次取较差的结果，对应已有的惩罚骰）。归零时强制休息：下一轮提示词要求 AI 写出主角昏睡或休息的情节，并自动记一次入睡 |
| 金钱 | 按档位换算收支，不足时提示词告知“买不起”。收入来自打工检定（成功等级决定收入档）、战利品、剧情给予 |
| 压力 0–100 | 失败、冲突、熬夜会升高，休息、娱乐、恋人互动会降低。高于 70 时检定 −10 |

**消耗品**：食物、药水、药品按档位恢复体力或生命。物品名由 AI 正文给出，脚本只认档位（少量 / 普通 / 大量）。

**时间与日结算**
- 时间来源优先级：表格全局状态表的 `当前时间`（`YYYY-MM-DD HH:MM`，日期变化即跨天）> `sleep` 标签 > 正文钟点（`storyClock` / `hourOfTimeLabel`）。注意填表在 AI 回复之后进行，表格日期变化可能晚一楼才读到，此时把跨天记到日期变化出现的那一楼，不回改上一楼。
- 跨天判定满足任一条件即可：出现 `sleep` 标签；钟点从深夜回到早上；正文出现“第二天”“次日”等字样；表格中的日期变化。
- 日结算内容：体力恢复（睡足恢复到 100，熬夜后只恢复到 70）、生命自然恢复、压力 −10、技能成长掷骰、好感冷却、每日上限清零。
- 23 点以后的行动额外记一次熬夜。
- **时间跳跃**（“一周后”、`skip` 标签）：按天数一次性结算。体力和生命直接回满；好感冷却最多扣到阶段下限；技能成长只掷一次。

## 8. 修改数值与推送到 shujuku / AcuDice

**原则：单向推送。** IGS 是唯一的真值来源，只往外写，不从表格读回、不比对、不判断改动来源、不弹确认框。

- **修改数值只在 IGS**：状态面板里点数字修改，立即生效，记一条 `manual` 日志。开局建卡、个性卡也都在 IGS 里。
- **表格里的数值列只是展示**：在表格里手改、或者表格插件填表时 AI 改的数值，下一次推送时都会被 IGS 的真值覆盖。面板和设置页的说明里写明这一点。
- **修改记录**：面板里提供“变动记录”页，列出每次变化的来源、楼层、前后数值。

### 8A. 推送路径

目标：shujuku 和 AcuDice 拿到的数值就是 IGS 的真值。
- **AcuDice 没有写入接口**，它的属性直接读 shujuku 表格的单元格（`dice-system/stable.js` 中 `getCharacterAttributes` → 读 `sheet.content[行]` 的属性列）。所以只要写进 shujuku，AcuDice 自动拿到同一份数值，不需要单独对接。
- **写入接口是现成的**，`data/shujuku/client.js` 的 `createShujukuClient`：`readTables()`、`updateCell(tableName, rowIndex, colName, value)`、`refresh()`（即 `refreshDataAndWorldbook()`）。

推送规则：
- **推送对象**：
  - 好感等维度 → 角色数值表（表名含“数值”，或状态栏里选中的表，与 `character-metrics.js` 的选表规则一致）；
  - 主角技能与生活条 → AcuDice 读取的表（疑为“主角信息 / 重要角色表 / 技能表”的属性列）。具体是哪张表、哪一列，按“先核实”的结论来定。
- **推送时机**，只有两个：
  1. **结算之后**：一楼结算完成，把有变化的格子写入，然后刷新一次；
  2. **生成开始之前**：读一次表格，把与真值不一致的格子补写，然后刷新，等刷新完成再放行生成（最多等 3 秒，超时就放行）。表格插件填表时 AI 改掉的数值，在这一步被纠正，赶在下一轮提示词组装之前。
- **一批只刷新一次**：所有格子写完后调用一次 `refresh()`，不要每写一格刷新一次。
- **不碰其它内容**：只改目标单元格；不新建行、不新建列、不改其它列；找不到对应的行时跳过，并记入诊断。
- **保留格式**：原来是“45/100”就写“45/100”，原来是“45%”就写“45%”；AcuDice 属性格是“多个属性写在一格”的格式，只替换其中目标属性的数值，其余原样保留（格式先核实）。
- **只写当前最新楼层**。
- **不监听表格变化回调**：单向推送不需要读回，因此不会出现“写入 → 回调 → 再写入”的循环。

**先核实**（执行前查清，写进交付说明）：
- AcuDice 读的是哪几张表、哪几列，单元格格式是什么（`stable.js` 中 `Oa` / `ja` / `ko` 的表头识别与单元格解析规则）；主角对应哪一行（按姓名匹配，还是固定第一行）。
- 表格插件怎样把表格注入提示词：如果通过世界书条目注入，需要 `refresh()` 才生效（本流程按此设计）；如果生成时现读表格，可以省掉刷新。
- `updateCell` 的 `rowIndex` 从 0 还是从 1 开始、是否算表头；`colName` 是否必须与表头完全一致。
- 表格数据是否按楼层存储、会不会跟着 swipe 回退；如果会，切换 swipe 后要等表格插件回退完成再推送。
- 写入与刷新的耗时。

- 推送子开关关闭，或者未安装表格插件时，数值系统照常运行，只是不推送。表格里原有的好感列照旧由状态栏只读展示；数值系统开启后，人际关系页和好感总览改为读取 IGS 真值。

### 8B. 字段映射（适配任意表格模板）

用户可能使用任何 shujuku 模板，表名、列名、数值写法差别很大，推送不能写死表名列名。2026-10-22 对用户本机 52 套模板的统计：

| 情况 | 例子 |
|---|---|
| 好感在专门的列 | 恋爱对象表·`对主角好感度`；角色数值表·`好感度`；角色关系表·`好感度`、`好感度阶段`；女性角色档案表·`好感度` |
| 好感是文字 | 恋爱对象表·`对主角好感状态`（“略有好感”之类） |
| 战斗属性一列一个 | 主角信息·`力量` `敏捷` `体质`…`生命值` `体力值` `法力值`；战斗场景表 |
| COC | 调查员状态表·`生命值` `SAN值`；调查员角色卡表·`STR` `CON`… |
| 多属性写在一格（AcuDice 读这种） | 主角信息表 / 重要角色表 / 恋爱对象表·`基础属性` `特有属性` |
| 技能另成一表 | 才艺技能表·`名称 / 熟练度`；主角技能表·`技能名称 / 技能等级` |
| 行式表（每行一个属性） | romance-minimal-table：角色状态·`属性 / 值 / 备注` |
| 英文列名 | 恋爱对象表·`name` `relation_state` |
| 角色名列 | `姓名` `角色姓名` `角色名` `角色真实姓名` `调查员姓名` `name` |

**映射规则**：每个 IGS 数值（好感、信任、了解、欲望、生命、体力、金钱、压力、每个技能）各对应一个推送目标 = 表 + 列（或行式表的“属性名”）+ 写入形式。

1. **自动识别**：读取当前模板的表头，按关键词给每列打角色（好感：`好感`；信任：`信任`；生命：`生命|HP|血量`；体力：`体力`；金钱：`金钱|金币|财物|资源`；理智：`理智|SAN`；角色名：上表的姓名列；多属性格：`基础属性|特有属性`；技能表：表名含`技能`且有名称列）。关键词表放在设置里可改，并开放 DLC 登记。
2. **映射页**：设置器“数值系统 › 推送到表格”下列出每个 IGS 数值当前映射到哪张表哪一列，自动识别的结果预先填好，用户可以用下拉框改，也可以设为“不推送”。
3. **写入形式**，每条映射单独选：
   - 数字（默认；保留原格式，如“45/100”“45%”）；
   - 阶段名（列里原本写文字时用，例如往`对主角好感状态`写“朋友”）；
   - 多属性格（只替换格内目标属性的数值，其余原样保留，格式与 AcuDice 一致）；
   - 行式（在属性列找到名为“好感”的那一行，写它的值列）。
4. **数值范围换算**：表格用的不是 0–100 时（例如 DnD 属性 3–18、等级 1–99），每条映射可以设范围，推送时线性换算。默认不换算。
5. **按模板记住**：映射按“表名 + 表头”生成的模板指纹保存。切换模板后自动换成该模板的映射；遇到没见过的模板就重新自动识别，并在诊断里提示“检测到新的表格模板，请检查映射”（不弹窗）。
6. **IGS 没有的数值不管**：法力值、堕落值、经验值、等级这类 IGS 不管理的列，不推送，仍由 AI 填表。想让 IGS 管理的话，在设置里新增一个**自定义数值**（名称、范围、对应的标签档位），再映射过去。
7. **找不到就跳过**：映射的表或列不存在、角色没有对应的行时，跳过并记诊断，不新建行列，不影响数值系统运行。

**推荐模板（可选）**：IGS 另附一套与数值系统列名完全对应的 shujuku 模板，导入即可免配置使用。不强制，用户自己的模板走映射。

### 8C. 基准模板与 IGS 适配版

基准模板：`参考文件/TavernDB_template_恋爱Gal_一键开关(1).json`（用户提供，标准恋爱 gal 模板）。数值系统的维度、范围、属性体系都以它为准，并内置它的字段映射。

**与数值系统相关的表**：

| 表 | 列 | IGS 用法 |
|---|---|---|
| 角色数值表 | `角色姓名` / `好感度` / `信任度` / `了解程度`（百分数，-100%～100%）/ 已知秘密 / 未知秘密 | 推送好感、信任、了解，写成 `34%` 格式；秘密两列不碰 |
| 主角信息表 | `基础属性` / `特有属性`（`属性名:数值；` 多属性格）/ `近况` / `随身财物` | 推送主角属性与技能；`近况`、`随身财物` 不碰 |
| 重要角色表 | `姓名` / `角色类型`（恋爱对象 / 家人 / 配角…，也可能有“主角”）/ `基础属性` / `特有属性` / `在场状态` | 读：自动登记（§5.1B）、在场判定、NPC 对抗数值（首次读取后冻结） |
| 全局状态表 | `当前时间`（`YYYY-MM-DD HH:MM`）/ `经过的时间` | 读：跨天判定的首选依据（§7） |
| 检定建议表 | `展示文本` / `骰子命令` | 读：玩家点选项时作为先掷后写的命令来源（§4.1） |
| 一键开关表 | `是否NSFW` | 读：可选，用来联动欲望维度显示 |

**注入方式**：角色数值表、主角信息表、重要角色表都开启了导出到世界书（关键词条目，depth 2 或 10000），因此推送后必须 `refresh()` 才会出现在下一轮提示词里（§8A）。

**冲突点**（适配版要改掉）：
- 角色数值表的更新规则让填表 AI 每轮改好感（`updateFrequency: 1`，“单次事件变动通常 5%～15%，极端事件 20%～40%”）。这正是好感膨胀的来源。
- 检定建议表的规则里让 AI 自己做属性成长。
- 主角信息表、重要角色表的规则让 AI 填写和修改基础属性。

**IGS 适配版**：以基准模板为底，只做以下修改，其余表和规则不动：
1. 角色数值表：删掉让 AI 改好感、信任、了解的规则，改成“这三列由前端维护，禁止修改；新角色建档时填 0%”。已知秘密、未知秘密仍由 AI 维护。
2. 检定建议表：删掉 AI 自己成长属性的规则；DSL、选项方向、检定时机等规则保留。
3. 主角信息表：`基础属性`、`特有属性` 改为“由前端维护，禁止修改”；其余列不变。

## 9. 提示词（全部在设置器中可编辑）

数值系统注入给 AI 的所有提示词都放在设置器“数值系统”分类下，用户可以逐条查看和修改，并提供“恢复默认”。这与现有的提示词子页、“提示词全开放”的规则一致。不在代码里写死不可修改的提示词，不使用本地词库替代提示词。

注入通过 `host/prompt-injector.js`，内容分段，每段在设置器里对应一个可编辑的模板：

| 段 | 内容 | 模板变量举例 |
|---|---|---|
| 主角状态 | 体力、生命、压力、金钱，以及“疲惫”“买不起”这类状态描述 | `{{体力}}` `{{生命}}` `{{状态描述}}` |

| 标签说明 | 要求 AI 在正文末尾输出哪些标签、档位有哪些 | `{{可用档位}}` |

## 10A. 开启时机与存档继承

**两级开关**：
- **总开关**（侧边栏“数值系统”分类）：决定这个功能是否可用。
- **本聊天开关**：决定当前这个聊天是否启用数值系统。总开关打开后，每个聊天各自决定用不用。

**开场建卡**：本聊天第一次启用时，在开场画面（IGS 开场演出之后、第一楼之前）弹出建卡页，提供三个选择：
1. **分配点数**：手动分配技能点数（点数池与上下限见 Q5）；
2. **快速开始**：直接使用卡里预设的初始值，没有预设时用默认值，一键进入；
3. **本聊天不用数值系统**：关闭本聊天开关。这个聊天之后不注入、不结算，与关闭时的现状一致。

**中途打开**（之前跳过或关闭过，现在想打开）：从侧边栏或状态栏的“启用数值系统”入口打开。
- 从当前楼开始生效。之前的楼层没有快照，重 roll 之前的楼层不涉及数值。
- 初始值：表格里有数值时询问是否一次性导入（这是唯一一次从表格读数值，由玩家点击触发）；没有时进入同样的建卡页（分配点数 / 快速开始）。
- 不回溯结算之前的剧情。

**中途关闭后再打开**：关闭期间数值冻结，不结算、不衰减；再打开时从冻结的数值继续，期间的剧情不补算。

**存档继承**：
- **同一张卡新开聊天**：建卡页多出一个选项“继承上一个聊天的数值”。
- **酒馆分支**：分支从分叉楼层的快照继续。

## 13. 易错点清单（执行前必读）

每一条写明：会出什么错、必须怎么做、怎么验收。标“先核实”的，要先查清现有代码或外部接口再动手，不得凭猜测实现。

### A. 生成与结算时机

| # | 易错点 | 必须怎么做 | 验收 |
|---|---|---|---|
| A1 | 非剧情生成也触发掷骰或注入：表格插件填表、辅助模型、总结、`quiet`、`impersonate`、`dryRun` 都会产生生成事件 | 沿用 `core/bootstrap.js` 现有的过滤（`impersonate` / `quiet` 跳过注入，`dryRun` 直接返回）；只有正常发送、重 roll（新 swipe）这两种生成才掷骰 | 单测：每种生成类型各跑一次，只有正常发送和新 swipe 掷骰 |
| A2 | `continue`（继续生成）被当成新一轮，重新掷骰 | 继续生成沿用本楼本 swipe 已有的检定结果，不重掷；结算在继续完成后对全文重新做一次（从结算前快照开始，保证幂等） | 单测：继续生成前后检定结果不变，标签不重复计入 |
| A3 | 流式输出时边出字边结算，标签被结算两次 | 只在 `GENERATION_ENDED` 后对完整正文结算一次；`GENERATION_STOPPED`（中途停止）按已有正文结算 | 单测：流式分段输入，结算只发生一次 |
| A4 | 重新渲染、翻页、切回聊天时再次结算 | 结算以 `chatId\|messageId\|swipeId` 为键做幂等，键已存在就只读不算 | 单测：同一楼连续调用结算 3 次，数值只变一次 |
| A5 | 玩家编辑了 AI 楼正文（`MESSAGE_UPDATED`） | 从该楼结算前快照重新结算该楼；只重算这一楼，不级联重算后续楼层 | 单测：编辑后该楼数值与新正文一致，后续楼不变 |
| A6 | 先掷后写的注入残留到下一轮 | 注入只对本次生成有效，生成结束或停止时清除（参照 `prompt-injector` 现有的 clear 逻辑） | 单测：连续两轮，第二轮注入不含第一轮的检定 |
| A7 | 玩家从酒馆原生输入框发送，而不是从 IGS 阅读器发送，先掷后写没触发 | 先掷后写挂在生成开始事件上，读取最后一条玩家楼的文本，不依赖从哪里发送 | 两种入口各测一次 |

### B. 存档与快照

| # | 易错点 | 必须怎么做 | 验收 |
|---|---|---|---|
| B1 | 快照只按楼层不按 swipe，左右切换 swipe 时数值错乱 | 键必须含 swipeId（§3）；切换到已有 swipe 只读取，不重掷 | 单测：两个 swipe 结果不同，来回切换各自不变 |
| B2 | 只存在 IndexedDB，换设备或导出聊天后数值丢失 | 先核实：写进聊天文件（楼层 `extra` 或聊天元数据）的接口与保存时机；IndexedDB 只作缓存 | 导出再导入聊天后数值仍在 |
| B3 | 删楼后数值没有回退 | 监听 `MESSAGE_DELETED`，当前状态取最后一个存活楼层的结算后快照 | 单测 |
| B4 | 快照越积越大，长聊天卡顿或发烫 | 快照只存结算后状态，不存全量日志；日志另存并限条数（例如最近 500 条）；禁止每楼深拷贝整份存档（遵守发烫修复的规矩：共享只读、写时浅拷） | 千楼聊天打开不卡；测试中无整份 `structuredClone` / JSON 深拷贝 |
| B5 | 配置（卡配置）和存档（聊天数值）混在一起，导出预设时把玩家数值带出去 | 两者分开存储；预设导出只带配置 | 单测：导出预设不含数值 |

### C. 标签解析

| # | 易错点 | 必须怎么做 | 验收 |
|---|---|---|---|
| C1 | AI 写出各种变体：全角括号【】、全角竖线｜、多空格、中英文冒号、标签换行 | 解析器宽松接受这些变体，参照 `fx-directives.js` 现有的容错写法 | 语料测试覆盖每种变体 |
| C2 | 档位词不在白名单里（例如 AI 写“超级开心”“+5”） | 先做近义词归一（超级开心 → 开心）；归一不了的整条丢弃，并记入诊断。**任何数字都不采纳** | 单测：带数字的标签被丢弃 |
| C3 | 角色名用了昵称、全名的一部分、`<user>`、`{{char}}` | 用 `resolveCharacterKey` + 别名解析；`<user>` / `{{user}}` 指主角；仍然解析不了的按路人处理，并记入诊断（“未识别的名字”），方便用户补别名 | 单测 + 诊断可见 |
| C4 | 标签漏剔除：显示在阅读器、被语音朗读、出现在漫画泡或弹幕里 | 统一在一处剔除，阅读器、TTS、漫画、弹幕、通知都用剔除后的文本 | 各出口各测一条 |
| C5 | AI 一楼打出大量标签刷分 | 单楼单角色单维度只结算一次（§4.2），配合每日上限 | 单测：一楼 10 个“感动”只算一次 |
| C6 | 引号里的台词、回忆段落里出现标签或跨天字样 | 标签不论位置都结算（标签是给脚本的）；跨天字样在引号和回忆段落内不算（§4.2） | 单测 |

### D. 时间与跨天

| # | 易错点 | 必须怎么做 | 验收 |
