# 数值系统 v2 计划：规则体系、角色卡、开放技能、故事中检定

本计划在 v1（`docs/STATS_SYSTEM_PLAN.md`，已随 v0.36.117–119 实施）的底层上重建玩法层。v1 的账本、种子、存档、推送、好感防膨胀全部保留；本计划只改「检定怎么发生、怎么算、怎么让玩家看见」。执行前先读 v1 文档 §13 易错点清单，本文 §12 只列新增项。

## 0. v1 为什么没起作用

| 问题 | 位置 |
| --- | --- |
| 检定只靠玩家输入命中固定词表；词表外的行动、选项、AI 写出的情节都不检定 | `core/stats-runtime.js` planCheck |
| AI 看不到主角技能，提示词只有生命、体力、压力、金钱，不会安排需要技能的关口 | `scene/stats/stat-prompt.js` |
| 检定结果只进提示词，玩家看不到骰子 | `stats-runtime.js` inject |
| `igs:stats-fx` 无人监听；好感提示只靠状态栏数值差分（需开「数值变化提示」，且只对当前说话人），检定与非说话人的好感变化没有演出 | `core/bootstrap.js` onChange、`visual/igs-ui/fx-runtime.js` favorToast |
| 选项气泡骰子读 AcuDice 属性，与本系统技能是两套 | `visual/igs-ui/reader-host.js` resolveOptionSendText |
| 技能是封闭清单，剧情出现「开锁」「潜行」无处安放 | `stat-state.js`、`stat-skill-match.js` |
| NPC 没有数值，无法对抗 | — |
| 总开关与本聊天开关都要手动打开 | `stat-settings.js` |

## 1. 已定决策

用户定：
- 技能名用 IGS 自己的（6 项基础属性 + 特有技能 + 世界观技能 + 自定义 + 剧情新技能）；计算方式用所选规则体系的官方规则。
- 规则体系在设置里全局选择：CoC 第七版或 D&D 第五版；允许随时切换。
- 旧存档自动换算，不要求重新建卡。
- NPC 需要角色技能以支持对抗；初始数值由一次 LLM 调用分配；新角色出现时提醒用户生成。
- 沿用 v1：骰子由脚本真随机，AI 只给离散标签不碰数字；重 roll 也重掷；好感防膨胀四层不动。
- 故事中途由 AI 发起的检定按数值自动判定（预掷，不额外调用 LLM）；只有选项气泡由玩家手动掷（§5.2）。
- CoC 大成功保留 v1 的「≤5」（约 5%），不改为官方的 01；大失败同样保留 v1 的「≥96」。

本计划替用户定（用户授权「深度思考、替我设计」，理由见各节）：
- 存档里的数值统一用百分制 1–99 作「底数」，规则体系只负责换算与掷骰；切换规则不改存档（§3）。
- 对抗平局改按官方规则（§4.1）。
- 难度用四档语义标签，由 AI 按「普通人能否做到」来选，再由规则体系换成各自的难度（§4.3）。
- NPC 角色卡与技能注册表存在聊天级，不进每楼快照（§6.4）。
- 掷骰卡在数值系统开启时默认显示（§9）。

## 2. 架构：规则体系是可替换的一层

```
检定来源（选项 / 预掷 / 输入匹配 / 战斗 / 关键事件 / 打工）
        ↓ 统一请求 { actor, skill, difficulty, opposed?, modifiers }
检定引擎 scene/stats/stat-engine.js
        ↓ 按设置取规则体系
规则体系 scene/stats/rulesets/coc7.js | dnd5e.js（登记表，留 DLC 口子）
        ↓ 统一结果 { ladder, success, roll 明细, display }
结算（账本 / 好感 / 成长）+ 演出（掷骰卡）+ 提示词（结果注入）
```

规则体系模块只做四件事，全部是纯函数：
1. `project(actorSheet, skill)`：把底数换成本体系的检定参数（CoC 为目标值，D&D 为加值）。
2. `resolve(request, random)`：掷骰并给出统一结果等级。
3. `contest(left, right, random)`：对抗。
4. `describe(...)`：生成掷骰卡与提示词里的明细文案（「1d100=37，需≤50」或「d20(14)+4=18，DC15」）。

现有直接调 `rollStatCheck` 的地方（`stats-runtime.js` rollCheck、`stat-battle.js`、`stat-favor-events.js` applyKeyEvent、打工）全部改走引擎；`choices/dice-check.js` 的 `rollD100` 与命令解析保留复用。

规则体系通过登记表注册（同 DLC 接口的皮肤/演出登记表做法），第三方以后可加别的体系；本期只做两套，不做 DLC 示例。

## 3. 数据模型

### 3.1 底数：存档只存百分制

所有属性与技能在存档里都是 1–99 的整数（v1 已是这样，基础属性 10–90、技能 10–90）。理由：
- CoC 本身就是百分制，底数即目标值，零损失。
- D&D 的数值可以从百分制确定性地推出（§4.2），反过来则会丢精度。只存一份底数，切换规则时不改任何存档字段，可以无损切回。
- AcuDice 推送继续推百分制，不受规则体系影响。

D&D 视图下用户在面板里手改数值时，只把被改动的那一项按 §4.2 的反向表写回底数，其余字段不碰（易错点 N8）。

### 3.2 技能注册表（聊天级）

v1 的技能名散在 `BASE_ATTRIBUTES`、`DEFAULT_SPECIAL_SKILLS`、世界观词表与自定义列表里。v2 收拢成一张注册表，每条：

| 字段 | 说明 |
| --- | --- |
| `name` | 规范名，即 IGS 技能名 |
| `kind` | `attribute`（6 项基础属性）或 `skill` |
| `attribute` | 技能所属属性（属性自身留空） |
| `category` | `daily` 日常 / `general` 通用 / `pro` 专业 / `rare` 稀有，决定未学基础值（§4.4） |
| `social` | 是否社交类，决定好感是否影响检定（§7.1） |
| `aliases` | 同义词，用于归并 AI 与插件写出的技能名 |
| `origin` | `builtin` / `world` / `custom` / `story`（剧情中新出现） |
| `opposedBy` | 默认对抗技能，如话术→理智、潜行→观察 |
| `createdAt` | 剧情技能首次出现的楼层 |

内置条目写在代码里，聊天存档只存 `origin: story` 的新增条目与用户改过的别名。

属性与技能的区别要讲清楚：「看看四周」是观察**属性**检定，「侦查现场」是侦查**技能**检定（挂在观察下）。v1 词表把「侦查、搜查、调查」当成观察属性的触发词，v2 拆成一个独立技能「侦查」挂在观察下，这样 D&D 下熟练加值才有意义（属性检定不加熟练）。拆分清单见附录 A。

### 3.3 主角

保留 v1 的 `protagonist.skills: { 名: { value, marked } }`，属性与技能同在一张表里，用注册表的 `kind` 区分。这样 v1 的建卡、成长、标记、推送代码都不用改结构。

新增 `protagonist.rank`：资历档（§4.2，只给 D&D 用），由累计成长次数推出，不单独存档。

### 3.4 NPC 角色卡（聊天级）

v1 的 `characters[名]` 只有好感维度（逐楼快照，保留不动）。v2 另建聊天级 `sheets[名]`：

```
{ rank: '普通人', attributes: { 健康: 52, … }, skills: { 话术: 63, … }, signature: ['剑术'],
  source: 'llm' | 'default' | 'user', provisional: { 潜行: true }, createdAt: 楼层 }
```

- NPC 不成长，角色卡生成后冻结。只有用户在面板里改，或批量补全填「待定」项时才写。
- 没有角色卡的 NPC 按「普通人」默认卡参与检定（属性全 50，技能全按未学），不阻塞。
- `provisional` 标记临时值（§6.3），补全返回后清除。
- 放聊天级而不进每楼快照：NPC 卡是静态的，进快照会让每楼存档膨胀；代价是删楼不会删卡，可以接受，面板里可手动删。

### 3.5 存档版本与迁移

`STATS_SAVE_VERSION` 1 → 2。迁移在 `deserializeLedger` 内做，纯函数：
1. 主角 `skills` 原样保留（底数不变）。v1 里「侦查」等原属于观察属性的词，不新建技能值，按未学处理。
2. 新增 `registry`（空，只有内置）、`sheets`（空）、`pending`（空）。
3. `entries[*].after` 不需要改结构；读取时缺字段按默认补。
4. 迁移后首次写回前，在 `chatMetadata.igs_stats_v1_backup` 留一份原样副本；面板「存档」区提供「删除旧版备份」。只备份一次，不重复。
5. 读到 version 3 以上照旧拒收不覆盖（v1 已有）。

规则体系**不进存档**，只记在每次检定的 meta 里（`check.ruleset`），用于重算与诊断。切换规则后，旧楼编辑正文重算时沿用该楼当时的体系（易错点 N5）。

## 4. 规则计算

### 4.1 CoC 第七版

- 检定：1d100 ≤ 目标值成功。困难需 ≤ 目标/2，极难需 ≤ 目标/5（向下取整）。
- 大成功 ≤5、大失败 ≥96（用户定，沿用 v1 与 AcuDice；官方为 01 与 96/100）。`coc7.js` 直接复用 `dice-check.js` 的 `successLevel`，与选项骰子走 AcuDice 时的结果一致。
- 奖励骰 / 惩罚骰：多掷十位骰取低 / 取高，互相抵消，净值最多 2 颗（v1 已实现，复用 `rollD100`）。
- 对抗：双方各掷，比成功等级（大成功 > 极难 > 困难 > 普通 > 失败）；同级时技能值高者胜；仍相同则维持现状（剧情上算僵持）。v1 的「同级判主角负」改掉。
- 对被动目标：v1 已实现的「对方技能 ≥50 定困难、≥90 定极难」保留，用于 NPC 不主动对抗的场合（如潜入时守卫的观察）。
- 成长：v1 的「成功打勾，跨天掷 d100 大于当前值 +1d10，上限 90」本来就是 CoC 规则，不动。

### 4.2 D&D 第五版

- 属性值 = round(底数 / 5)，夹在 1–30；修正值 = floor((属性值 − 10) / 2)。底数 50 → 10 → +0，底数 90 → 18 → +4。
- 技能熟练度由底数决定（对齐 CoC 官方技能水平表的分段）：

| 底数 | 档 | D&D |
| --- | --- | --- |
| 未学 / <25 | 未学 | 只加属性修正 |
| 25–49 | 入门 | 只加属性修正 |
| 50–74 | 熟练 | + 熟练加值 |
| 75–89 | 精通 | + 熟练加值 ×2（专精） |
| 90+ | 大师 | + 熟练加值 ×2（D&D 下与精通相同，差别体现在属性修正与 CoC 下） |

- 熟练加值看资历档：普通人 +2、老手 +3、精英 +4、大师 +5、传奇 +6（与官方 1/5/9/13/17 级对应）。
  - 主角的资历由累计成长次数推出：0 / 10 / 25 / 45 / 70 次分别对应五档。
  - NPC 的资历由角色卡生成时 LLM 给出。
- 属性检定（6 项基础属性本身）只加修正值，不加熟练。
- 检定：d20 + 加值 ≥ DC 成功。优势 / 劣势掷 2d20 取高 / 低，不叠加，互相抵消。
- 对抗：双方 d20 + 加值，高者胜，平局维持现状。
- 被动值：10 + 加值，有优势 +5、劣势 −5。用于 NPC 被动抵抗与 §8.2 被动感知。
- 自然 20 / 1：官方规则只对攻击检定生效，属性检定与技能检定不自动成功或失败。设置项「D&D 自然 20/1 视为大成功/大失败」默认关。

### 4.3 难度：四档语义标签

AI 只写四档之一，规则体系各自换算：

| 标签 | 给 AI 的定义 | CoC | D&D |
| --- | --- | --- | --- |
| 简单 | 普通人多半能做到，失败会有点尴尬 | 普通难度 + 1 颗奖励骰 | DC 10 |
| 普通 | 需要一定本事，外行容易失手 | 普通难度 | DC 15 |
| 困难 | 内行也要认真对待 | 困难难度 | DC 20 |
| 极难 | 只有高手才有机会 | 极难难度 | DC 25 |

「毫无悬念」的行动不检定，提示词里明确写（§5.2）。

成功率参考（主角默认建卡属性约 40–60；CoC 简单档按 1 颗奖励骰近似）：

| 主角 | 简单 | 普通 | 困难 | 极难 |
| --- | --- | --- | --- | --- |
| CoC 技能 25（未学常见值） | 44% | 25% | 12% | 5% |
| CoC 技能 50（熟练） | 75% | 50% | 25% | 10% |
| CoC 技能 75（精通） | 94% | 75% | 37% | 15% |
| D&D 加值 +0（属性 50，未学/入门） | 55% | 30% | 5% | 0% |
| D&D 加值 +2（属性 50，熟练） | 65% | 40% | 15% | 0% |
| D&D 加值 +4（属性 50，精通） | 75% | 50% | 25% | 0% |
| D&D 加值 +6（属性 70，精通） | 85% | 60% | 35% | 10% |

两套体系的手感差别如实保留：CoC 高手与新手差距大；D&D 低端更宽容，但普通人摸不到极难。提示词要求 AI 极难档少用（§5.2）。对抗时双方同值，CoC 约各半，D&D 约 45% 胜、5% 平。

### 4.4 未学技能的基础值

CoC 官方每个技能有固定基础值（侦查 25、开锁 1 等）。IGS 技能大多不在官方表里，按注册表 `category` 给：

| 类别 | 基础值 | 例 |
| --- | --- | --- |
| 日常 daily | 25 | 家务、烹饪、运动、照顾 |
| 通用 general | 15 | 话术、侦查、潜行、急救 |
| 专业 pro | 5 | 开锁、医术、驾驶飞行器 |
| 稀有 rare | 1 | 魔法、咒语、古文字 |

官方表里有的同名技能（侦查、聆听、急救、潜行、闪避等）直接用官方基础值，闪避按「敏捷 / 2」。附录 A 给出对照。D&D 下未学技能只看属性修正，基础值不参与计算。

v1 建卡时「未选的特有技能不进存档」不变：缺项在检定时按基础值算，不写存档。

### 4.5 统一结果等级

结算与演出不再直接认 CoC 的等级名，改认中立等级：

| 中立等级 | CoC | D&D |
| --- | --- | --- |
| `crit` 大成功 | ≤5 | 关闭自然 20 规则时：超过 DC 10 以上；开启时：自然 20 |
| `extreme` 极佳 | 极难成功 | 超过 DC 5–9 |
| `hard` 良好 | 困难成功 | 超过 DC 1–4 |
| `pass` 成功 | 普通成功 | 恰好达到 DC |
| `fail` 失败 | 失败 | 低于 DC |
| `fumble` 大失败 | ≥96 | 关闭自然 1 规则时：低于 DC 10 以上；开启时：自然 1 |

D&D 的分档只用于 IGS 的演出与好感、打工收入等结算，不改变官方的成败判定。掷骰卡与提示词显示各体系自己的文字（CoC 写「困难成功」，D&D 写「成功（超出 3）」）。

需要改的消费方：`stat-bars.js` workIncomeTier、`stat-battle.js` outcomeOf、`stat-favor-events.js`、`visual/igs-ui/fx-result-model.js`。

### 4.6 修正来源

v1 的生活条修正在 D&D 下换成对应写法：

| 来源 | CoC | D&D |
| --- | --- | --- |
| 体力 <30、生命 <20（各一项） | 惩罚骰 1 颗 | 劣势（两项都有也只算一次劣势） |
| 压力 >70 | 目标 −10 | 加值 −2 |
| 队友协助 | 奖励骰 1 颗 | 优势 |
| 好感（§7.1） | 奖励 / 惩罚骰 | 优势 / 劣势 |

奖惩骰与优势劣势都先合并成「净优势值」再交给规则体系，CoC 最多 ±2 颗，D&D 只有 ±1。

## 5. 检定从哪里来

v1 只有「玩家输入命中词表」一个入口。v2 有五个，优先级从上到下，同一楼只取一个（易错点 N6）：

### 5.1 选项气泡（已有，改路由）

表格选项的骰子列（`检定 <user> 观察 难度=困难`、`对抗 …`）在数值系统启用时改走 IGS 引擎：
- 角色名与属性名经注册表别名解析；主角读 `protagonist.skills`，NPC 读 `sheets`。
- 没登记的技能名按 §6.1 当场登记。
- 发送文本仍是 `formatCheckMessage` 的「元叙事」块，AI 侧与表格侧格式不变。
- 本楼结算时，`planCheck` 发现玩家楼里已有 IGS 写的元叙事块，直接采用其结果作本楼 check（用于成长打勾），不再按输入匹配重掷。元叙事块里带一段不显示的 `igs-check` 标识，避免误认 AcuDice 写的块。
- 数值系统未启用时维持现状走 AcuDice。

选项上显示预估成功率（「观察·困难 约 25%」），按当前规则体系与修正实时算；设置可关。

### 5.2 故事中途的检定：预掷（新增，主入口）

用户定：故事中途由 AI 发起的检定按数值自动判定，不让玩家点、不额外调用 LLM；手动掷只留给选项气泡。

做法：生成开始时，本楼还没有选项检定或输入匹配检定，脚本就先掷好一颗骰（CoC 一颗 d100，D&D 一颗 d20），按主角当前数值算出「这颗骰下各技能能过到哪一档」，写进提示词。AI 写到需要检定的地方，自己选一个合适的技能与难度，按表里的结果写，正文末尾打一个标签说明用了哪项。

注入示例（CoC，骰面不告诉 AI，只给结论）：

```
【本轮骰运】若主角本轮需要检定，按下表写结果，不得改判；一轮只检定一次，用不到就不检定。
能过到极难：烹饪
能过到困难：观察、话术
只能过普通：力量、敏捷、魅力、侦查
失败：健康、理智、潜行
未学的技能：日常类只能过普通，其余失败
对抗在场角色：林晚抵抗话术时按困难算
用过后在正文末尾写 [igs-stat:roll|技能|难度]，新技能写 [igs-stat:roll|开锁|普通|敏捷]
```

- 表只列有用的分组，不列每个技能每档的组合；单调性保证「能过困难」就一定能过普通。
- 未学技能按类别各占一行（§4.4），不逐个列。
- 对抗在场 NPC 时，按 NPC 抵抗技能折算成难度（CoC 用 §4.1 被动目标规则，D&D 用被动值作 DC），只列在场 NPC 的默认对抗项。
- 修正（体力、压力、好感）在算表时已计入。好感只影响对该 NPC 的社交技能，表里单列一行（「对林晚用话术：能过到困难」）。

结算：
1. 生成结束，读到 roll 标签 → 用同一颗骰按标签的技能、难度重算一次结果，写进 `meta.check`（成长打勾、掷骰卡都用这份）。
2. 骰与表存在本楼生成状态里；继续生成沿用，重 roll 重掷（v1 规则）。
3. AI 没打标签：按本楼无检定处理，诊断记 `stats-roll-skipped`。
4. 标签里的技能不在表里（新技能）：按 §6.1 登记，用这颗骰按未学或临时值算。

已知代价：AI 可能挑一个表里成功的技能来写。缓解：提示词要求技能必须贴合行动；掷骰卡展示真实骰面与技能，玩家看得到。主角擅长的技能本来就更容易被用上，这在剧情上也说得通，不另加限制。

成本：每轮多注入约 8 行提示词，不增加调用次数。

设置「故事中检定」：预掷（默认）/ 手动掷骰 / 关闭。
- 手动掷骰：AI 写到行动发起处停下打 roll 标签，阅读器显示掷骰按钮，玩家点击后掷骰并续写（`tavern-helper-adapter.js` 已有 continue / `/trigger` 封装）。每次检定多一次续写调用。玩家没点而是直接打字发送：作废，记诊断 `stats-roll-abandoned`。放在 P4。

提示词约束（两种方式共用）：
- 毫无悬念的事不检定；一楼最多一次。
- 极难少用，只留给真正的关键时刻。
- 失败不能让剧情卡死：失败也要推进，只是付出代价（受伤、暴露、错过、关系受损）。

### 5.3 玩家输入匹配（v1 已有，降为兜底）

保留 v1 词表匹配与先掷后写。改动：
- 词表按 §3.2 拆分属性与技能，并接入注册表别名。
- 匹配不到时不再调辅助模型猜，改注入预掷表（§5.2）由 AI 自己选技能，省一次调用也避开生成开始时不能调酒馆模型的限制。
- 匹配到具体技能时注入「本轮检定」段，不再注入预掷表。
- 匹配到的检定照旧静默掷骰，但掷骰卡要在发送后、生成前显示出来（§9.1）。

### 5.4 结算内检定（v1 已有，改走引擎）

战斗、打工、关键事件突破（魅力检定）、送礼都在结算里由脚本掷，改走引擎即可，规则体系自动生效。

### 5.5 被动感知（新增，不掷骰）

每轮注入主角的被动感知档位（D&D 为被动察觉值，CoC 为观察 / 侦查的档名），AI 据此决定主角能注意到什么，不需要掷骰也不需要掷骰。只占一行提示词。

## 6. 开放技能与快速补全

### 6.1 新技能登记

新技能名可能来自：roll 标签第 4 栏、选项骰子列、NPC 角色卡生成时的招牌技能、玩家自定义。登记流程：
1. 规范化：去空白，1–8 字，无数字、无标记符号（沿用 `validCustomSkillName`）。
2. 归并：先查注册表规范名与别名，命中则用已有技能。再查附录 A 的内置别名表。都没命中才新建。
3. 新建：所属属性取标签给的；没给时按附录 A 的关键字猜（「剑、拳、枪」→ 力量或敏捷等），猜不到归敏捷并标记 `attributeGuessed`，补全时一并让 LLM 确认。类别默认 `general`。
4. 上限：剧情技能每聊天最多 24 个，一楼最多新建 2 个。超出后不再登记，检定按所属属性的属性检定算，记诊断 `stats-skill-cap`。
5. 阅读器细线提示「新技能：开锁（敏捷）」，面板可改名、改属性、合并到已有技能、删除。

### 6.2 缺漏数值的三层补全

新技能登记后，所有角色都缺这一项。处理分三层，前一层保证不阻塞，后一层提高合理性：

**第一层：立即可用，不调模型。** 检定当场需要时：
- 主角：按未学基础值（CoC）或纯属性修正（D&D）。
- 在场 NPC：按所属属性的档位估一个临时值（属性高的给「入门」，属性很高的给「熟练」），写进 `sheets[名].skills` 并标记 `provisional`。这样 NPC 不会因为「默认未学」在对抗里一律偏弱。
- 不在场的 NPC：不写，等用到时再算。

**第二层：批量补全，一次调用。** 新技能进入补全队列。本楼生成结束后（不在生成开始事件里，易错点 N1），后台发一次 LLM 请求：
- 一次问清队列里所有技能 × 所有已有角色卡的角色 + 主角。
- 每格只回一个档位（未学 / 入门 / 熟练 / 精通 / 大师），不回数字。
- 参考资料：每个角色只带角色卡或世界书条目的摘要（截断到 300 字），不带聊天正文。
- 单次最多 8 个角色、6 个技能；超出拆成下一批，下一楼结束后再发。
- 返回后脚本按 §6.3 把档位换成底数，替换临时值，清除 `provisional`。

**第三层：冻结。** 已有值（非 provisional）补全时不改，只填空。防止数值被慢慢抬高。之后的变化只有主角成长与用户手改。

主角特殊处理：人设写了相关经历时（「退伍军人」之于射击），补全最多给到「熟练」，并在细线提示「按人设补全：射击 熟练」，面板可撤销。不写人设或人设无关时一律未学。

补全时机设置：每楼结束后自动（默认）/ 手动点「补全数值」/ 关闭（只用第一层）。

### 6.3 档位换底数

LLM 永远只给档位，脚本用本楼种子在区间内取值，保证同一聊天重算结果一致：

| 档位 | 属性底数 | 技能底数 |
| --- | --- | --- |
| 很弱 / 未学 | 20–30 | 基础值 |
| 偏弱 / 入门 | 35–45 | 25–45 |
| 普通 / 熟练 | 45–55 | 50–70 |
| 出众 / 精通 | 60–70 | 75–85 |
| 顶尖 / 大师 | 75–90 | 90–95 |
| 超凡（仅非人） | 91–99 | — |

属性用左边的五档词（很弱、偏弱、普通、出众、顶尖），技能用右边的五档词，两套词不混用，LLM 输出时更不容易错。

底数上限保持 99，D&D 下最高属性值 20。龙、神明这类超出人类上限的角色不再往上加数值，靠 §7.3 的敌人档与剧情处理。

### 6.4 新角色出现时生成角色卡

触发：v1 的登记规则（角色卡名、群聊成员、世界书有条目、累计出现）判定某角色为重要角色、且 `sheets` 里还没有这个名字。

流程：
1. 阅读器细线提示「新角色：林晚 · 生成数值」，带按钮。几个角色同时出现时合并成一条（「新角色 3 位 · 生成数值」）。
2. 用户点击 → 一次 LLM 请求生成所有待生成角色。没点之前该角色用默认卡（§3.4）。
3. 人际关系页的角色卡上也有「生成数值」按钮；设置 › 数值系统 › 角色 有「为全部缺卡角色生成」。
4. 设置「新角色数值」：提醒（默认）/ 自动生成 / 不生成。

请求内容：角色名、角色卡或世界书条目摘要（截断到 600 字）、当前世界观、当前技能注册表的技能名与所属属性。要求输出 JSON：

```json
{ "林晚": { "资历": "普通人", "属性": { "健康": "普通", "敏捷": "出众" },
           "技能": { "话术": "熟练", "艺术": "精通" }, "招牌技能": [ { "名": "茶艺", "属性": "敏捷" } ] } }
```

- 只列与「普通 / 未学」不同的项，省输出。
- 招牌技能最多 3 个，走 §6.1 登记。
- 校验：档位只收白名单词；出现数字整格丢弃；未知技能名走登记或丢弃；整份解析失败则角色保持默认卡，提示「生成失败，可重试」，不写半份数据（易错点 N3）。

成本估算：一个角色约 800 输入 token + 200 输出 token。

调用渠道：优先用自动插图设置里的独立 API（v1 辅助模型同一套配置）；没有独立 API 时，在没有主生成进行时走酒馆 generateRaw，并经 `host/background-generation.js` 标记为后台请求，避免被数值系统当成一次主生成去结算（易错点 N2）。生成进行中点击按钮则排队到生成结束。

跨聊天沿用角色卡：同一角色卡开新聊天时，从上一个聊天复制已生成的 NPC 卡，省得重新生成。本期不做，列入 P4。

## 7. 对抗、好感与战斗

### 7.1 好感影响社交检定

注册表里 `social: true` 的技能（话术、魅力、表白类等），对方是已登记 NPC 时，好感阶段给修正：

| 好感阶段 | CoC | D&D |
| --- | --- | --- |
| 深爱、强烈在意 | 奖励骰 1 颗 | 优势 |
| 明确喜欢 至 淡淡不喜 | 无 | 无 |
| 厌烦排斥、强烈反感 | 惩罚骰 1 颗 | 劣势 |
| 仇恨 | 惩罚骰 2 颗 | 劣势 |

这让好感有了实际用处：关系好，劝说、请求更容易成功。

### 7.2 检定结果反过来约束好感

社交检定的结果写进本楼 meta，结算好感标签时：
- 失败或大失败：本楼对该角色的正向好感标签降一档（心动→开心→平淡），防止「劝说失败但对方好感大涨」。
- 大成功：本楼单楼上限 +3 放宽到 +4，不突破关口。
- 关键事件突破关口的魅力检定（v1 已有）改走引擎，按规则体系掷。

v1 的四层防膨胀（方向标签查表、越高越难涨、单楼与每日上限、关口要关键事件）全部保留。

### 7.3 战斗按规则体系速算

保留 v1「整场速算」：一个 battle 标签，脚本一次算出胜负，AI 只写过程。

CoC：
- 每回合主角最佳战斗技能对敌人战斗值做对抗。按官方规则，主角反击时同级攻击方胜，闪避时同级闪避方胜。v1 的「同级判主角负」去掉。
- 敌人档沿用 v1：杂兵 35 / 1 回合、精英 55 / 2 回合、头目 75 / 3 回合。

D&D：
- 主角 AC = 10 + 敏捷修正。敌人档换成攻击加值与 AC：杂兵 +3 / AC 12、精英 +5 / AC 14、头目 +7 / AC 16，回合数同 CoC。
- 每回合主角做一次攻击检定（d20 + 加值 ≥ 敌人 AC），命中即赢下该回合；敌人的威胁由闪避豁免体现，不再单独掷敌人攻击。攻击检定的自然 20 / 1 按官方规则必中 / 必失。
- 闪避回合改为一次敏捷豁免，DC 按敌人档 12 / 14 / 16。

两套共用：
- 胜负档沿用 v1（大胜、胜、险胜、败），伤势、体力、金钱结算不变，战败不死。
- 敌人是已有角色卡的 NPC 时，用角色卡里的战斗技能代替档位值。
- 敌人数量的惩罚骰改为劣势；队友协助给奖励骰或优势，并肩取胜仍算一次「共患难」。

### 7.4 NPC 对主角发起检定

NPC 试图骗主角、偷袭、诱惑时，主角是被动的一方。预掷表里同时给出「在场 NPC 对主角出手时主角能否识破 / 躲开」一行（按主角观察、心理学、闪避对 NPC 的话术、潜行、格斗折算），AI 照写，标签写 `[igs-stat:roll|观察|普通|对抗:林晚|话术]`。结算按同一颗骰重算主角一边。

NPC 之间的冲突不掷骰，由 AI 按双方角色卡档位直接写。

## 8. 提示词

全部进设置器可编辑（沿用 v1 §9 的模板与变量机制），新增段：

| 段 | 内容 | 何时注入 |
| --- | --- | --- |
| `skills` | 主角技能档位一行，如「观察 熟练、话术 入门、烹饪 精通」；只列入门以上，最多 12 项 | 每轮 |
| `perception` | 被动感知档位（§5.5） | 每轮 |
| `roll` | 预掷结果表与标签格式（§5.2），四档难度的定义（§4.3） | 本轮没有选项检定或输入匹配检定时 |
| `sheets` | 在场 NPC 的资历与招牌技能一行 | 有在场 NPC 时 |
| `check` | 改成按规则体系写明细，如「侦查（困难）：d20(14)+4=18，DC20，失败」 | 有检定时 |
| `sheetGen` | 角色卡生成请求（§6.4） | 后台请求，不进主生成 |
| `backfill` | 批量补全请求（§6.2） | 后台请求，不进主生成 |

`skills` 与 `sheets` 只写档位名，不写底数，延续「AI 不碰数字」。

v1 的 `tags` 段补一行 roll 标签。为控制长度，`roll` 段只在本轮没有现成检定时才注入；有检定时换成 `check` 段。

## 9. 界面

样式复用现有 class 与主题变量，跟随皮肤，不写内联样式；文案书面化，中英文之间不加空格。

### 9.1 掷骰卡

复用 `visual/igs-ui/fx-result-*`（选项骰子已在用）。数值系统启用时，所有检定都播放：
- 选项：玩家点击后播放，定格后发送（现有行为）。
- 输入匹配：发送后、生成前播放，不阻塞发送。
- 预掷：AI 打了 roll 标签的楼，阅读器翻到标签所在句之后的那一页时播放；没打标签不播。
- 手动掷骰（可选档）：玩家点击后播放，定格后再续写。
- 结算内检定（战斗、打工、关键事件）：本楼渲染到第一页时播放。
- 卡面：技能名、难度、骰面、目标、结果文字；CoC 显示百分骰两颗（十位、个位），D&D 显示 d20 与加值。

现有 `resultFx.enabled`（掷骰展示，默认关）在数值系统启用时视为开，单独可关。

### 9.2 数值变化

- 接上 `igs:stats-fx`：其他角色的关系阶段跨越、关键事件结果、成长、战斗结果走生成细线（`showImageNotice`）；当前说话人的好感飘字仍由状态栏 favorToast 负责。新技能、新角色走阅读器提示条。
- 不弹窗、不挡画面（v1 §10）。

### 9.3 角色卡面板

人际关系页（`visual/igs-ui/record-panel.js`）每个已登记角色加一栏：
- 资历、6 项属性、已有技能。按当前规则体系显示：CoC 显示百分值，D&D 显示属性值 / 修正与熟练标记。
- 临时值带「待定」标记。
- 按钮：生成数值 / 重新生成（覆盖前确认）/ 编辑 / 删除角色卡。

设置 › 数值系统 › 存档区增加：
- 主角技能表（含未学的注册技能，按体系显示）。
- 剧情技能列表：改名、改属性、合并、删除。
- 检定记录：最近 50 次，每条有楼层、技能、难度、骰面、结果、规则体系。让玩家能核对骰子没有作弊。
- 删除旧版备份（§3.5）。

### 9.4 「为什么没检定」

「复制本页诊断」加一段：本楼检定来源（选项 / 预掷 / 输入匹配 / 结算 / 无）；为无时写原因（未匹配、被否定句排除、AI 未打 roll 标签、本聊天未启用）。这是排查「技能没起作用」的主要工具。

### 9.5 开局引导

v1 的建卡区只在设置页里，玩家不打开设置就不知道要启用。改为：总开关开着、本聊天还没启用也没暂停时，阅读器首楼显示一次细线提示「数值系统 · 快速开始 / 建卡 / 本聊天不用」。选「本聊天不用」后不再提示。设置「新聊天」：询问（默认）/ 自动快速开始 / 不启用。

## 12. 易错点（v2 新增，执行前必读）

- **N1** 生成开始事件会被宿主等待，此时调酒馆 generateRaw 等于嵌套主生成。角色卡生成与补全一律放在生成结束之后。
- **N2** 插件自己发的后台请求同样会触发全局生成事件。必须经 `host/background-generation.js` 标记，数值运行时的 onStarted / onFinished 要跳过后台请求，否则会把 LLM 返回的 JSON 当成一楼正文去结算。现状：`stats-runtime.js` 没有调用 `isBackgroundGenerationActive()`，只靠 type 为 quiet 时跳过；IGS 写词等后台请求走酒馆 generateRaw 时是否会被 v1 误结算，P0 先核实，属实就一并修。
- **N3** LLM 输出只收白名单档位；出现数字整格丢弃；未知技能名走登记或丢弃；整份解析失败时不写半份数据。
- **N4** 档位换底数用「本聊天种子 + 角色名 + 技能名」派生随机数，不用 Math.random，保证重算与切换后结果一致。
- **N5** 检定 meta 记 `ruleset`；生成开始时锁定本次体系，生成中途切换不影响本次；编辑旧楼重算沿用当时体系。
- **N6** 一楼只有一个检定来源（§5 的优先级）。玩家楼里有 IGS 元叙事块时输入匹配不再掷；元叙事块带 `igs-check` 标识，与 AcuDice 写的块区分。
- **N7** 预掷的骰与结果表存在本楼生成状态 `g.preroll` 里，结束结算时按标签用同一颗骰重算，不能重掷；继续生成沿用，新发送、重 roll 重掷。表是在生成开始时按当时数值算的，结算重算也用生成开始时的数值快照（`stateBefore`），不用本楼结算后的数值。手动掷骰档另见：续写时用刚写入的 `meta.check`，不能沿用 latestEntry 的旧检定；新发送、新 swipe 时作废 pendingRoll。
- **N8** D&D 视图手改数值只回写被改的那一项，不能把整张表按投影值写回底数（会丢精度）。
- **N9** sheets 与注册表是聊天级，不进每楼快照。删楼回到某技能创建之前，技能仍在，界面不能因此报错。
- **N10** sheets 的键必须是 v1 resolveCharacter 归一后的规范名；全名、昵称先归一，避免同一人两张卡。
- **N11** roll 标签必须被所有出口剥除。`scene/directive-tags.js` 的 `STAT_INLINE_RE` 已覆盖 igs-stat 前缀，补测试确认 roll 也被剥。
- **N12** 未学技能不写存档（v1 规则）；推送到表格时缺项不推，不能推基础值冒充已学。
- **N13** 补全与角色卡生成失败最多自动重试 1 次，之后只给按钮，不循环请求。
- **N14** 手动掷骰档在自动阅读、挂机状态下会卡住，此时按预掷处理。
- **N15** 结果等级改中立后，旧存档 meta 里的 CoC 等级名（普通成功、困难成功等）照读，做兼容映射。
- **N16** 好感修正只作用于 `social` 技能，且对方是在场的已登记 NPC。
- **N17** v1 战斗技能清单里的格斗、射击、法术在默认技能里并不存在，实际一直落到力量 / 敏捷。注册表补上这些技能后，旧存档主角没有这几项，按未学基础值算，不要报错。
